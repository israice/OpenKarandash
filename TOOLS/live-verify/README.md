# Живая проверка на сервере владельца

Правило из `DOCS/agents/проверка.md`: задача закрывается после живой проверки, и проверяет агент сам. Запрет «не поднимать свой сервер» (`DOCS/decisions/002`) не означает «нельзя проверить живьём»: сервер, который поднял владелец, доступен — только не напрямую.

**Жёсткое правило.** Из сессии не запускается сервер. Второй экземпляр дерётся за `DATA/.sessions.db` и перезаписывает `DATA/vault/` (`DOCS/decisions/001`), а за собой оставляет сторож, который живёт вечно. Сервер не отвечает — так и пишешь в отчёте (раздел «Сервер не отвечает»), а не поднимаешь его.

## Что откуда видно

Всё локально: сервер отвечает только запросам с этой машины (`isLocalRequest` в `server.js`), а проверочные скрипты и есть локальный клиент. Поэтому нужен node на Windows и ничего больше.

`SYSTEM/live-check.mjs` запускается node на Windows, поднимает отдельный безголовый Edge со своим профилем `C:\Users\Public\okcheck\profile` (браузер владельца не трогает), открывает пульт (порт берёт из `.env`) и выполняет в странице переданный JS. API пульта сценарий зовёт обычным `fetch` со страницы — для сервера это локальный запрос.

## Порядок

1. `npm run check` — статическая проверка, сервер ей не нужен.
2. `npm run ui` — все вкладки, страницы «+» и окно настроек: ошибки консоли, пустые панели. Код 0 — чисто, 1 — есть замечания (чинить), 3 — прогон возможен только на Windows. Ветку исполнителя: `npm run ui -- --url <адрес предпросмотра /branch/<ветка>/>`. Прогон ничего не нажимает внутри вкладок — работает ли сама правка, он не знает.
3. Сценарий под правку — готовый или свой (ниже). Правка ленты, событий хода, новой роли или поля сессии проверяется во всех трёх отображениях: Sessions, Feed и Flow < TEMP < 321 — они рисуют одни и те же строки `/api/sessions/messages`, расхождение между ними — дефект.
4. В отчёте: что проверено живьём (чем и на какой сессии), что нет и почему.

## Готовые сценарии

Запуск одной командой из корня проекта:

```bash
node TOOLS/live-verify/run.mjs <сценарий> [ключ=значение ...] [--shot <снимок.png>] [--timeout <сек>]
```

Обёртка `run.mjs` дописывает к сценарию вызов с параметрами, кладёт готовое тело в `DATA/live/` (не в git, не под eslint, не под сторожем файлов) и зовёт `SYSTEM/live-check.mjs`. Она же ждёт, пока пульт загрузится, сама спрашивает сервер, жив ли он (до полуминуты — на случай перезапуска сторожем), ловит исключение сценария, убирает строку «Assertion failed … async.c», не зависает на первом вызове и копирует снимок куда сказано (например, в scratchpad — оттуда его можно прочитать). Код выхода: 0 — результат без `ok: false`; 1 — `ok: false`, исключение или таймаут; 2 — неверный вызов; 3 — отсюда не запустить. `--timeout` — предел самой обёртки (300 с по умолчанию); у `short-turn` свой `timeout=` на ход (240 с) — поднимая второй, подними и первый.

| Сценарий | Параметры | Что делает | Что меняет у владельца |
|---|---|---|---|
| `open` | `view=<вкладка>\|all`, `page=<папка страницы «+»>`, `count=<CSS-селектор>`, `wait=<мс>` | открывает вкладку (имена — из `App.VIEWS`) или страницу «+», меряет видимое, собирает ошибки, случившиеся при нём, считает элементы по селектору; со `--shot` — снимок открытого | ничего |
| `styles` | `select=<CSS-селектор>`, `view=<вкладка>`, `props=<список>`, `open=1`, `limit=<n>` | цвета элемента числами: фон и текст выбранного и невыбранного пункта (у селекта — `option`), плюс служебный `Add`, если он есть; без дампа всех пунктов и без снимка — раскрытый нативный список в снимок не попадает | ничего |
| `connect-cli` | `agent=opencode`, `target=<id цели>`, `detect=1` | `/api/agent/detect` и `/api/agent/connect` — то же, что Connect в Settings; отдаёт версию и бесплатные модели | переключает активное окружение этого агента на сервере |
| `short-turn` | `agent=opencode`, `model=`, `target=`, `prompt=`, `mode=Chat\|Action`, `session=<id>`, `timeout=<сек>`, `paid=1`, `cleanup=1` | короткий настоящий ход бесплатной моделью: поток `/api/agent/ask` до конца, виды живых событий против строк базы; не уложился — останавливает ход `/api/agent/stop` | заводит сессию с заголовком `[live-verify] …` (`cleanup=1` удаляет такие сессии); без `model=` зовёт connect и этим переключает активное окружение агента, как `connect-cli`; ответ завершившегося хода уходит владельцу в Telegram, если мост настроен |
| `three-views` | `session=<id>` (без него — самая новая), `wait=<мс>` | открывает сессию в Sessions, Feed и Flow < TEMP < 321, сверяет число строк и счёт реплик и размышлений с базой, разбивку по видам отдаёт как есть | выбирает сессию на канвасе «321»; активный пункт меню Flow (хранится на сервере, `/api/flow/state`) переключает на «321» и возвращает |

Обычная цепочка после правки ленты или событий:

```bash
node TOOLS/live-verify/run.mjs short-turn                       # → "session": "<id>"
node TOOLS/live-verify/run.mjs three-views session=<id> --shot <scratchpad>/flow.png
node TOOLS/live-verify/run.mjs short-turn cleanup=1             # убрать пробные сессии
node TOOLS/live-verify/run.mjs three-views                      # вернуть канвас «321» на настоящую сессию
```

**Пробный ход — только бесплатной моделью**: у OpenCode это `opencode/*-free` и `opencode/big-pickle`. Не платные и не `anthropic/*`: это деньги и лимиты владельца. `paid=1` — только когда проверяется именно этот путь. По умолчанию `short-turn` берёт OpenCode в режиме Chat. Этот режим инструментов не ограничивает (`askOpenCode` в `server.js`) — безвредность хода держится на самом вопросе, поэтому в пробном ходе ничего не проси править.

**Пробный ход виден владельцу.** Сессия появляется у него в списке, а последний ответ каждого завершившегося хода сервер шлёт в Telegram людям из `TELEGRAM_USER_IDS` (`notifyTurnFinished` в `server.js`, `DOCS/decisions/024`). Поэтому ход — один и короткий, не пачкой; убрал за собой (`cleanup=1`) — и в отчёте назвал id пробной сессии.

## Свой сценарий

Файл с одной функцией; лежать может где угодно, в том числе в scratchpad, — обёртка читает его сама:

```js
// Параметры приходят строками: node TOOLS/live-verify/run.mjs <путь>/my.js session=<id>
async function scenario(P) {
    const post = async (url, body) => (await fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(body || {}) })).json();
    const { messages = [] } = await post('/api/sessions/messages', { id: P.session });
    return { ok: messages.length > 0, roles: messages.map((m) => m.role).join(',') };
}
```

На чём прошлые сессии теряли время:

- **Всё API — только POST с JSON-телом**, кроме `/api/fragment/*`. Обычный `fetch(url)` (GET) и `?id=` в адресе получают `405 { ok: false, error: "Expected POST" }`, выдуманный путь вроде `/api/sessions/list` — `404 { ok: false, error: "Unknown endpoint" }`; данных в таком ответе нет, и сценарий, не глядя на `ok`, молча считает нули. Список сессий — `POST /api/sessions` с `{}`, строки — `POST /api/sessions/messages` с `{ id }`; текст строки лежит в `text` (не `content`), роль — в `role`.
- **Лента Sessions — `#chatList`.** `document.querySelector('.chat__list')` находит список задач на странице Feed. Сессию открывать `await App.openSession(id)`, вкладку — `MissionTabs.show('chat')`.
- **Страница «+»** открывается кнопкой `.toolbar [data-folder="<папка>"]` (у Feed — `Feed`); её `<main>` — `document.getElementById(кнопка.dataset.page)`.
- **Списки сессий в Feed (`#sessionFeedSelect`) и Flow (`#flowSessionSelect`) перечитываются по `mousedown`** на самом select: сначала событие `mousedown`, пауза, потом `value` и событие `change`. `#flowSessionSelect` показан только на канвасе «321».
- **Имена брать со страницы**, а не держать в сценарии: вкладки — `Object.keys(App.VIEWS)`, страницы «+» — `.toolbar [data-page]`. Селектор сперва подтверди Grep-ом в исходнике вкладки: разметка меняется.
- **Вкладка одна на все вызовы** и живёт между ними: положенное в `window` доживает до следующего вызова — так ведут долгий ход (первый сценарий запускает его, не дожидаясь конца, и кладёт состояние в `window.__t`, второй опрашивает). Перезагрузка страницы это стирает. Параллельные агенты делят ту же вкладку — сценарии гонять по одному.
- **После правки клиентского файла страница перезагружается сама; после правки серверного сторож перезапускает сервер**, дождавшись конца идущих ходов (`DOCS/decisions/020`). Что старый процесс погашен, видно по последней строке `DATA/server-exits.log` (`child exited … restarting=true`); новый после этого ещё секунд двадцать не отвечает — пересобирает карту проекта (`prepareVault`). Обёртка эти полминуты ждёт сама; сценарий, запущенный раньше, чем сторож заметил правку, отработает на старом коде — сверяй время строки в журнале. Новый файл `*-server.js` сторож не увидит до ручного перезапуска — это к владельцу.
- Сценарий в `SYSTEM/` или `PROJECTS/` не клади: правка там перезагружает страницу у владельца. `DATA/` и папки с точки сторож не обходит.
- Результат должен сериализоваться в JSON: узлы DOM и `Map` превращай в строки и числа.

## Нижний слой: live-check.mjs напрямую

Нужен редко — когда обёртка не подходит. Файл для него — тело async-функции с `return` на верхнем уровне (не разбирается ни `node --check`, ни eslint, поэтому его место — `DATA/live/` или scratchpad, но не папки с кодом, а писать его удобнее не Write, а из Bash — хук `syntax-check.js` на такой файл ругается):

```bash
node SYSTEM/live-check.mjs DATA/live/my.body.js DATA/live/my.png
```

- Аргументов у сценария нет: только файл тела и, если нужен снимок, путь к нему третьим словом. Путь должен быть обычным виндовым — файл из `/tmp` node на Windows не откроет, клади его в `DATA/live/` или в папку сессии.
- Первый вызов поднимает Edge и может не вернуть управление: запускать в фоне и читать вывод из файла. Следующие вызовы берут уже живой Edge.
- «Assertion failed … async.c» в конце — node на Windows при выходе, не ошибка.
- `{}` в ответе — в сценарии брошено исключение (так печатается объект ошибки). Оберни тело в `try/catch` и верни `String(e.stack)`.
- «Detected unsettled top-level await» — Edge закрыли посреди сценария (параллельный агент гасил свой). Повтори вызов.

Погасить Edge по окончании проверки — только его, по профилю; если рядом работают другие агенты, их сценарий при этом оборвётся:

```bash
powershell.exe -NoProfile -Command "Get-CimInstance Win32_Process -Filter \"Name='msedge.exe'\" | Where-Object { \$_.CommandLine -like '*okcheck\\profile*' } | ForEach-Object { Stop-Process -Id \$_.ProcessId -Force }"
```

## Сервер не отвечает

Признаки: обёртка вернула `"serverDown": true` (пульт не открылся вовсе либо страница открыта, а сервер полминуты не отвечает); `npm run ui` упал, не дойдя до списка вкладок. Страница в проверочном Edge остановку сервера переживает и выглядит живой — по открывшейся вкладке о сервере не суди. Почему сервер остановился, видно в `DATA/server-exits.log`. Дальше:

- сервер не поднимать — ни «на минуту», ни «для проверки»;
- сделать всё, что от сервера не зависит: `npm run check`, `node --check`, прямой вызов модуля (например, `SYSTEM/core/reload.js` и `SYSTEM/core/branch-preview.js` зовутся без сервера);
- в отчёте сказать прямо: сервер владельца не запущен, живьём не проверено то-то, проверю такой-то командой, когда он поднимется. Задачу в beads не закрывать.

## Прежде чем писать «живьём не проверить»

Список «осталось непроверенным» — тоже перекладывание на владельца. Сначала обходные пути (каждый уже пройден живьём — где записано, сказано в скобках):

- **Разрушительная команда** (`DOCS/decisions/049`: `npm run branches` со снятием веток) — на своих временных ветках через `--only <ветка>`.
- **CLI не подключён** («… is not connected») — подключи сам сценарием `connect-cli`, а не проси владельца открыть Settings.

Непроверенным остаётся только то, что действительно нельзя вызвать по заказу (например, `run.failed` по лимиту шагов), — и в отчёте сказано почему.
