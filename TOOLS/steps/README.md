# Из чего состояли ходы

```bash
node TOOLS/steps/run.mjs                                # сводка по последним 8 сессиям
node TOOLS/steps/run.mjs 20                             # по последним 20 сессиям
node TOOLS/steps/run.mjs 8 pi-windows-mutwv071           # одна сессия подробно
node TOOLS/steps/run.mjs 16 --vs 2026-10-04T16:00      # «было → стало»
node TOOLS/steps/run.mjs --pair <сессия-было> <сессия-стало>   # две сессии рядом
node TOOLS/steps/run.mjs 12 --turns                     # разбор по ходам, а не по сессиям
node TOOLS/steps/report.mjs                            # сводка всего сразу
node TOOLS/steps/report.mjs --since 2026-10-04T19:00   # сводка с «было → стало»
```

Скрипт читает `DATA/.sessions.db` (шаги инструментов) и разбирает их по видам из
`SYSTEM/core/waste-kinds.js` — тем же списком, по которому работает остальная
проверка ходов. Ничего не пишет и никуда не ходит.

**Форма «было → стало»** (`--vs <время>`) делит окно сессий надвое по отметке
времени и печатает обе половины рядом — по видам, а не только итогом. Правка
обычно бьёт по одному виду, и по нему и видно, сработала она или нет. Отметку
ставь по времени между старой и новой сессиями; если одна половина пуста,
инструмент так и говорит, а не рисует сравнение с нулём.

**Время везде местное.** В базе записано UTC, а инструмент печатает местное:
время в списке сессий можно скопировать и поставить в `--vs` без поправки.
Пока печаталось UTC, а отметка понималась как местное, сравнение выдавало
правдоподобную неправду — на окне из шестнадцати сессий «лишних 442 → 73»
при пустой правой половине.

**Форма «две сессии»** (`--pair <было> <стало>`) сравнивает две конкретные
сессии. Нужна там, где задача повторяется: окно по времени берёт разные задачи,
а доказательством правки служит одна и та же работа, сделанная до и после.

**Шаги на ход, а не на сессию.** Сессии разной длины сравнимы только по шагам на
ход: «80 → 65 шагов» на глаз выглядит улучшением, пока не видно, что во второй
сессии было два хода, а в первой один. Число ходов берётся из строк роли `user`.

**Виды про домашнюю работу не ставятся ходу, которому отчёт уже уехал в
запрос.** Отмечается это по `result_meta` (`suggestions.homework`): без отметки
инструмент требовал бы от агента того, что сервер уже сделал.

**`--turns`** показывает каждый ход отдельно: шаги, жёсткие лишние и сколько
символов уехало в запрос отчётом разведки. Нужен там, где сравнивают ходы **одной
сессии** между собой — сводка по сессии их сливает, и разница не видна. Именно
так выглядит доказательство работы памяти сессии: первый ход получает отчёт, а
продолжение — карту, и обе величины стоят рядом.

Колонка **«до правки»** — сколько шагов прошло до первого изменения файла, то есть
сколько стоила разведка. Это величина, которой проверяется сам отчёт разведки: по
замеру 2026-10-04 она у ходов с отчётом и без него почти одинакова (12.5 против
13.7), то есть отчёт делает оставшиеся шаги дешевле, а не короче. Держите её под
глазом: если число разойдётся — это будет первый настоящий сдвиг.


## Сводка одной командой

```bash
node TOOLS/steps/report.mjs                            # сервер, ходы, отчёт, подбор
node TOOLS/steps/report.mjs --since 2026-10-04T19:00   # и сравнение половин
```

Четыре инструмента показывают четыре среза, и держать в голове, какие запускать, —
лишняя работа. `report.mjs` сводит их в один отчёт: жив ли порт, сколько шагов на
ход и сколько лишних, ехал ли отчёт разведки и в каком объёме, подбирались ли
записки и приёмы. Каждая строка говорит, чего она **не** доказывает: например,
сводка по отчёту показывает, что он едет, но не показывает, что ходы стали
короче, — за этим идут в раздел «ходы».

## Что смотреть

**Доля жёстких лишних шагов** — это и есть та величина, которую правка должна
снижать. Считать вручную ничего не нужно: скрипт сам берёт прошлое и настоящее.

**Виды по частоте** — вид с наибольшим числом и есть следующая работа.

**Виды без пометки «мягкий»** — нарушения правила, их и надо снижать. **Мягкие**
(`read-untouched`, `console-search`, `search-same-file`, `repeat-read`,
`same-call-twice`, `verify-churn`) — время, которое тратится, но которое правило
само по себе не запрещает: чтение файла без правки допускается для правил и
названного человеком файла, консольный поиск возвращает те же совпадения, первые
два поиска по одному файлу — разведка, первая пятёрка живых проверок за сессию —
нормальная работа. В общий счёт они не идут и портят его только если забыть,
что они мягкие.

**Сессии подряд** — если лишние шаги идут поровну во всех, дело в правиле или в
том, что оно не доезжает до агента; если одна сессия выбивается, дело в задаче.

**Вид, которого больше не стало** — и есть доказательство, что изменение
сработало. Ссылаться на него в записке решения можно только отсюда.

## Накрывает ли отчёт то, что правили

```bash
node TOOLS/steps/quality.mjs      # по всем сессиям pi-windows
node TOOLS/steps/quality.mjs 10   # по последним десяти
```

`run.mjs` отвечает на вопрос «сколько шагов ушло впустую», `quality.mjs` — на
другой: «называет ли отчёт файл, который ход на самом деле правил». Пока не
называет, весь остальной механизм (`DOCS/decisions/092`) работает вхолостую, и
узнать об этом можно только здесь.

Метрика — **первый изменённый файл внутри проекта**. Всё, что правилось после,
— открытия по ходу, их отчёт назвать не может; считать их за промах отчёта
нельзя, замер от этого занижается вчетверо. Имена берутся из заголовков
`## Файл …` отчёта, а не из любого упоминания имени в его тексте: агент видит
именно заголовки, и совпадение внутри куска кода его не спасает.

Замер на всех сессиях 2026-10-04: **9 из 16**. Число небольшое, и оно честное:
часть промахов — это второй-третий адрес того же класса, открытый уже по ходу,
часть — файл, созданный самим ходом.

Снизу инструмент печатает разрез **со строкой `Code:` в клике и без неё** — это
проверка решения 091: клик с этой строкой даёт сборщику точные файлы вместо поиска
по имени класса. На 2026-10-04 — **2 из 3** со строкой и **7 из 13** без неё: выборка
мала, и «2 из 3» не доказательство размера эффекта, но направление совпадает с
замыслом, а число копится само.

В сводке есть строка **«покрытие по исполнителям»** — сколько сессий и шагов
пришлось на каждого агента в окне. Она существует после поломки прошлого цикла:
инструмент качества молча терял все сессии pi, и заметно это стало только здесь,
где один агент вдруг даёт ноль. Ноль строк у исполнителя — первый признак, что
что-то отвалилось, а не «просто тихо».
