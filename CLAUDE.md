## Карта проекта и память

Знания о проекте живут в Obsidian-vault внутри репозитория: папка `DATA/vault/` (не коммитится). Сервер создаёт и наполняет её при запуске и обновляет через 3 секунды после правок.

Что в ней лежит:
- `DATA/vault/Проект/` — заметка на каждый файл папки проекта (включая скрытые и игнорируемые git; не обходятся только `.git` и `DATA/` — всё, что сервер собрал сам), на его секции и функции, плюс `API/` с заметкой на каждый роут. Связи берутся из настоящих ссылок: литералы `/api/...`, `src`/`href`, `require`, вызовы функций.
- `DATA/vault/Сессии/` — память о прошлых сессиях: что просили, чем закончилось, какие файлы затронуты. Помеченные `stale: true` устарели — после них файлы уже менялись.

Правила:
- Ищи по проекту командой `node PROJECTS/Graph/search.js "запрос"` — полнотекстовый поиск (FTS5/BM25) по коду, заметкам и прошлым сессиям, выдаёт узел, путь и фрагмент. Фильтр: `node PROJECTS/Graph/search.js --kind session "запрос"`. Индекс собирает сервер; MCP-инструменты `obsidian_*` не используем — они требуют запущенного Obsidian и токена.
- `DATA/vault/Проект/` перезаписывается целиком при каждой пересборке. Свои заметки клади в корень vault — их никто не тронет, и они попадут и в граф, и в поиск.
- Граф смотрят во вкладке Graph веб-интерфейса, приложение Obsidian не открывается.

## Конвенции

- Проект принципиально без зависимостей: только встроенные модули Node (`node:sqlite`, `http`, `child_process`). Не создавать `package.json`, не предлагать npm-пакеты.
- Порт и любые секреты — только в `.env` (создаётся при первом запуске с `PORT=3001`, в git не попадает). Сервер поднимается строго на этом порту и соседние не подбирает: вторая копия на той же папке дерётся за `DATA/.sessions.db`/`DATA/.index.db` и перезаписывает `DATA/vault/`. Новую настройку заводить в `.env`, а не хардкодом и не отдельным файлом.
- Комментарии в коде и ответы в чате — на русском. Язык задан именно здесь, а не в личных настройках CLI: у Windows-claude и WSL-claude они разные (см. «Claude из WSL»).

## Проверка изменений

- Правки проверяются смоуком: `node SYSTEM/smoke.js`. Он сам поднимает сервер на свободном порту, дёргает маршруты и **гасит его в конце**, `.env` и `.sessions.db` не трогает. Добавили маршрут — допишите к нему `check(...)` в том же файле; других автоматических проверок в проекте нет.
- Не запускать `server.js` из сессии — ни в фоне через `&`, ни на переднем плане. Без `NO_RELOAD=1` поднимается сторож с дочерним процессом, а на Windows завершение сессии не шлёт им сигналов: оба остаются жить. Осиротевший сторож держит cwd проекта (папку нельзя переименовать), сутками крутит опрос файлов и дерётся за `DATA/.sessions.db` со следующей копией. Запуск блокирует хук `.claude/hooks/no-bg-server.js`.
- Сервер для себя пользователь запускает сам (`node server.js` в своём терминале, останов — `Ctrl+C`).
- Если зомби всё же завёлся, искать по рабочему каталогу, а не по имени процесса — в диспетчере задач он неотличим от прочих `node.exe`:

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Select-Object ProcessId, CommandLine
Stop-Process -Id <pid> -Force
```

## Claude из WSL

Сервер умеет звать не только Windows-CLI, но и WSL (`server.js`, `TARGETS`): `wsl.exe bash -lc "claude ..."`, cwd при этом становится `/mnt/c/...`. Поведение там **не полностью совпадает** с Windows — что важно знать:

- Папку проекта в WSL нужно один раз пометить доверенной, иначе `.claude/settings.json` (permissions и хуки) игнорируется целиком. Проверка — запустить `claude` в `/mnt/c/...` и принять диалог, либо выставить `projects["/mnt/c/0_PROJECTS/OpenKarandash"].hasTrustDialogAccepted: true` в `~/.claude.json` **внутри WSL** (у Windows и WSL это разные файлы).
- Хук `.claude/hooks/file-lock.js` под WSL ходит до сервера не по `127.0.0.1` (в виртуалке это её собственный loopback), а по адресу шлюза по умолчанию — его хук берёт из `/proc/net/route`. Со стороны сервера такому запросу открыт ровно один маршрут: `isWslRequest()` в `server.js` узнаёт адрес на адаптере «vEthernet (WSL)» по его же маске и пускает только `/api/claude/lock-check`. Всё остальное API (чтение и запись файлов, запуск CLI) виртуалке по-прежнему отвечает 403 — править файлы WSL-claude и так может напрямую, через `/mnt/c/...`, сервер ему для этого не нужен.
- Сессии не общие: история CLI лежит в `~/.claude/projects/C--0-PROJECTS-OpenKarandash` (Windows) и `-mnt-c-0-PROJECTS-OpenKarandash` (WSL) — продолжать сессию надо тем же CLI, которым её начали. Сервер это стережёт: в таблице `sessions` есть колонка `target`, и запрос к сессии чужого CLI отклоняется с объяснением, а не уходит в `--resume` за ошибкой. У сессий, заведённых до появления колонки, `target` пуст — их по-прежнему пускает куда угодно.
- Глобальные `~/.claude/settings.json` у Windows и WSL свои: язык ответа, набор хуков, плагинов, скиллов и субагентов различается. Модель и effort расхождением не будут — сервер передаёт их флагами на каждый запуск.
- Команды PowerShell из этого файла (поиск зомби выше) в WSL не работают — там `ps aux | grep server.js`.

## Клиентский код

Клиент целиком лежит в `SYSTEM/`. `SYSTEM/index.html` — только разметка и стили; отдаётся по адресу «/», поэтому пути в нём пишутся от корня проекта (`SYSTEM/app.js`, `PROJECTS/Graph/graph.js`), а не относительно самого файла. Скрипты подключены с `defer` отдельными файлами:

| Файл | Что в нём | Что публикует |
|---|---|---|
| `SYSTEM/app.js` | ядро: настройки и провайдеры, панель сессий, лента сообщений | `window.App` |
| `PROJECTS/Graph/graph.js` | вкладка Graph целиком (стили — `PROJECTS/Graph/graph.css`, серверная половина — `PROJECTS/Graph/graph-server.js`, поиск из терминала — `PROJECTS/Graph/search.js`) | `window.MissionGraph` |
| `PROJECTS/Flow/flow.js` | вкладка Flow целиком (стили — `PROJECTS/Flow/flow.css`) | `window.MissionFlow` |
| `PROJECTS/Kanban/kanban.js` | вкладка Kanban целиком (стили — `PROJECTS/Kanban/kanban.css`) | — |
| `PROJECTS/Edit/button-edit.js` | кнопка Edit целиком: своя разметка + комментарии к элементам (стили — `PROJECTS/Edit/button-edit.css`, серверная половина — `PROJECTS/Edit/screenshot.js`) | — |
| `PROJECTS/Settings/settings.js` | кнопка-шестерёнка и окно настроек целиком: своя разметка + логика провайдеров (стили — `PROJECTS/Settings/settings.css`) | `window.Settings` |
| `SYSTEM/home-tasks.js` | вкладка Home | — |
| `SYSTEM/tabs.js` | панель вкладок, `showView` | `window.MissionTabs` |
| `SYSTEM/toolbar-reorder.js` | drag-and-drop кнопок `.toolbar` по долгому нажатию | — |
| `SYSTEM/sessions-toggle.js` | кнопка Sessions в тулбаре Chat | — |
| `SYSTEM/toolbar-menu.js` | меню кнопки «+» в тулбаре табов: показать/скрыть остальные кнопки (стили — `SYSTEM/toolbar-menu.css`) | — |

Правила, чтобы одна поломка не гасила интерфейс целиком:
- Никогда не класть JS обратно в `<script>` внутри `index.html`. Новый кусок интерфейса — новый файл с `defer`: браузер выполняет их независимо, и исключение в одном не отменяет остальные.
- Чужое (`App.openModal`, `MissionTabs.show`, …) вызывать **внутри функций и обработчиков**, а не на верхнем уровне файла. Тогда порядок загрузки ни на что не влияет и циклические связи безопасны.
- `app.js` идёт первым: остальные файлы берут из `window.App` общее ядро.
- Всё, что сервер подставляет в HTML (`{{APP_VERSION}}`, `{{VERSION_LIST}}`), обязано проходить через `escapeHtml` в `server.js` — иначе `<` из сообщения коммита рвёт страницу.
