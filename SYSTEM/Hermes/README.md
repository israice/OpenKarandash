# Hermes

Оркестратор: принимает цель целиком, сам дробит её на подзадачи, выполняет и проверяет. Моделью не является — см. [DOCS/decisions/007](../../DOCS/decisions/007-hermes-оркестратор-а-не-модель.md) и [целевую архитектуру](../../DOCS/целевая-архитектура.md).

Лежит в `SYSTEM/`, а не в `PROJECTS/`: `PROJECTS/` — разделы самого приложения, у каждого своя кнопка в тулбаре и карточка в списке. Hermes ни тем, ни другим не является — это часть системы, которой приложение строится.

## Установка

Ничего делать не нужно: сервер ставит Hermes сам при первом запуске (см. [DOCS/decisions/008](../../DOCS/decisions/008-установка-hermes-при-первом-запуске.md)). Ход установки виден на вкладке Hermes, провайдер выбирается в настройках.

Руками, без сервера:

```bash
node SYSTEM/Hermes/hermes-setup.js --status    # что уже готово
node SYSTEM/Hermes/hermes-setup.js --install   # доставить недостающее
```

Отключить автоустановку — `HERMES_AUTOINSTALL=0` в `.env`.

## Из чего состоит

| Файл | Что делает |
|---|---|
| `hermes-setup.js` | установка при первом запуске: агент, окружение Python, конфиг |
| `hermes-agent-connector.js` | Hermes как исполнитель: цели (Windows/WSL), команда запуска, отчёт о расходе |
| `hermes-server.js` | маршруты установки и выбора провайдера |
| `agent/` | сам Hermes на коммит из `AGENT-PIN.txt`; в git не попадает |
| `runtime/<win\|wsl>/` | окружения Python, по одному на систему; в git не попадают |
| `../templates/hermes-setup.eta`, `../templates/hermes-provider.eta` | панели установки и выбора провайдера |

## Маршруты

| Путь | Что делает |
|---|---|
| `/api/hermes/setup/status` | что уже установлено, идёт ли установка, последние строки лога |
| `/api/hermes/setup/start` | доставить недостающее; на готовой установке ничего не делает |
| `/api/hermes/provider/set` | провайдер и модель из настроек: ключ в `.env`, выбор в конфиг Hermes |
| `/api/fragment/hermes-setup` | панель хода установки |
| `/api/fragment/hermes-provider` | выбор провайдера в окне настроек |

## Дробление и проверка — внутри Hermes

Своего планировщика и проверяющего в проекте нет и не будет: раньше они были написаны здесь (`plan`/`start`/`stop`/`state`), но настоящий Hermes умеет это сам, и самописная копия немедленно расходилась с ним. Осталось только то, чего у него нет: установка, выбор провайдера и запуск его как исполнителя. Мотив — в [целевой архитектуре](../../DOCS/целевая-архитектура.md), раздел «Разделение ролей».

## Hermes как исполнитель

Помимо своей вкладки Hermes доступен как обычный провайдер в чате — строка `hermes` в таблице `AGENTS` сервера. Подключается в Settings: выбирается не путь к CLI (он ставится вместе с проектом), а **система запуска**.

| Цель | Когда доступна | Как зовётся |
|---|---|---|
| `hermes-windows` | сервер на Windows и стоит `runtime/win` | напрямую, `Scripts\hermes.exe` |
| `hermes-wsl` | сервер в WSL, либо сервер на Windows (тогда через `wsl.exe bash -lc`) | `runtime/wsl/venv/bin/hermes` |

Запуск идёт через `hermes -z "<задание>"` — единственный режим Hermes, рассчитанный на скрипты: печатает только итоговый текст, инструменты, память и `AGENTS.md` при этом загружаются как обычно, подтверждения обходятся.

**Как потом понять, кто выполнил задание.** К каждому ответу сервер прикладывает отчёт `--usage-file`, который пишет сам Hermes, и кладёт его в историю сессии полем `result_meta`:

```json
{ "executor": "hermes", "target": "hermes-wsl", "provider": "openrouter",
  "model": "…", "hermesSessionId": "…", "apiCalls": 3 }
```

`hermesSessionId` — id запуска в состоянии самого Hermes (`DATA/hermes`), по нему сессия находится и с его стороны. Колонка `target` в таблице `sessions` хранит `hermes-wsl` / `hermes-windows`, так что перепутать исполнителя с Claude нельзя.


## Hermes и подписка Claude

Claude в этом проекте запускается только через CLI — своего ключа `ANTHROPIC_API_KEY` нигде нет, и заводить его не нужно. Hermes это устраивает: у него есть источник учётных данных `claude_code`, который читает вход Claude Code (`~/.claude/.credentials.json`, `agent/credential_sources.py`). Поэтому провайдер `anthropic` работает **по той же подписке**, что и Claude CLI.

В настройках это первый вариант — «Claude по подписке CLI»: поле ключа для него заполнять не надо.

Проверено запуском: `hermes auth list` показывает

```
anthropic (1 credentials):
  #1  claude_code          oauth   claude_code ←
```

а одношаговый запуск отвечает и пишет в отчёт `provider: anthropic`, `model: claude-sonnet-5` при пустых `ANTHROPIC_API_KEY` в окружении, в `.env` проекта и в `.env` Hermes.

**Модель указывать обязательно.** С пустой моделью Hermes уходит в API с пустым полем и получает `HTTP 400: model: String should have at least 1 character` — по этой ошибке причину не угадать. Поэтому у провайдера есть умолчание (`claude-sonnet-5` для Anthropic), которое подставляется, если поле оставили пустым. Имена моделей у Hermes свои: `claude-sonnet-5`, `claude-opus-4-8`, `claude-haiku-4-5-20251001` — с дефисами, не с точками.
