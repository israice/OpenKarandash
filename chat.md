Да. Если убрать тему локальных LLM, то вся наша идея сводится к следующему.

### 1. Канвас — как в n8n, но смысл другой

Берём только саму механику:

- бесконечный canvas;
- zoom;
- связи между нодами;
- движение по графу;
- realtime-построение;
- визуальные состояния.

Но **ноды — не workflow-операции**, а реальные элементы происходящего с агентом.

---

### 2. Граф показывает всю сессию

Во время работы агента граф строится в реальном времени.

На нём видно:

- сообщение пользователя;
- что агент получил;
- какие правила применились;
- какие документы прочитал;
- какие данные были впрыснуты в контекст;
- какие инструменты вызвал;
- какие MCP использовал;
- что получил от MCP;
- поисковые запросы и результаты;
- решения;
- вопросы пользователю;
- ответы пользователя;
- действия;
- ошибки;
- результаты;
- ответ пользователю;
- переходы между этапами.

То есть получается **карта фактического выполнения**, а не заранее нарисованный workflow.

---

### 3. Разные типы нод визуально различаются

Каждый тип имеет:

- собственную иконку;
- цвет;
- форму/визуальный стиль;
- состояние выполнения.

Например:

- 💬 пользователь;
- 🤖 ответ модели;
- 📄 Markdown;
- 🔍 web search;
- 🔌 MCP;
- 🛠 tool;
- 📁 файл;
- 🧠 memory;
- 📚 RAG;
- ❓ обязательный вопрос;
- ✅ подтверждение;
- ⚠️ ошибка;
- 🔀 решение/ветвление;
- 👤 другой агент;
- 📋 правило;
- 🎯 цель.

Пользователь должен **с одного взгляда понимать граф**.

---

### 4. Каждая нода раскрывается гармошкой

Не отдельное окно.

Нода остаётся на canvas, а внутри раскрываются секции:

**Что вошло**
→ входные данные.

**Что произошло**
→ действие.

**Что вышло**
→ результат.

**Контекст**
→ что было передано дальше.

**Инструмент**
→ какой именно tool/MCP был вызван.

**Результат инструмента**
→ что он вернул.

Для разных типов нод набор гармошек разный.

---

### 5. Главное — происхождение каждого шага

Связи должны показывать:

> **откуда появилось это действие и что на него повлияло.**

Например:

```
User
  ↓
Rule: "сначала проверить наличие MCP"
  ↓
Search MCP
  ↓
MCP найден
  ↓
MCP installed
  ↓
MCP result
  ↓
Agent decision
  ↓
Answer
```

Таким образом можно восстановить реальную цепочку.

---

### 6. Ноды должны быть редактируемыми

И вот здесь находится главная идея проекта.

Ты смотришь на уже выполненную сессию и говоришь:

> «Вот здесь перед этим шагом надо было обязательно задать вопрос».

Ты **вставляешь ноду прямо между существующими нодами**.

Например:

```
Find document
      ↓
    ❓ "Уточнить формат?"
      ↓
Read document
```

И эта правка становится **правилом для будущих сессий**.

То есть ты не пишешь огромный system prompt.

Ты **исправляешь поведение агента непосредственно на графе**.

---

### 7. Можно добавлять обязательные гейты

Например:

```
Task
 ↓
❓ Ask user
 ↓
Validation
 ↓
Tool
 ↓
Result
```

Гейт может означать:

- обязательно спросить;
- обязательно подтвердить;
- обязательно проверить;
- обязательно найти инструмент;
- обязательно получить документ;
- нельзя продолжать без результата;
- при отсутствии результата перейти в другой путь.

---

### 8. Правила становятся отдельными нодами

Вместо:

> огромного system prompt на несколько тысяч токенов

получаем маленькие независимые правила:

```
Rule A
Rule B
Rule C
Rule D
```

И граф показывает, **какое правило реально было применено**.

Это позволяет постепенно строить поведение агента из небольших компонентов.

---

### 9. Документы становятся частью графа

Если агент использовал `something.md`, пользователь видит **сам файл как ноду**.

Можно:

- открыть содержимое прямо в ноде;
- изменить его;
- сохранить;
- увидеть новую версию;
- увидеть, где этот документ используется.

Особенно важно различать:

```
document.md
```

как постоянный источник и

```
document.md @ session
```

как конкретное использование этого документа в сессии.

---

### 10. Самое интересное — редактирование собственных слов

Это не просто version control.

Ты можешь увидеть:

> «Вот здесь я сказал агенту X».

И изменить это непосредственно там.

Получается очень простой способ **редактировать собственные инструкции, знания и правила поведения**, не занимаясь инженерией prompt'ов.

---

### 11. Граф постепенно «выпрямляется»

Первоначально агент может делать:

```
A → B → C → D → E → F → G
```

После нескольких сессий и твоих исправлений:

```
A → C → E → G
```

Потому что ненужные рассуждения и действия становятся формализованными правилами.

То есть система превращается из:

**«агент каждый раз думает, что делать»**

в:

**«агент уже знает правильный маршрут, а думает только там, где действительно нужна интеллектуальная работа».**

Это потенциально даёт:

- меньше токенов;
- меньше задержки;
- меньше ошибок;
- более предсказуемое поведение;
- более дешёвое выполнение;
- более устойчивые результаты.

---

### 12. Модели становятся просто компонентами графа

Одна модель может вызвать другую:

```
Main Agent
    ↓
Specialist Agent
    ↓
Structured Result
    ↓
Main Agent
```

Результат возвращается обратно в текущий flow.

То есть **LLM — это тоже нода**, а не центр всей архитектуры.

---

### 13. Можно делать специалистов

Разные профили могут иметь разные:

- правила;
- инструменты;
- MCP;
- документы;
- обязательные вопросы;
- разрешения;
- маршруты.

И один агент может передать часть работы другому.

Получается:

```
Orchestrator
   ├── Research Agent
   ├── Coding Agent
   ├── Review Agent
   └── Specialist Agent
```

---

### 14. Самое важное отличие от обычного workflow

n8n отвечает на вопрос:

> **«Что должно произойти?»**

Твоя система должна отвечать на два вопроса:

> **«Что реально произошло?»**

и

> **«Как изменить то, что будет происходить в следующий раз?»**

И вот второе — ключевое.

Пользователь не программирует агента традиционным способом.

Он **наблюдает его поведение → вмешивается в граф → исправляет → получает новое поведение в будущих сессиях.**

По сути, это можно сформулировать одной фразой:

> **Canvas становится интерфейсом редактирования поведения агента.**

И тогда граф — одновременно **runtime trace, память поведения, debugger и редактор будущих правил**.
