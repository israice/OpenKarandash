# Web Linux Desktop

Независимые графические рабочие столы Linux в Docker-контейнерах с доступом из
обычного браузера через noVNC. Один общий образ, N сессий, никакого Chrome
внутри. Стек — Docker Engine + Compose + небольшой менеджер сессий на FastAPI.

```
Браузер ──HTTP──► manager (FastAPI :8080)
                  ├── /s/            список сессий (HTTP Basic)
                  ├── /s/<id>/       noVNC-клиент
                  ├── /ws/<id>/      WebSocket ──прокси──► RFB (x11vnc)
                  ├── /api/...       CRUD сессий + контроль ресурсов
                  └── docker-proxy ──► Docker API
                                        │
                                        ▼
                          wd-<id>  контейнер-сессия (общий образ)
                          Xvfb :N → LXDE (openbox + lxpanel + pcmanfm)
                                → x11vnc → 127.0.0.1:5900+ (внутренняя сеть)
                          wd-home-<id>  Docker volume с домашним каталогом
```

## 1. Что внутри образа сессии

| Компонент | Зачем |
|---|---|
| `debian:trixie-slim` | база |
| `xvfb`, `xauth`, `x11-utils` | виртуальный дисплей |
| `x11vnc` | RFB-сервер поверх Xvfb |
| `lxde-core` | полноценный десктоп: `startlxde`, `lxsession`, `openbox` (WM), `lxpanel` (панель + меню приложений), `pcmanfm` (рабочий стол + файловый менеджер), `lxterminal`, `lxmenu-data`, `lxsession-logout`. В trixie весь LXDE — **GTK3**, GTK2-приложений в образе нет || `x11-xserver-utils` | `xrandr` для смены разрешения |
| `dbus`, `dbus-x11` | шина сессии, без неё панель и рабочий стол сыпятся |
| `menu-xdg` | `debian-menu.menu` — без него подменю «Debian» в меню приложений пустое |
| `xdg-utils` | `xdg-open`: без него файловый менеджер не открывает документ нужной программой |
| `libglib2.0-bin` | `gsettings` — смена темы иконок без `lxappearance` |
| `tango-icon-theme` | полноцветные «легаси»-иконки (`terminal`, `system-file-manager`, `gnome-log-out`, …), которых нет в Adwaita |
| `adwaita-icon-theme` | символьные иконки, которые запрашивают все GTK3-виджеты (`view-refresh-symbolic`, `dialog-information-symbolic`, …) |
| `librsvg2-common` | **SVG-загрузчик gdk-pixbuf**. Без него не декодируется ни один SVG: и все масштабируемые иконки (включая Tango), и ассеты самой темы GTK (`bullet-symbolic.svg`) рисуются пустыми |
| `fonts-dejavu-core` | иконки и шрифты |
| `procps`, `psmisc` | `pgrep`/`pkill` в супервизоре |
| `sudo` | пользователь сессии становится root внутри контейнера: без него `sudo apt-get install` не работает и в сессии **ничего не установить** |
| `ca-certificates`, `curl` | https-загрузки (`curl \| bash` — обычный способ поставить утилиту) |

Менеджер сессий (отдельный образ) — это FastAPI + docker SDK + статика noVNC.
noVNC отдаётся менеджером, а не отдельным контейнером на сессию: один вход,
одна точка авторизации, один WebSocket-прокси.

## 2. Быстрый старт

```bash
cp .env.example .env      # можно вообще ничего не менять
docker compose up -d --build
```

Откройте в браузере:

* `http://127.0.0.1:8080/s/` — список сессий, **уже без логина и пароля**.

На странице есть кнопка «+ Start a desktop»: нажали — создалась сессия,
дождались готовности и браузер сам открыл рабочий стол. Никаких паролей,
никаких команд в терминале.

Из терминала, если нужно:

```bash
./scripts/desktop-session.sh create --resolution 1440x900
# session 3f9c1a20be44 created (starting)
# url: http://127.0.0.1:8080/s/3f9c1a20be44/
```

и откройте полученный URL. Никаких VNC-клиентов ставить не нужно.

### Автологин — как это устроено

По умолчанию `MANAGER_AUTO_LOGIN=1`: тот, кто открыл URL, сразу считается
пользователем `MANAGER_USER` (по умолчанию `admin`). Ни пароля, ни формы входа,
ни HTTP Basic-запроса в браузере. Статика noVNC и WebSocket проверяются той же
логикой, поэтому картинка не «протекает» мимо автологина.

Значит «достижимость URL = вход». Отсюда два следствия:

* `MANAGER_BIND` по умолчанию `127.0.0.1` — снаружи машины сервис не виден;
* если нужен доступ из сети, поставьте перед менеджером обратный прокси со своей
  аутентификацией либо выключите автологин (`MANAGER_AUTO_LOGIN=0`) и задайте
  `MANAGER_USER` / `MANAGER_PASSWORD` — тогда вернётся обычный HTTP Basic.

`MANAGER_PASSWORD` и `MANAGER_API_TOKEN` остаются необязательными: они нужны
только скриптам, которые хотят аутентифицироваться явно. Проверить, кем вы
сейчас считаетесь: `curl http://127.0.0.1:8080/api/whoami`.

## 3. Установка на чистый Debian/Ubuntu

```bash
# 1. Docker Engine + Compose plugin
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg python3
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/debian $(lsb_release -cs) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
     docker-buildx-plugin docker-compose-plugin

# 2. Проект
sudo mkdir -p /opt/webdesktop && sudo chown "$USER" /opt/webdesktop
cp -r . /opt/webdesktop && cd /opt/webdesktop
cp .env.example .env        # .env можно не править: пароль не требуется

# 3. Запуск
docker compose up -d --build
```

Требуется Python 3.9+ на хосте только для скриптов; в самих контейнерах
интерпретатор нужен лишь менеджеру (он внутри образа).

Проверка:

```bash
docker compose ps
curl -s http://127.0.0.1:8080/healthz
python3 tests/test_acceptance.py      # полный набор критериев приёмки
```

#### Почему `docker compose down` иногда ругается на сеть

```
! Network webdesktop_sessions Resource is still in use
```

Контейнеры сессий создаются менеджером через Docker API и **не являются
сервисами compose**, поэтому compose их не останавливает. Каждый такой
контейнер держит endpoint во внутренней сети `webdesktop_sessions`, и сеть не
удаляется.

Менеджер решает это сам: при остановке (SIGTERM) он **останавливает** все свои
контейнеры по метке `webdesktop.session` (но не удаляет), а у compose выставлен
`stop_grace_period: 45s`, чтобы это успело произойти до SIGKILL. Остановленный
контейнер сеть не держит, поэтому обычный `docker compose down` проходит.

Сессии при этом не теряются. При следующем старте менеджер поднимает ровно те
сессии, которые считал работающими: запись в базе сессий остаётся `running`.
Сессия, остановленная пользователем через API или UI, хранится как `stopped` и
не поднимается.

Отдельно стоит случай `down` → `up`. Compose при `down` удаляет сеть сессий, а
при `up` создаёт заново, уже с **новым** id, — остановленные контейнеры остаются
привязаны к несуществующей сети и не могут стартовать. Менеджер это
распознаёт и пересоздаёт такой контейнер с тем же именем; домашний том — отдельный
объект — сохраняется, поэтому файлы пользователя не теряются. Проверяется
тестом `7b`.

Если менеджер был убит через `docker kill -9` или запущен с
`STOP_SESSIONS_ON_SHUTDOWN=0`, используйте скрипт — он останавливает менеджер,
подчищает всё оставшееся и только затем вызывает `compose down`:

```bash
./scripts/down.sh              # контейнеры и сети, домашние тома сохраняются
./scripts/down.sh --data       # плюс удалить тома сессий (wd-home-*)
./scripts/down.sh --volumes    # плюс удалить всё, включая тома менеджера
```

```powershell
.\scripts\down.ps1
.\scripts\down.ps1 -SessionData
.\scripts\down.ps1 -Volumes
```

Переключатель в `.env`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STOP_SESSIONS_ON_SHUTDOWN` | `1` | Останавливать контейнеры сессий при остановке менеджера, чтобы `compose down` проходил. `0` — сессии продолжат работать, и чистить их придётся вручную (или через `scripts/down.sh`). |

Прямой доступ к API, если скрипты не подходят (пароль не нужен — работает
автологин):

```bash
curl -X POST http://127.0.0.1:8080/api/sessions \
     -H 'Content-Type: application/json' -d '{"resolution":"1280x800"}'
curl http://127.0.0.1:8080/api/sessions
curl -X POST http://127.0.0.1:8080/api/sessions/<id>/restart
curl -X DELETE "http://127.0.0.1:8080/api/sessions/<id>?delete_data=true"
curl http://127.0.0.1:8080/api/resources | python3 -m json.tool
```

Если автологин выключен (`MANAGER_AUTO_LOGIN=0`), к каждому запросу добавьте
`-u admin:$PASS` или `-H "Authorization: Bearer $MANAGER_API_TOKEN"`.

## 5. Ресурсы

### 5.1 Ограничения на сессию

Задаются в `.env` (или `config/manager.yaml`), применяются Docker'ом как
**жёсткие** лимиты при создании контейнера:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `SESSION_MEMORY_MB` | 512 | жёсткий лимит RAM |
| `SESSION_CPUS` | 0.5 | квота CPU |
| `SESSION_PIDS_LIMIT` | 512 | защита от fork-бомбы |
| `SESSION_TMPFS_MB` | 64 | `/tmp` контейнера (X-сокет, логи) |

Swap отключён (`MemorySwap == Memory`), `CapDrop=ALL`,
`no-new-privileges`, tmpfs для `/tmp`, файловая система не read-only (создана
для полноценного десктопа, изоляцию обеспечивают лимиты и отдельный том).

`TMPDIR` в сессии указывает на **том с домашним каталогом**
(`/home/desktop/.tmp`), а не на `/tmp`: tmpfs на 64 МиБ — это память сессии
и `noexec`, а установщики вида `curl -fsSL … | bash` качают и распаковывают
туда сотни мегабайт (CLI opencode — 94 МиБ архив и ~213 МиБ распакованного
бинаря). В tmpfs это либо `ENOSPC` (`curl: (23) Failure writing output to
destination`), либо съеденная RAM сессии. На томе с файлами места хватает
всегда, и `curl | bash` работает без плясок с `TMPDIR`.

### 5.2 Контроль нагрузки

Compose не планировщик ресурсов, поэтому перед созданием контейнера менеджер
проверяет:

* `max_sessions` — сколько сессий одновременно допустимо;
* `min_free_memory_mb` — сколько свободной RAM должно остаться **до** старта;
* `reserve_memory_mb` — сколько должно остаться **после** добавления лимита
  новой сессии;
* `min_free_disk_mb` — свободное место под `/var/lib/docker`;
* `max_load_per_cpu` — load average на ядро.

Если ресурсов не хватает, при `OVERLOAD_ACTION=queue` запрос встаёт в очередь
(до `MAX_QUEUE`, ждать `QUEUE_TIMEOUT_S`), при `OVERLOAD_ACTION=reject` сразу
получает HTTP 429 с конкретной причиной.

**Уже работающие сессии никогда не убиваются из-за лимитов** — ограничения
применяются только к новым сессиям.

Менеджер читает `/host/proc`, `/host/sys` и `/host/var/lib/docker`
(read-only монтирования), поэтому видит хост, а не свой собственный cgroup.

### 5.3 Измеренные значения

Замерено на Debian 13 (trixie), Docker Engine, контейнер `1440x900`:

| Величина | Значение |
|---|---|
| `docker image ls` | 493 MB |
| Сжатый образ (то, что тянется по сети) | **123.6 MB** (`docker image inspect --format '{{.Size}}'`) |
| Распакованный образ (22 слоя, `docker history`) | **369 MB** |
| Установленные пакеты | 430 MB в 327 пакетах |
| RAM одной сессии в простое | **≈ 64 MB** (`docker stats`), пик до ~150 MB при запуске приложений |
| CPU одной сессии в простое | < 1.5 % ядра |
| Лимит по умолчанию | 512 MB / 0.5 CPU |

Про `docker image ls`: Docker Desktop в режиме containerd image store
показывает сумму распакованных слоёв **плюс** сжатый размер (369 + 124 ≈ 493),
поэтому число завышено примерно втрое. Проверяйте `docker image inspect <image>
--format '{{.Size}}'` (сжатый) и `docker history` (распакованный). Скрипт
`scripts/image-size.sh` печатает все три числа.

Логика уменьшения образа (каждый шаг замерен на этой машине):

| Шаг | Установлено | Сжатый образ |
|---|---|---|
| LXDE + X + зависимости, `--no-install-recommends` | 714 MB | — |
| удалён Mesa (libLLVM 124 MB, gallium 41 MB, libz3 27 MB) — Xvfb с `-extension GLX` | ~500 MB | — |
| multi-stage: `.deb` из apt-кеша удаляются, но остались бы в том же слое → `COPY --from` | 367 MB | **126 MB** |
| возврат `adwaita-icon-theme` + `librsvg2-common` (иконки и SVG-загрузчик) | 383 MB | 128 MB |
| чистка вычистки: Ghostscript, polkit, systemd, lightdm убраны **согласованно** | 367 MB | **124 MB** |

### Что вычищается и как

Пять стеков пакетов в контейнере бесполезны, но apt не может их удалить сам:
каждый из них — жёсткая зависимость чего-то нужного.

| Стек | Кто его тянет | Почему убираем |
|---|---|---|
| Mesa GL (libLLVM 126 MB) | `xvfb → libgl1 → libglx0 → libglx-mesa0` | Xvfb запускается с `-extension GLX` и никогда не создаёт GL-контекст; нужны только `libGL.so.1`/`libGLX.so.0` из `libgl1`/`libglx0` — они остаются |
| Ghostscript CLI + шрифты URW (15 MB) | `libspectre1 → libgs10` | нужен только openbox для SVG/PDF-оформления окон; штатная тема LXDE растровая |
| polkit | `lxsession → lxpolkit`, `lxsession-logout → polkitd` | polkit не может ничего решать внутри контейнера, а агент только рисует ошибку «No session for pid N» |
| systemd | `lxsession → libpam-systemd → systemd` | шину сессии запускает сам `entrypoint.sh` (`dbus-launch`) |
| display manager (`lightdm`) | `light-locker → lightdm` | менеджера дисплея в контейнере нет |

Вычистка идёт через `dpkg --purge --force-all`, и оставшиеся зависимости закрывает
**dummy-пакет** `webdesktop-slim-stub`: он ничего не содержит, но объявляет
`Provides` для имён удалённых пакетов (`libglx-mesa0`, `libspectre1`,
`polkit-1-auth-agent`, `polkitd`, `default-dbus-session-bus`, `light-locker`).
Без него база dpkg остаётся несогласованной и **любой `apt-get install` внутри
образа падает** с «Unmet dependencies». Состояние проверяет тест `11c`
(`apt-get check`).

Сравнение с XFCE (`xfce4` вместо LXDE) не проводилось: LXDE уже даёт полный
десктоп, а XFCE добавляет xfce4-panel/xfwm4/xfdesktop, то есть больше пакетов
при том же результате. Если понадобится, `docker build --build-arg` с другим
списком пакетов покажет разницу.

## 6. Безопасность

Что уже сделано:

* **VNC-порт не публикуется на хосте.** Он существует только в bridge-сети
  `webdesktop_sessions`, и достучаться до него может только менеджер (и сами
  сессии — они в той же сети). На хост не пробрасывается ни один порт.
* **Аутентификация везде**: HTTP Basic на `/api/*`, `/s/*` и на WebSocket
  upgrade. Пароли сравниваются через `hmac.compare_digest` и никогда не
  передаются в URL.
* **Изоляция сессий**: у каждой свой контейнер, свой `DISPLAY`, свой порт,
  свой Docker volume, свой пользователь `desktop` (uid 1000).
* **Менеджер выполняет только session-scoped команды.** Узкий NDJSON `exec`
  API сначала проверяет владельца сессии и managed-container label, а
  остановка дополнительно сверяет `exec` с конкретным контейнером. Произвольные
  Docker-команды и доступ к сокету из desktop-контейнера отсутствуют.
* **`CapDrop=ALL` + точечный `CapAdd`**: обратно возвращается ровно то, что
  нужно `dpkg` для установки пакетов (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`,
  `FSETID`, `SETGID`, `SETUID`, `SETFCAP`, `SYS_CHROOT`, `KILL`,
  `AUDIT_WRITE`). `SYS_ADMIN`, `NET_ADMIN`, `SYS_PTRACE`, `SYS_MODULE` по
  прежнему отброшены, `privileged` не используется.
* **Секретов в образе нет**: `VNC_PASSWORD` не запечён в `Dockerfile`,
  передаётся менеджером через API Docker при создании контейнера.
* Владелец сессии видит только свои сессии; идентификатор сессии не считается
  секретом.

Что **сознательно ослаблено** — ради рабочей сессии:

* **Внутри сессии есть root.** Пользователь `desktop` может стать root через
  `sudo` без пароля: иначе в сессии нельзя ничего установить.
  `no-new-privileges` у сессий отключён именно поэтому — он запрещает
  setuid-переход, и с ним `sudo` не работал бы вовсе. Границы контейнера
  при этом прежние: нет `docker.sock`, нет монтирований с хоста, жёсткие
  лимиты RAM/CPU/pids, отдельный том.
* **У сессии есть выход в интернет** (сеть `webdesktop_sessions` больше не
  `internal: true`) — иначе не скачать ни пакета, ни скрипта установки.
  Побочный эффект: сессия дотягивается и до портов, опубликованных на
  хосте. На Docker Desktop for Windows до IP самого хоста она не
  дотягивается, на Linux — дотягивается.
* **Менеджер умеет читать файлы из сессии** (`get_archive`) — без этого файл
  нельзя вынести на хост. Область видимости ограничена домашним томом
  сессии (`/home/desktop`), остальные пути отклоняются.

Что нужно сделать перед публикацией в интернет:

```bash
# 1. Терминация TLS перед менеджером
cat > compose.tls.yaml <<'YAML'
services:
  manager:
    ports: !reset []
  caddy:
    image: caddy:2-alpine
    restart: unless-stopped
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy-data:/data
    networks: [edge]
volumes:
  caddy-data:
YAML

cat > Caddyfile <<'CADDY'
desktop.example.com {
    reverse_proxy wd-manager:8080
}
CADDY

docker compose -f compose.yaml -f compose.tls.yaml up -d
```

Caddy сам получит сертификат Let's Encrypt. WebSocket проксируется
прозрачно. Если TLS терминируется на nginx/haproxy, важно только пробросить
заголовок `Upgrade`/`Connection` и не буферизовать ответ.

Дополнительно стоит:

* задать `MANAGER_API_TOKEN` для скриптов, чтобы не светить пароль в `ps`;
* ограничить `MANAGER_BIND=127.0.0.1`, если прокси стоит на той же машине;
* если прокси сам умеет аутентифицировать (basic auth на Caddy, OAuth на
  nginx), оставить автологин включённым — менеджер внутри сети закрыт, а
  снаружи пароль спрашивает прокси; либо выключить `MANAGER_AUTO_LOGIN=0`
  и задать `MANAGER_PASSWORD` в самом менеджере;
* включить `ALLOWED_ORIGINS`, если API дёргает другой фронтенд;
* настроить ротацию `MANAGER_PASSWORD` (менеджер перезапустить:
  `docker compose up -d manager`).

## 7. Устройство сессии

### Первый запуск

`entrypoint.sh` при старте один раз копирует `/opt/desktop-defaults` в домашний
каталог (том), помечая это файлом `~/.desktop-initialized`:

* `wallpaper.png` — обои;
* `Desktop/*.desktop` — ярлыки Home, File Manager, Terminal, Set Screen
  Resolution, Desktop Preferences, Icon Theme, Restart Desktop;
* `.config/lxsession/LXDE/autostart` — панель + рабочий стол + их
  автовосстановление;
* `.config/lxpanel/LXDE/panels/panel` — панель;
* `.config/pcmanfm/LXDE/desktop-items-0.conf` — обои и настройки рабочего стола;
* `bin/` — вспомогательные скрипты.

Повторный запуск контейнера пользовательские изменения **не трогает** —
кроме ярлыков рабочего стола и панели: они принадлежат образу (ярлыки и так
возвращаются, если пользователь их удалил), поэтому обновляются при старте.
Свою раскладку панели при этом сохранить можно: как только `lxpanel`
перезаписывает файл (пользователь что-то перетащил), метка `webdesktop-managed`
исчезает и образ больше не трогает этот файл.

### Панель, окна, ярлыки

Панель (`lxpanel`) с меню приложений (`lxmenu-data`), переключателем окон и
часами, оконный менеджер — `openbox` с темой LXDE, рабочий стол — `pcmanfm
--desktop`: иконки, контекстное меню, перетаскивание, окна с заголовками,
рабочие области.

Панель запускает файловый менеджер и терминал. Двух кнопок из штатной панели
нет:
* **браузера** — его в образе нет по замыслу (он живёт на клиенте), а
  `/usr/bin/x-www-browser` не существует: кнопка только вводила в заблуждение;
* **блокировки экрана** — `lxlock` требует один из системных блокировщиков
  (`light-locker`, `xscreensaver`, …), которых в образе нет, а у пользователя
  сессии нет пароля: заблокированную сессию уже не разблокировать из браузера.
  Кнопка, которая запирает пользователя снаружи, хуже, чем её отсутствие.

### Иконки

Иконки в сессии — **GTK3**: в trixie весь LXDE (`lxsession`, `lxpanel`,
`pcmanfm`, `lxterminal`) собран на GTK3. GTK3 строит цепочку поиска так:

```
<текущая тема> → Adwaita → gnome → hicolor
```

(см. `gtk_icon_theme_load_themes()` в `gtkicontheme.c`). Отсюда решения:

* **Tango** — текущая тема: это единственный источник полноцветных «легаси»-имён
  (`terminal`, `system-file-manager`, `web-browser`, `gnome-log-out`),
  которых нет в Adwaita 48 — она символьная;
* **Adwaita** в цепочке присутствует всегда и даёт символьные иконки, которые
  запрашивают все GTK3-виджеты (кнопки меню, чекбоксы, панель инструментов).

Обе темы масштабируемые (SVG), поэтому в образе обязательно есть
`librsvg2-common`: без SVG-загрузчика `gdk-pixbuf` не декодирует ни одного
SVG, и иконки рисуются пустыми. Это проверяет тест `11c`.

Смена темы — ярлык **Icon Theme** на рабочем столе (или команда
`set-icon-theme <имя>`). `lxappearance` в образе нет: в trixie это GTK3-приложение,
которое тянет за собой весь GTK3 + systemd + polkit стек. Вместо него тема
меняется напрямую: имя записывается в `~/.config/gtk-3.0/settings.ini` и в
`~/.config/lxsession/LXDE/desktop.conf` (чтобы `lxsession` при следующем
старте рабочего стола не вернул старую тему). Новая тема применяется после
перезапуска рабочего стола.

### Разрешение экрана

Ярлык «Set Screen Resolution» (или терминальная команда `set-resolution
1280x800`) пишет запрос в `~/.resolution-request`. Супервизор сессии его
замечает, перезапускает стек Xvfb/LXDE/x11vnc с новой геометрией и удаляет
запрос. Вкладка браузера переподключается сама (x11vnc `-forever`), нужно
подождать ~10 секунд. Разрешение также задаётся при создании сессии:
`create --resolution 1600x900`.

### Буфер обмена

Текст, скопированный на хост-машине, попадает внутрь сессии по **Ctrl+V в
окне noVNC** (работает и Ctrl+Shift+V, и Cmd+V на macOS):

1. браузер отдаёт содержимое своего буфера обмена странице — через своё
   событие `paste` (оно не требует ни защищённого контекста, ни разрешения
   на чтение буфера) или, если оно не сработало, через асинхронный Clipboard
   API;
2. страница передаёт текст в сессию как RFB-сообщение `ClientCutText`;
3. x11vnc кладёт его в X-выделения `CLIPBOARD` и `PRIMARY` сессии;
4. в сессию уходит `Shift+Ctrl+V` — сочетание, которое в LXTerminal означает
   Edit → Paste (в GTK-приложениях вставка — `Ctrl+V`).

То есть привычного `Ctrl+V` в браузере достаточно: текст окажется там, где
стоит курсор в сессии. Внутри самой сессии работает и обычный `Shift+Ctrl+V`
(как в любом Linux-терминале). В строке состояния noVNC появляется
«Clipboard sent to the session (N chars)» — это подтверждение, что текст
дошёл.

Тот же путь работает и через панель «Clipboard» в панели управления noVNC:
вставьте текст в её поле — он уйдёт в сессию и будет вставлен туда же.
Это запасной вариант, если браузер не отдаёт буфер обмена по Ctrl+V.

**Обратное направление** (копирование в Linux → на хост) тоже работает
автоматически: скопировали текст в сессии (`Ctrl+C`) — он попал в буфер
обмена браузера. Механизм: x11vnc отправляет изменение выделения
`CLIPBOARD` как RFB-сообщение `ServerCutText`, страница ловит его и
кладёт в буфер обмена браузера через Clipboard API.

* Если браузер не даёт записать в буфер обмена (страница открыта не по
  `https`/`localhost`, или браузер требует жест пользователя), в правом
  нижнем углу появляется панель с текстом и кнопкой «Copy to clipboard» —
  один клик и текст в буфере хоста.
* Мышь-выделение (выделение `PRIMARY`) наружу **не** отправляется: иначе
  каждое выделение текста мышью затирало бы буфер обмена на хосте.
* Через панель «Clipboard» noVNC текст из сессии тоже попадает в поле
  панели — это запасной вариант, если автозапись не сработала.

Скопированный текст не переживает перезапуск сессии: `CLIPBOARD` живёт в
X-сервере, а он пересоздаётся вместе с контейнером.

### Файлы: как вынести файл из сессии

Кнопка **Files** в верхней панели сессии открывает список файлов
домашнего каталога сессии (`/home/desktop`). Папки открываются, файлы
скачиваются на хост обычной загрузкой браузера. Менеджер читает файл из
контейнера через Docker API (`get_archive`) и отдаёт его с
`Content-Disposition: attachment`.

То же самое доступно через API:

```bash
curl -s http://127.0.0.1:8080/api/sessions/<id>/files?path=/home/desktop | python3 -m json.tool
curl -sOJ http://127.0.0.1:8080/api/sessions/<id>/files/download?path=/home/desktop/notes.txt
```

Область видимости — только домашний том сессии: путь вне `/home/desktop`
отклоняется (HTTP 400), потому что Docker API читает файлы от root
внутри контейнера, и без этой границы скачивался бы и `/etc/shadow`.

### Установка пакетов

Внутри сессии работает `sudo` без пароля, есть интернет и целый `dpkg`:

```bash
sudo apt-get update          # первый раз: список пакетов в образе пустой
sudo apt-get install -y sl   # дальше любой пакет из Debian
```

`curl` и `ca-certificates` тоже есть, поэтому обычный способ установки
работает так же:

```bash
curl -fsSL https://example.com/install.sh | bash
```

Что это значит с точки зрения изоляции:

* пользователь сессии может стать root **внутри контейнера** — сознательный
  размен: рабочий стол, в который нельзя поставить софт, нерабочий;
* границы контейнера при этом прежние: нет `docker.sock`, нет монтирований
  с хоста, нет `privileged`, есть жёсткие лимиты RAM/CPU/pids и отдельный
  том;
* у сессии есть выход в интернет (сеть `webdesktop_sessions` больше не
  `internal: true`), поэтому она дотягивается и до опубликованных на хосте
  портов. На Docker Desktop for Windows до IP самого хоста она не
  дотягивается вовсе, на Linux — дотягивается.


### Что происходит при сбое

Супервизор каждые 2 секунды проверяет Xvfb, x11vnc и `pcmanfm --desktop`;
упавший компонент поднимается автоматически, поэтому пользователь не видит
чёрный экран. `SIGTERM` корректно гасит все процессы (`docker stop`,
`docker compose down` работают чисто).

### Главная сессия — шаблон для новых сессий

Первая созданная сессия автоматически становится **главной**: это образец,
с которого делаются все новые сессии. Кнопка «Make main» есть в каждой строке списка
(и «Unassign» — у главной). Назначить главной можно любую сессию, в том
числе созданную только что.

Из главной наследуется всё, что в ней накоплено:

| Что | Откуда берётся в новой сессии |
|---|---|
| Файлы, документы, обои, настройки панели и темы иконок | домашний каталог главной копируется в новую сессию **как есть** — на момент создания |
| Установленные программы (`sudo apt-get install`) | главная публикуется в образ-шаблон, новая сессия создаётся из него |

Сессии, которые **уже созданы**, не затрагиваются: главная меняется только
для тех копий, которые делаются после этого. Старая сессия остаётся такой,
какой была.

Как это работает:

1. Копия домашнего каталога идёт через Docker API: архив главной
   читается, корневой каталог убирается, архив кладётся в том новой
   сессии **до старта контейнера** (том к тому моменту ещё пустой, и
   Docker дописывает в него содержимое образа, не затирая скопированные
   файлы). Владельцы файлов и права сохраняются.
2. Образ-шаблон (`webdesktop:template-<дата>`) — это `docker commit` главной:
   в образ попадает её изменяемый слой, то есть ровно установленные
   программы. Конфигурация образа берётся из базового, а не из контейнера:
   иначе в шаблон попали бы `VNC_PORT` и `VNC_PASSWORD` конкретной сессии и
   каждая копия спрашивала бы пароль, которого никто не знает.
3. Шаблон публикуется заново, только если изменился изменяемый слой главной
   (то есть в неё поставили или удалили программу). Каждая публикация
   копирует слой целиком, поэтому лишние образы удаляются: неиспользуемый
   образ-шаблон менеджер убирает сам, а занятый сессией — оставляет
   (`docker image prune` добьёт его руками).

Шаблон работает и когда главная остановлена: копия снимается с диска, а не
с работающего контейнера.

Через API:

```bash
curl -X POST http://127.0.0.1:8080/api/sessions/<id>/make-main
curl -X POST http://127.0.0.1:8080/api/sessions/<id>/unmake-main
curl http://127.0.0.1:8080/api/template
```

Новая сессия создаётся как обычно (`POST /api/sessions`) — если главная
назначена (первая сессия назначается автоматически), копия будет сделана с неё.
Создать сессию **без** наследования
можно, передав `{"inherit": false}`.

## 8. Тесты

```bash
python3 tests/test_acceptance.py
```

Проверяются все критерии приёмки: сборка образа, отсутствие Chrome, запуск
контейнера, доступ к noVNC, авторизация, две одновременные сессии, разные
дисплеи, изоляция данных, сохранность данных после рестарта контейнера,
применение лимитов, отказ при нехватке ресурсов без убийства работающих
сессий, отсутствие опубликованных VNC-портов, измеренный размер образа и
потребление памяти, а также **сквозной прогон пути браузера**: WebSocket → RFB
→ пиксели, с проверкой, что на кадре действительно дескстоп (обои, иконки,
панель), а не чёрный экран.

Отдельно проверяется путь буфера обмена: страница отдаёт текст в сессию
(`ClientCutText` по WebSocket — ровно то, что делает браузер по Ctrl+V), и
текст должен появиться в X-выделении `CLIPBOARD` внутри контейнера.

Обратное направление проверяется так же: текст копируется **внутри** сессии,
и клиент должен получить его как `ServerCutText` по WebSocket — это ровно то
сообщение, из которого страница делает буфер обмена хоста.

Отдельно проверяется, что файлы выходят из сессии: файл создаётся в
домашнем каталоге, затем должен появиться в `GET /api/sessions/{id}/files`
и скачаться байт-в-байт через `files/download`. Путь вне домашнего тома
(`/etc`) должен быть отклонён.

Отдельно проверяется, что в сессии **устанавливаются пакеты**: `sudo`
работает без пароля, DNS резолвит зеркала Debian, `apt-get update` проходит
и `apt-get install` ставит пакет.

Отдельно проверяется пункт `7b`: живая сессия переживает полный
`docker compose down` + `up` — и вместе с ней сохраняются файлы
пользователя. Это самый частый способ «сломать» стек, поэтому он и стоит
отдельным тестом.

Отдельно проверяется слой рабочего стола (`11c`): у каждого ярлыка на
`~/Desktop` команда `Exec=` должна существовать в контейнере, имя `Icon=`
должно разрешаться в одну из тем, все кнопки панели должны указывать на
установленные приложения, `gdk-pixbuf` должен уметь декодировать SVG —
иначе иконки рисуются пустыми, — а `apt-get check` должен быть чистым:
иначе образ с вычищенными пакетами нельзя расширить. Именно этот тест ловит
«мёртвый» ярлык Settings и несуществующее имя иконки.

Вспомогательные инструменты:

* `tests/test_novnc_stream.py` — клиент на голом stdlib, повторяющий поведение
  noVNC в браузере (WebSocket + RFB + сохранение PNG);
* `tests/vnc_screenshot.py` — снимок экрана напрямую по RFB;
* `tests/des.py` — DES для VNC-аутентификации, проверен тест-вектором FIPS.

Артефакты (скриншоты) складываются в `tests/artifacts/`.

## 9. Известные ограничения

1. **TLS не настроен по умолчанию** — задача предполагает локальный доступ.
   Для интернета обязательно добавьте реверс-прокси с сертификатом (раздел 6).
   Caddy-конфиг готов, но намеренно не включён: без доменного имени он не
   запустится.
2. **Один пользователь без ролей** — по умолчанию автологин: кто открыл URL,
   тот и оператор (владелец всех сессий). HTTP Basic с одним логином и паролем
   остаётся (`MANAGER_AUTO_LOGIN=0`). Отдельных учёток «на каждого
   пользователя» нет: для этого нужен внешний identity-провайдер (OAuth,
   LDAP) и слой авторизации поверх `auth.Principal`.
3. **Один браузер на сессию** — x11vnc запущен с `-nevershared`: новый
   клиент вытесняет предыдущего. Это сделано намеренно (иначе брошенный
   клиент блокирует x11vnc на минуты), но одновременно два окна рабочего
   стола в разных вкладках работать не будут.
4. **Защита VNC-паролем — дополнительный слой.** В сессии с
   `SESSION_VNC_PASSWORD` x11vnc включает RFB-аутентификацию (максимум 8
   символов, ограничение протокола). Основная защита — менеджер; пароль
   полезен как второй рубеж, но не заменяет HTTPS.
5. **Звука и USB-устройств нет.** Xvfb их не эмулирует, в образе нет
   PulseAudio/ALSA — это сознательная экономия ~30 MB.
6. **OpenGL нет** (Mesa удалена). LXDE, файловый менеджер и терминал работают;
   3D/видео в браузере внутри сессии — нет. Для видео понадобится
   `mpv`/`ffplay` с программным декодированием.
7. **Разрешение меняется перезапуском X-стека** (~10 секунд недоступности).
   Живое изменение через RandR не используется намеренно: Xvfb не поддерживает
   создание режимов надёжно, и «почти работающая» смена разрешения хуже
   явного перезапуска.
8. **Смены GTK-темы оформления нет.** Меняются иконки (ярлык Icon Theme),
   но не тема виджетов: `lxappearance` в trixie — GTK3-приложение, которое
   тянет за собой весь GTK3 + systemd + polkit стек, поэтому его нет в образе.
   Виджеты остаются в стандартной теме GTK3 (Adwaita).
9. **Резервное копирование — tar home-тома.** Согласованных снимков для
   работающей сессии нет; для консистентной копии остановите сессию
   (`stop <id>`), затем `backup`, затем `start`.
10. **Одновременная работа на одном диске.** `docker system df` и очистка
    образов — ваша ответственность; менеджер измеряет свободное место, но не
    удаляет ничего сам.
11. **Проверено на Docker Engine 29.6 / Docker Desktop 4.84, Debian 13
    внутри контейнера.** На cgroup v1 лимит `blkio_weight` передаётся
    (на v2 он отключается автоматически — иначе Docker отказывается создавать
    контейнер). На хостах с SELinux может понадобиться `:z` на монтировании
    тома.
12. **Образ-шаблон — это отдельный образ на диске.** Каждая публикация
    копирует изменяемый слой главной целиком, поэтому образ, из которого
    создана живая сессия, удалить нельзя, пока сессия существует. Неиспользуемые
    образы менеджер убирает сам, остальные — через `docker image prune`.

## 10. Структура проекта

```
Dockerfile                       образ сессии (LXDE + Xvfb + x11vnc)
compose.yaml                     manager + docker-proxy + сборка образа
.dockerignore                    контекст сборки образа сессии
.env.example                     настройки по умолчанию (копируется в .env)
assets/wallpaper.png             обои рабочего стола
config/
  manager.yaml                   лимиты, пороги admission control, таймауты
  lxsession/desktop.conf         определение LXDE-сессии (WM, темы)
  entrypoint/
    entrypoint.sh                супервизор: Xvfb -> LXDE -> x11vnc
    bootstrap.sh                 первичная настройка домашнего каталога
    healthcheck.sh               проверка готовности (пассивная по порту)
    desktop-items/*.desktop      ярлыки рабочего стола
    lxde-profile/                профиль LXDE по умолчанию (копируется в $HOME)
      .config/lxsession/LXDE/autostart
      .config/lxpanel/LXDE/panels/panel
      .config/pcmanfm/LXDE/desktop-items-0.conf
      bin/{set-resolution,set-icon-theme,lxde-restart}
manager/
  Dockerfile                     образ менеджера (+ noVNC)
  Dockerfile.dockerignore        контекст сборки менеджера
  requirements.txt
  app/
    main.py                      FastAPI: API, /s/, /ws/, healthcheck
    auth.py                      автологин, HTTP Basic, владение сессиями, WS-апгрейд
    service.py                   жизненный цикл сессии
    docker_ctl.py                узкий слой над Docker API
    scheduler.py                 admission control и очередь
    resources.py                 RAM/CPU/диск хоста
    store.py                     метаданные сессий (вне контейнеров)
    vncproxy.py                  WebSocket <-> RFB
    config.py                    конфигурация (файл + переменные окружения)
scripts/
  desktop-session.sh             CLI: create/list/stop/restart/delete/backup
  down.sh                        гарантированная остановка стека (bash)
  down.ps1                       то же самое для PowerShell
  resources.sh                   что сейчас ест ресурсы
  image-size.sh                  честные размеры образа
tests/
  test_acceptance.py             критерии приёмки (основной набор)
  test_novnc_stream.py           сквозной тест пути браузера + скриншот
  vnc_screenshot.py              снимок экрана по RFB
  des.py                         DES для VNC-аутентификации
  artifacts/                     скриншоты тестов
```
