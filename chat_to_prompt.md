Автопроверок в проекте нет (`DOCS/decisions/025`), а живой стек агенту недоступен. Поэтому у каждой задачи **две разные строки приёмки**:

- **проверяю сам** — то, что закрывается без сервера: `npm run check`, `node --check`, прогон чистой функции разбора на сохранённом ответе;
- **проверка живьём** — пошаговый сценарий: что открыть, что нажать, что должно появиться. Проходит его агент сам на сервере пользователя через `SYSTEM/live-check.mjs` (правило в `AGENTS.override.md`, «Конвенции»); пользователю сценарий отдаётся, только если агенту он недоступен. Чтобы первая строка вообще существовала, нужны **фикстуры**: сохранённый поток одного хода Claude и одного хода Hermes плюс маленький скрипт, прогоняющий их через разбор без сервера. ## 1. К чему идём

Диалог начался с вопроса «как логировать всё, что Claude обдумывает в `claude -p`» и вырос в архитектуру из трёх плоскостей.

```
CONTROL PLANE          Hermes: граф задач, состояние, retry, fallback, планирование
        │
EXECUTION PLANE        Claude Code CLI (supervisor) · OmniRoute (маршруты) · workers · tools
        │
OBSERVABILITY PLANE    адаптеры → raw + normalized → Event Store → лента, поиск, replay
```

Роли жёстко разделены и не смешиваются:

- **Hermes — главный оркестратор.** Получает задачу, разбивает на подзадачи, выбирает для каждой исполнителя, хранит историю попыток, делает fallback. Не «тупой диспетчер»: сложные решения отдаёт Claude, но состояние держит у себя.
- **Claude Code CLI — дорогой supervisor.** Планирует в начале, проверяет на контрольных точках, выносит вердикт «принято / на переделку». Участвует не в каждом шаге — в этом вся экономия.
- **OmniRoute — routing plane.** Доставляет worker-запрос выбранной модели у выбранного провайдера, следит за лимитами и ошибками. Решений уровня «задача сделана неправильно» не принимает.
- **Workers** — дешёвые и бесплатные модели, на них основная масса работы.
- **Observability** — адаптер на каждый источник, который вытаскивает максимум того, что источник реально отдаёт, и переводит в единый формат событий.

Два правила, которые пользователь проговорил отдельно и которые нельзя нарушать:

1. **Никакого Anthropic API и никаких ключей Anthropic.** Claude — только локальный процесс Claude Code CLI по подписке. Маршрутизатор не имеет права подменять самого Claude на дешёвую модель: он обслуживает workers. Запрет касается именно подмены Claude и ключей Anthropic — **ключи worker-провайдеров допустимы**, но живут в `.env`, как все секреты проекта. Сегодня это нарушено: ключ OpenRouter пишется открытым текстом в `~/.pi/agent/auth.json` (`server.js:1873-1882`) мимо `.env` — отдельная задача `OpenKarandash-f59.20`.
2. **Основной интерфейс — лента, а не дерево.** Пользователь поправил это дважды. События идут вертикально сверху вниз; блок раскрывается прямо в ленте; связи (`session_id`, `task_id`, `attempt_id`, `parent_id`) живут **внутри данных** и служат фильтрам, а не превращают экран в дерево. При этом всё, что принадлежит параллельному исполнителю, складывается **внутрь его блока-контейнера**, чтобы одновременные задачи не перемешивались.

Формулировка, на которой сошлись в конце: не «мы всегда получаем максимум», а **«архитектура всегда пытается получить максимум доступного для конкретного источника»**. Скрытый chain of thought закрытой модели не обещаем — обещаем не потерять ничего из того, что источник отдал.

### Этап 1 — поля Event Schema в базе · `OpenKarandash-f59.2`

**Зачем.** Единый формат событий — фундамент всей архитектуры диалога. Без `task_id` и `attempt_id` нельзя показать историю попыток («задача C выполнялась дважды, вот оба результата»), без `source`/`actor`/`event_type` — фильтровать ленту, без `provider` — вообще увидеть, кто отвечал.

**Что есть сейчас.** В `messages` уже лежат `parent_tool_use_id`, `tool_use_id`, `model`, `effort`, токены, стоимость, `stop_reason`, `mode`, `extra_meta`, `result_meta` (`server.js:2641-2687`). Нет: `source`, `actor`, `event_type`, `task_id`, `attempt_id`, `provider`, `raw`. Провайдер выводится косвенно через `sessions.target`.

**Отдельный идентификатор графа задач.** Диалог специально отметил: одного `session_id` мало, потому что одна пользовательская сессия рождает десятки задач, сотни попыток и тысячи событий. Нужен свой идентификатор графа задач рядом с идентификатором сессии, иначе фильтры и сводки упрутся в это позже.

**Сначала спецификация, иначе два исполнителя напишут два несовместимых набора.** Первый артефакт этапа — не код и не эссе, а таблица. Черновик, который надо утвердить и дополнить:

| поле | тип | обязательно | кто заполняет | значения |
|---|---|---|---|---|
| `source` | TEXT | да | тот, кто пишет строку | `claude`, `hermes`, `bridge`, `router`, `worker`, `server`, `user` — список открытый, новое значение пишется как есть |
| `actor` | TEXT | нет | там же | кто действовал внутри источника: `orchestrator`, `supervisor`, `model`, `tool`, `subagent` |
| `event_type` | TEXT | да | там же | `text`, `thinking`, `tool.call`, `tool.result`, `notice`, `routing.fallback`, `provider.error`, `decision`, `verdict` — **неизвестный вид пишется как есть, а не отбрасывается** (`DOCS/decisions/012`) |
| `task_id` | TEXT | нет | оркестратор при заведении подзадачи | id подзадачи; у строк вне графа — пусто |
| `attempt_id` | TEXT | нет | оркестратор при каждой попытке | номер попытки внутри `task_id` |
| `provider` | TEXT | нет | тот, кто выбрал маршрут | имя провайдера, у прямого CLI — цель (`wsl`/`windows`) |
| `raw` | TEXT | нет | автор строки | исходное событие целиком (этап 2) |

Три вопроса, на которые таблица обязана ответить до кода: **что делать со старыми строками** (пусто или дозаполнять), **кто и когда рождает `task_id`/`attempt_id`**, и **не дублирует ли это уже имеющееся** — сегодня роль «источника» частично несут `tool_name` и `extra_meta` (JSON), и решить «колонка или ключ в JSON» надо один раз, а не по ходу.

Отдавать в `listMessages` (`server.js:2882-2892`). Показать в Feed — там поля рисуются от данных, а не от зашитого списка (`fillKv`, `PROJECTS/Feed/page.js:362-379`), так что новые ключи появятся почти сами; в Flow дописать в секцию `Metadata` (`sessionMetadata`, `flow.js:2731-2743`).

### Этап 2 — сырое событие рядом с каждым, а не только с непонятым · `OpenKarandash-f59.3`

**Зачем.** Диалог: «сохраняем и нормализованное событие, и оригинальное raw — тогда новый тип reasoning-события у новой модели не потребует переделывать систему». У нас принцип соблюдён наполовину: `JSON.stringify(event)` записывается **только** для ролей `system`, `unknown`, `top_level` (`server.js:3078-3103`). У распознанных событий — `assistant`, `tool`, `thinking`, `result` — исходника нет вовсе, остаются лишь те поля, под которые заведены колонки.

**Что делать.** Писать исходное событие в колонку `raw` для всех ролей. Пересмотреть обрезку `DETAIL_CLIP_LEN = 50000` (`server.js:2916-2921`): либо своя граница для `raw`, либо вынос длинных тел в файлы рядом с базой.

**Отдельно: журнал должен быть неизменяемым.** Диалог требует, чтобы сырой слой только дописывался, а нормализованное представление строилось поверх него — тогда ничего не теряется даже при ошибке интерфейса или разбора. У нас это нарушено в одном месте: после хода Hermes записанные по потоку строки **заменяются** разбором его истории (`hermesHistory.rebuild`, `SYSTEM/core/hermes-history.js:295-319`, `DOCS/decisions/039`). Замена сделана осознанно и даёт правильный порядок, но вместе с ней исчезает то, что мы видели своими глазами во время хода. Правильный вид: сырые события потока сохраняются навсегда, а пересборка меняет только нормализованный слой. Если так дорого — хотя бы сохранять замещаемые строки, а не затирать.

**Проверяю сам.** На фикстуре хода у строк всех ролей заполнено `raw`; посчитан средний размер сырого события и прикинут суточный прирост базы из частоты событий одного прогона (ждать сутки не нужно — это не единица работы); `npm run check` проходит.

**Проверяет пользователь.** В Feed, в Sessions и на ноде Flow у строки любой роли — не только у «неизвестного события» — раскрывается сырое событие; после хода Hermes видно и то, что пришло потоком, и то, что дал разбор истории.

### Этап 4 — замерить, пуст ли `thinking` в `-p`, и решить про PTY · `OpenKarandash-f59.5`

**Зачем.** Это центральная находка диалога. По issue самого Claude Code, в headless-пути запись выглядит как `{"type":"thinking","thinking":"","signature":"…"}` — текст пустой; а интерактивная TUI-сессия сохраняет полные размышления в тот же JSONL. Отсюда и вырос `claude-pty-wrapper`: он запускает **интерактивный** Claude внутри PTY, а наружу даёт headless-интерфейс, и дополнительно отдаёт сырой лог PTY и сырые записи session JSONL.

**Сначала замер, а не реализация.** Утверждение взято из чужого issue и может быть неверным для нашей версии CLI. Более того, наш мост уже собирает `reasoning` из `thinking_delta` (`claude-bridge/cli_process.py:174-194`), и `DOCS/decisions/029` прямо говорит, что до этой правки поле размышлений у Hermes пустовало, а после — заполнилось. Значит, какое-то содержимое в `-p` приходит. Нужен честный прогон: один и тот же запрос через `-p` и интерактивно, сравнить, что оказалось в размышлениях.

**Если подтвердится, что в `-p` пусто.** Тогда PTY-путь: в проекте сейчас нет ни `node-pty`, ни `script`/`unbuffer` — все запуски это обычный `spawn` с пайпами. И нет чтения `~/.claude/projects/**/*.jsonl`, причём это **записанное решение** (`README.md:180`, `PROJECTS/Chat/README.md:73`). Отменять его надо запиской, а не тихой правкой. Учесть и цену: PTY ломает текущую схему остановки хода (`killProcessTree`, PID-маркер для WSL) и, возможно, продолжение сессий моста (`claude-bridge/session_cache.py`), на котором держатся 96–99 % попаданий в кеш (`DOCS/decisions/041`).

**С чего начинать — не с чужих жалоб, а с документации.** Разговор нашёл официальные страницы, и они первичнее issue: у размышлений есть настройка отображения (`display: "summarized"` — поток возвращает сжатое изложение, а не полную цепочку), есть справочник флагов CLI и описание headless-режима.

- Отображение и потоковая передача размышлений: <https://platform.claude.com/docs/en/build-with-claude/streaming>, <https://platform.claude.com/docs/en/docs/build-with-claude/extended-thinking>
- Справочник флагов CLI: <https://code.claude.com/docs/en/cli-usage> (адрес на `docs.anthropic.com` отдаёт 301 сюда)
- Headless-режим: <https://code.claude.com/docs/en/headless>

**Жалобы, на которых держится утверждение из разговора** (проверить, актуальны ли для нашей версии — часть может быть уже закрыта):
<https://github.com/anthropics/claude-code/issues/85443>, <https://github.com/anthropics/claude-code/issues/87393>, <https://github.com/anthropics/claude-code/issues/87947>, <https://github.com/anthropics/claude-code/issues/79021>, <https://github.com/anthropics/claude-code/issues/7840>

**Сравнивать надо три пути, а не выбирать между двумя.** Разговор перечислил их явно:

1. перехватывать поток во время работы — **это то, что мы делаем сейчас**, и именно этот путь надо взять точкой отсчёта в замере;
2. читать запись сессии после её окончания;
3. поднять обёртку, которая внутри запускает обычный интерактивный режим, а наружу даёт headless-интерфейс.

У третьего пути источников сразу три, и они друг друга страхуют: собственный поток обёртки, запись сессии и сырой журнал псевдотерминала (`--raw-pty-log`).

**Две оговорки, которые разговор сделал честно, и их надо унести с собой.** Первая: известен баг, при котором текстовый блок, оказавшийся между двумя блоками размышлений, вообще не попадает в запись сессии. Значит даже путь через транскрипты не даёт полноты, и запасной источник нужен в любом случае. Вторая: полный вывод размышлений в редких случаях выдаётся по отдельному обращению в отдел продаж — обычным флагом его не включить. Практического хода тут нет, дверь записана закрытой, чтобы к ней не возвращались.

**Инструменты, которые разговор предложил и просил проверить построчно, а не по описанию:**

Состояние проверено живьём 2026-09-18 (`OpenKarandash-f59.16`):

### Этап 5 — OmniRoute как routing plane · `OpenKarandash-f59.6`

**Зачем.** Это половина экономики всей схемы: массовую работу делают бесплатные и дешёвые модели, Claude вызывается точечно. Пользователь отдельно уточнил, что провайдер выбирается **на каждую подзадачу свой**, а не один на всю сессию, и что исчерпанный лимит не должен ломать задачу — подзадача уходит другому провайдеру и продолжает с того же места.

**Чего нет.** Всего. Кода OmniRoute в проекте нет; список провайдеров в интерфейсе — четыре локальных CLI с зашитыми моделями (`SYSTEM/providers.js:15-56`); у Hermes единственный провайдер `claude-bridge` и `fallback_providers: []` (`hermes-home.config.example.yaml:12`); `rate_limit_event` читается только для прямого Claude (`server.js:1133, 1365-1370`), **в ветке Hermes лимит не читается вовсе**, переключения при 429 нет нигде.

**Что такое OmniRoute — выяснено (`OpenKarandash-f59.16`, 2026-09-18).** Три адреса из разговора (<https://github.com/manuelapetsi/omniroute>, <https://github.com/rgplvr/omniroute>, <https://github.com/denzainch/omniroute>) — не три разных проекта, а **три устаревших форка одного апстрима**, и брать не годится ни один: у всех ноль-одна звезда, нет релизов, последние пуши июнь–июль.

Настоящий адрес — **<https://github.com/diegosouzapw/OmniRoute>** (MIT, активен, пуш 2026-09-17). Заявленное в разговоре подтверждается его README: режимы ровно те (`auto`, `auto/cheap`, `auto/coding`, плюс `auto/fast`, `auto/smart`, `auto/offline`), Claude Code — первоклассный клиент (`omniroute run claude`, эндпоинт `http://localhost:20128/v1`), и **Hermes Agent от Nous Research прямо указан в списке поддерживаемых клиентов**. Отдельно ценно для нашего правила про ключи: после установки модель `auto` отвечает без ключей и без регистрации — предзаведены бесплатные провайдеры.

Проверить при внедрении, а не поверить на слово: их же README предупреждает, что кодинг-агенты (`POST /v1/responses` от Claude Code) валят процесс по памяти на двух длинных контекстах, и дефолтный `OMNIROUTE_MEMORY_MB=1024` в докер-образе мал. Запасной вариант, если не сложится, — LiteLLM.

**Официальный путь сверен (`OpenKarandash-f59.16`).** Штатная настройка работы через шлюз — <https://code.claude.com/docs/en/llm-gateway> (старый адрес на `docs.anthropic.com` отдаёт 301 сюда). Ответ для нашего правила про ключи **хороший**: ключ Anthropic не обязателен. Если задать только `ANTHROPIC_BASE_URL` и не задавать учётку шлюза, запросы идут через шлюз, а действующей учётной записью остаётся сохранённый вход claude.ai — то есть подписка. Если ключ всё-таки задан, это ключ **шлюза**, а не Anthropic (`ANTHROPIC_AUTH_TOKEN`, при неясности документация советует именно его).

Две оговорки оттуда же, и обе бьют по замыслу — записать и не забыть:

1. Anthropic прямым текстом не поддерживает маршрутизацию Claude Code на **не-Claude** модели через любой шлюз. Технически это работает, но вне поддержки — а у нас именно это и задумано для workers.
2. Учётка шлюза перебивает сохранённый вход claude.ai, а Remote Control и голосовой ввод отключаются, когда `ANTHROPIC_BASE_URL` указывает на не-Anthropic хост, даже при живом входе claude.ai.

**Что делать.** Выбор связки «модель + провайдер» на подзадачу; `attempt_id` и история попыток (задел — этап 1); обработка 429 и переключение на другого провайдера внутри той же подзадачи; события маршрутизации в ленту отдельным источником (`routing.fallback`, `provider.error` — формат из диалога). Включить переключатель CLI/Omniroute (`PROJECTS/Settings/settings.js:101, 204-205`), он уже нарисован как «Coming Soon».

**Готово, когда.** Подзадача, упёршаяся в лимит, доделывается другим провайдером без падения сессии, и в ленте видно оба захода с причиной переключения.

### Этап 6 — лента: контейнеры, полнота блока, поиск, replay · `OpenKarandash-f59.7`

**Зачем.** Последняя реплика диалога — прямое требование: общая лента одна, но каждый параллельный исполнитель получает свой блок-контейнер, и всё принадлежащее ему (промпт, размышления, вызовы, результаты, ошибки, повторы) складывается внутрь.

**Что сейчас.** Chat и Feed плоские: субагент отмечается лишь символом `↳` (`PROJECTS/Chat/chat-stream.js:172-187`) или подписью «Subagent» (`PROJECTS/Feed/page.js:541`). Настоящая вложенность есть только в графе Flow (`flow.js:2986-2991`) — но пользователь просил ленту, а не граф.

**Четыре части.**

1. **Контейнеры параллельных исполнителей** в Chat и Feed: блок задачи, внутрь которого падают её события; порядок самой ленты при этом остаётся хронологическим.
2. **Полнота блока в Chat** (заведено отдельно: `OpenKarandash-f59.28`, вместе с недостающим во Flow). Сейчас во время хода у шага нет тела: `detail` появляется только при перечитывании из базы (`PROJECTS/Chat/chat-stream.js:182-209`), поэтому живой шаг даже не кликается. Плюс на сообщении не видно ни модели, ни провайдера, ни токенов. Feed это всё уже умеет (`PROJECTS/Feed/page.js:454-564`) — перенести формат, а не писать заново.
3. **Поиск и фильтр** по ленте: по источнику, типу события, инструменту, провайдеру, `task_id`. Сейчас нет ни поля поиска, ни фильтра по роли.
4. **Replay** — воспроизвести сохранённую сессию по времени. Данных для этого хватает уже сейчас, интерфейса нет.
5. **Сводка сессии над лентой** — то, что в диалоге нарисовано шапкой: статус, сколько задач активно, сколько завершено, сколько было переключений провайдера и ошибок, сколько провайдеров участвовало. Частично это уже есть карточкой «Whole session» в Feed (`PROJECTS/Feed/page.js:393-446`), но она внизу списка полей, а не сводка сверху.
6. **Залатать дыру живой подписки.** `/api/sessions/attach` (`server.js:3349-3364`) не хранит буфера: подключившийся получает только то, что случится дальше. События, пришедшие между разрывом связи и переподключением, в живой ленте Chat уже не появятся — они догоняются лишь финальным перечитыванием из базы. Feed и Flow этой дырой не страдают, потому что всегда читают базу. Нужен либо буфер последних событий хода, либо курсор, с которого клиент просит продолжение.

**Готово, когда.** Три параллельные подзадачи не перемешиваются в ленте; живой шаг раскрывается без перезагрузки; поиск по имени инструмента находит все его вызовы; обрыв связи посреди хода не оставляет дыру в ленте; `npm run check` проходит и `ui-checker` прошёл живой интерфейс на сервере пользователя.

### Этап 7 — логин и маскирование секретов · `OpenKarandash-f59.8`

**Зачем.** Пользователь сказал: «доступ будет только при логине». Вторая половина — redaction: диалог отдельно отметил, что raw-логи могут нести ключи и токены, и что защита нужна даже при закрытом доступе, потому что утечка идёт не только через человека, но и через бэкапы, браузер, сторонний сервис.

**Что сейчас.** Логина нет вообще: единственная защита — `isLocalRequest` по 127.0.0.1 (`server.js:3454-3467`). Любой процесс на машине имеет полный доступ ко всем API, включая запуск CLI и правку сообщений. Маскирования нет: `toolInput` / `toolResult` / `resultMeta` пишутся в базу и показываются как есть (обрезается только длина), то есть вывод команды с секретом ляжет в `.sessions.db` и в карточку Feed целиком. Ключ OpenRouter хранится открытым текстом в `~/.pi/agent/auth.json` (`server.js:1873-1882`).

**Что делать.** Аутентификация вместо проверки адреса. Отдельный слой маскирования: перед записью и, обязательно, перед показом. Сырое держать в защищённом виде, в интерфейс отдавать безопасную версию.

**И режимы видимости — это не то же самое, что маскирование.** Диалог просил различать полный технический режим для своей машины и безопасный режим веб-интерфейса. Маскирование решает «что нельзя показывать никогда», режимы — «что показывать этому зрителю сейчас». Пригодится, как только к пульту подойдёт не один человек, а команда.

**Готово, когда.** Страница не открывается без входа; подставной секрет в выводе инструмента не виден в ленте; переключение режима меняет полноту ленты, не трогая хранимые данные.

### Этап 8 — адаптер как отдельная сущность, а не код внутри коннектора · `OpenKarandash-f59.9`

**Зачем.** Вся архитектура диалога держится на слое адаптеров: у каждого источника свой, он знает, где искать данные, переводит их в общий формат, и добавление нового провайдера не трогает интерфейс. У нас такого слоя нет: разбор событий вшит внутрь самих коннекторов — `onLine` живёт внутри `askClaude` (`server.js:1192-1371`), `onEvent` внутри `askHermes` (`server.js:2378-2456`), у `pi` и `opencode` свои куски там же. Поэтому каждое улучшение приходится делать по четыре раза, а обычно делают один раз — отсюда и расхождение из этапа 3.

**Что делать.** Вынести разбор в отдельные модули-адаптеры с одним контрактом «сырое событие источника → запись Event Schema», по одному на источник. Это прямо совпадает с уже заведённой задачей `OpenKarandash-b9y.7` («свести дубли четырёх коннекторов CLI») и с `DOCS/decisions/022` — адаптеры просятся в пустующую `SYSTEM/cli/`. Попутно закрыть дыру: `codex` вообще не умеет вести разговор (`askCodex` отдаёт «не реализовано», `server.js:1709-1712`), то есть один из четырёх источников в системе наблюдения не участвует.

**Ещё две вещи сюда же.**

- **Capability discovery.** Адаптер должен объявлять, что его источник реально отдаёт: размышления, вызовы инструментов, расход токенов или только текст. Тогда интерфейс показывает максимум доступного сам, без правок под каждый новый источник.
- **События-решения.** Диалог просил хранить не только действие, но и его причину: почему выбрана эта модель, этот провайдер, почему результат отправлен на переделку. Без этого лента отвечает на «что произошло», но не на «почему».

**Готово, когда.** Новый источник подключается одним адаптером без правок страниц; в ленте у события видно, какими возможностями обладал его источник; решение о выборе модели видно отдельной записью.

### Этап 9 — граф задач и состояние оркестрации · `OpenKarandash-f59.10`

**Зачем.** Оркестратор из диалога — это не «разослал и забыл»: он держит состояние каждой подзадачи и историю попыток, чтобы при отказе знать не «провайдер A умер», а «подзадача C выполнялась дважды, вот оба результата, пробуем третий маршрут». Без этого ни переделка, ни переключение провайдера не имеют памяти.

**Что есть.** Только идентификаторы вызовов и связь «родитель-потомок» у помощников (`parent_tool_use_id`). Собственного графа подзадач с их статусами нет: таблицы `hermes_runs`/`hermes_tasks` были остатком удалённого оркестратора и намеренно удаляются при старте (`DOCS/decisions/038`) — их схема под это и не годилась.

**Что делать — отражать, а не заводить.** Решением владельца граф задач живёт в Hermes; своей копии мы не держим (иначе повторим ошибку, уже разобранную в `DOCS/decisions/038`, где вторая копия журнала расходилась с первой). Наша работа: вытащить из Hermes состояние подзадач — статус, попытки, исполнителя, итог — и показать его в ленте, связав с событиями через `task_id`/`attempt_id` из этапа 1. Если Hermes чего-то из этого не отдаёт, сначала выяснить, отдаёт ли (у него есть API сессий и своя база `state.db`, читалка которой уже написана — `SYSTEM/core/hermes-tool-runs.js`), и только потом решать, что делать с недостающим.

**Снимок состояния — тоже его, а не наш.** Диалог просил периодический срез «какие задачи активны, чьи лимиты исчерпаны». Заводить свой снимок — это ровно «своя память» из запрета. Сначала проверить, что уже хранит Hermes, и брать оттуда.

**Сюда же — визуальная постановка задач.** Комментарий к элементу интерфейса должен становиться подзадачей графа, иначе граф пригоден только для переписки, а не для того, ради чего проект затевался.

**Проверяю сам.** Разбор состояния Hermes работает на сохранённом ответе его API без живого стека; `npm run check` проходит.

**Проверяет пользователь.** По завершённой сессии в ленте видно дерево подзадач с попытками и итогами, и оно совпадает с тем, что показывает сам Hermes.

### Этап 10 — контур проверки и переделки · `OpenKarandash-f59.11`

**Зачем.** Это сердце всего разговора, и до сих пор в плане его не было. Пользователь сформулировал прямо: Claude используется точечно — в начале для разбора задачи и на контрольных точках для проверки, — а массовую работу делают дешёвые исполнители. Вся экономия существует только если есть вердикт и возврат на доработку. Без этого контура OmniRoute просто удешевляет запросы, но никто не отвечает за качество результата.

**Что есть.** Кирпич уже проверен вживую: синхронная передача задачи профилю-специалисту с явной инструкцией вместо пересылки всей переписки — `hermes-home/bin/handoff`, `DOCS/decisions/031`. Есть и профили (`developer`, `qa-checker`, `reviewer`, `docs-writer`). Чего нет — самого цикла: вердикта, счётчика попыток, правила остановки.

**Где исполнители работают — решено: каждый в своей ветке.** Это важнее, чем кажется, и определяет весь контур. Исполнитель получает собственную ветку и портит только её; рабочая папка остаётся за человеком, и никто в неё одновременно не пишет. Вердикт «принято» — это не пометка в ленте, а **слияние ветки в основную, и делает его проверяющий**. Отклонённая работа просто остаётся в своей ветке и никому не мешает.

Отсюда следствия, которые надо заложить сразу:

- ветка заводится на подзадачу, а не на сессию, и её имя должно быть видно в ленте рядом с задачей (поле из этапа 1);
- «принято» и «влито» — разные события: вердикт может быть положительным, а слияние упасть на расхождении, и это не должно выглядеть как успех;
- два исполнителя, правившие одно и то же по-разному, — штатный случай, а не сбой; решает проверяющий, и его выбор тоже событие;
- это ровно то, что проект уже требует: при старте он выводит предупреждение, что агентам следует работать в отдельных копиях (`.worktrees/`), — значит механизм есть, его надо не изобретать, а подключить к контуру.

**Важно: изолируются файлы, но не наблюдение.** Здесь ветки сталкиваются с двумя жёсткими правилами проекта, и это надо решить до кода, иначе схема не соберётся:

- база сессий лежит в папке запуска (`server.js:2572`), а сервер занимает один порт и при занятом выходит с ошибкой (`DOCS/decisions/001`). Значит исполнитель в своей копии **не может поднять свой сервер**, а если бы поднял — писал бы в свою базу, и единая лента распалась бы на двадцать;
- поэтому правило такое: **события всегда пишет главный сервер в главную базу**, а в ветку уходит только рабочая папка запускаемого помощника (его `cwd`). Лента остаётся одна, изоляция касается только файлов.

**Следствие, у которого пока нет ответа: ветку нельзя посмотреть живьём.** Интерфейс поднят с главной папки, и визуальная постановка задачи (комментарий к элементу в Karandash, канвас) работает там же. Правка уедет в ветку, которую человек не увидит, пока она не влита. Для изменений интерфейса это разрывает сам смысл визуальной постановки: задачу поставили, глядя на экран, а результат смотреть не на чем, и проверяющий судит по тексту правок вместо работающего экрана. Нужен способ показать ветку живьём — отдельный порт для проверки, временная подмена статики или что-то ещё. Заведено отдельно: `OpenKarandash-f59.17`, решать вместе с этапом 9.

**Второе следствие: разбор больших файлов становится предусловием, а не уборкой.** Двадцать веток от одной точки будут править один и тот же `server.js` на три с половиной тысячи строк — и конфликты слияния станут основным режимом, а не редкостью. В проекте это уже заведено отдельной темой (`OpenKarandash-b9y`, `DOCS/decisions/022`), но теперь у неё другой смысл и другая срочность: без неё параллельная работа будет захлёбываться в разборе конфликтов.

**Третье следствие: проверка должна быть воронкой.** Если каждую из двадцати веток смотрит дорогой проверяющий, потратим больше, чем сэкономили. Порядок: сначала машинная проверка прямо на ветке (`npm run check`, а для интерфейса — прогон `ui-checker`), затем дешёвый рецензент, и только прошедшее — дорогому. Дорогой смотрит не работу, а то, что уже прошло два сита.

**Четвёртое: непринятые ветки надо убирать.** Иначе через месяц в репозитории сотни мёртвых веток от отклонённых попыток. Политика уборки — часть контура, а не отдельная забота человека.

**Что делать — сам круг настраивается в Hermes, у нас его видно.** По решению владельца логика «кому отдать, когда позвать проверяющего, сколько раз переделывать» живёт в Hermes: там для этого есть профили-специалисты и проверенная вживую синхронная передача (`DOCS/decisions/031`). Наша часть — сделать круг видимым и не дать ему потеряться:

- **Вердикт как событие.** «Принято» или «на переделку» с причиной — отдельной записью в ленте (`event_type: verdict` из этапа 1), а не текстом внутри ответа.
- **Слияние как часть вердикта.** Принято → проверяющий вливает ветку; отклонено → ветка остаётся непринятой. В ленте видно и то, и другое, и они различаются.
- **Возврат на доработку** виден вместе с номером попытки (из этапа 9).
- **Политика вызова Claude и предел переделок** — настройка Hermes, а не наш код. Записать, где именно она задаётся, чтобы её можно было менять не трогая пульт. Диалог предостерёг от жёсткого «ровно два раза за сессию».

**Проверяю сам.** На фикстуре хода с отказом разбор кладёт вердикт отдельной строкой с причиной; `npm run check` проходит.

**Проверяет пользователь.** Задача с заведомо плохим первым результатом проходит круг «сделано → отклонено с причиной → переделано другим исполнителем → принято», и весь круг виден в ленте.

**Готово, когда.** Задача с заведомо плохим первым результатом проходит круг «сделано → отклонено с причиной → переделано другим исполнителем → принято», и весь круг виден в ленте, включая причину отказа.

### Этап 11 — сквозная нить через границы процессов и мост как источник · `OpenKarandash-f59.12`

**Зачем.** Диалог рисовал цепочку целиком: задача Hermes → делегирование Claude → запрос маршрутизатора → провайдер → модель → результат → решение проверяющего. Чтобы такую цепочку показать, идентификатор должен пережить границу процесса. У нас он умирает на первой же: наш сервер знает свою сессию, Hermes — свою, `claude-bridge` не знает ни той, ни другой.

**Чем это оборачивается сегодня.** Мост — полноправный участник: он переспрашивает модель при неразобранном вызове, поднимает заниженные таймауты терминала, чинит обрезанный запрос, отклоняет несуществующий инструмент. Всё это он доставляет в ленту **строками внутри поля размышлений** (`claude-bridge/run_notes.py`, разбор — `SYSTEM/core/hermes-history.js`), потому что другого канала до нас у него нет. В `DOCS/decisions/039` это записано прямо, вместе с честной пометкой, что на живом стеке не проверено, доходят ли эти строки вообще.

**Что делать.** Прокинуть общий идентификатор хода вниз по цепочке (заголовком в мост и дальше) и завести мосту собственный адаптер (этап 8), чтобы его события приходили как события, а не как текст в чужом поле. Тогда у каждой записи ленты появляется ответ на «чей это шаг и из какого запроса он вырос».

**Готово, когда.** По любому событию ленты восстанавливается вся цепочка до провайдера; пометки моста приходят своим каналом, и это подтверждено живым прогоном, а не предположением.

### Этап 12 — измерить, окупилась ли затея · `OpenKarandash-f59.13`

**Зачем.** Вся схема оправдана ровно одним: дорогой участник работает точечно, массовую работу делают дешёвые. Проверить это нечем — сводки по стоимости сессии нет. А цена вопроса высокая: проект уже дважды менял решение об оркестраторе (`015` убрал, `029` вернул), и третий разворот вслепую обойдётся дороже любого из первых двух.

**Что делать.** Считать и показывать по сессии: сколько стоила целиком, какая доля пришлась на дорогого проверяющего, сколько ходов ушло на переделки, сколько было переключений провайдера. Данные частично уже собираются — расход токенов и стоимость пишутся по ходам (`server.js:2641-2687`), кеш-метрики приходят от моста.

**Заодно — честная арифметика переделки.** Круг «сделали дёшево → отклонили → переделали → снова проверили» не всегда дешевле, чем сразу поручить дорогой модели. Нужно уметь это сравнивать, а не только ограничивать число кругов.

**Готово, когда.** По завершённой сессии видно, сколько она стоила и на что; на двух-трёх реальных задачах измерено, дешевле ли вышло, чем прежним способом.

### Этап 13 — перестать держать две расходящиеся настройки · `OpenKarandash-f59.15`

**Зачем.** Идея из разговора, которую легко пропустить: у Hermes есть готовая команда `hermes import-agent claude-code` — она забирает из `~/.claude` инструкции, разрешения, MCP-серверы и навыки Claude Code. То есть верхний слой можно поднять, не выбрасывая уже настроенное.

У нас эти две половины живут врозь и расходятся: настройки Claude Code лежат в своих местах (причём у Windows-копии и WSL-копии они **разные** — свой набор хуков, навыков, помощников), а Hermes настраивается отдельным файлом и своим образцом конфигурации. Каждое расхождение всплывает как «на одной машине работает, на другой нет».

**Что делать.** Проверить импорт на нашем стеке (<https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/agent_import.py>, описание — <https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/import-from-other-agents.md>) и решить, что делаем источником правды. Осторожно: импортировать надо ровно то, что должно совпадать, а не всё подряд — разрешения у контейнерного Hermes намеренно другие.

**Готово, когда.** Ответ записан: что импортируем, что держим раздельно и почему; расхождение между двумя копиями Claude больше не сюрприз.

## 5. Пробелы и риски, которые диалог не разбирал

Ниже то, о чём в разговоре речи не было, но без чего схема не доживёт до рабочего состояния. Это не отдельные этапы — это оговорки, которые надо держать в голове на каждом из них. Общая задача под них — `OpenKarandash-f59.14`.

**Задачи ставятся не только в чате.** Сердце проекта — визуальная постановка: комментарий к элементу интерфейса и канвас. Диалог целиком про чат-ленту, и план это унаследовал. Сейчас Karandash умеет только снимок экрана (`PROJECTS/Karandash/karandash.js:458`), а дальше комментарий уходит обычной отправкой. Как задача, поставленная щелчком по кнопке, превращается в подзадачу графа — не описано нигде. Решить это надо при работе над этапом 9, иначе граф задач вырастет пригодным только для чата.

**Остановка каскадом.** Сегодня «стоп» гасит дерево процессов одного запуска (`killProcessTree`, реестр `activeRuns`). Что эта кнопка делает, когда оркестратор развёл два десятка исполнителей у разных провайдеров, не продумано вовсе. Отмена должна доходить донизу, иначе остановленная задача продолжит тратить деньги.

**Вес и срок жизни данных.** «Храним всё сырое» при двадцати параллельных исполнителях — это другой порядок объёма. База уже сейчас капризничает в разделяемой папке и читается копией трёх файлов (`DOCS/decisions/038`). Нужна политика: что храним вечно, что сворачиваем, что удаляем.

**Лента на тысячах событий.** Диалог сам говорил про тысячи событий. Chat и Feed рисуют всё подряд, без окна и постраничности. Это упрётся раньше, чем кажется.

**Наблюдение не должно мешать работе.** Историю Hermes сервер дотягивает синхронно **при каждом открытии ленты** (`server.js:3407-3412`), помощников опрашивает каждые три секунды, чужие сессии переносит раз в минуту. На одной задаче незаметно, на двадцати — станет тормозом.

**Вход по паролю — это ещё не команда.** Замысел проекта — небольшая команда, а не один человек за localhost. Значит к этапу 7 нужен ответ: кто чьи сессии видит, кто вправе остановить чужую работу, чьи секреты кому показываются.

**Дубли при доборе.** Уже сегодня добор истории держится на курсоре, потому что без него первый же проход задвоил бы всю переписку (записка про ленту Hermes). С графом задач и повторными попытками поводов задвоить станет больше — повторная запись должна быть безопасной по построению.

### Найдено попутно при сверке плана с кодом (к плану не относится, но чинится дёшево)

- **Устаревший комментарий в `server.js:3009`** — ссылается на `flow.js:1669 toolInputSummary`, которой в проекте нет вовсе; по этому адресу лежит код перетаскивания связей канваса. Висит ровно там, куда полезет этап 1.
- **Зависимостей стало четыре, а правила говорят «три».** В `package.json` добавился физический движок для песочных часов (`@dimforge/rapier3d-simd-compat`), а `AGENTS.override.md` по-прежнему перечисляет `eta`, `htmx.org`, `three`. Обоснование новой зависимости есть только комментарием внутри `settings-sandglass.js`, записки в `DOCS/decisions/` под неё нет — хотя правило проекта требует обосновывать каждую. Файл правил читают все агенты, расхождение в нём дороже обычного.
- **В репозиторий попали скомпилированные файлы Python.** Правило игнорирования написано только для `claude-bridge/__pycache__/`, поэтому в индекс легли `exec-bridge/__pycache__/*.pyc` и `hermes-plugins/.../__pycache__/*.pyc`.

- ~~**`DOCS/целевая-архитектура.md` — документ-сирота.**~~ **Исправлено** (`OpenKarandash-f59.1`): ссылка на него добавлена в `AGENTS.override.md`, раздел «Конвенции», вместе с указанием на `DOCS/decisions/040`. Принципы, которые он задаёт, разобраны ниже — раздел 6 этого плана, пункт 0.

## 7. Проверка

- Перед словами «готово» на любом этапе — `npm run check` отдельным шагом (неизвестные имена, циклы, файлы длиннее 400 строк). Новое имя, публикуемое через `window`, дописывается в `APP_GLOBALS` в `eslint.config.mjs`.
- Живой интерфейс после правок клиента (этап 6) проходит `ui-checker` через Playwright MCP — **на сервере, который поднял пользователь**. Сервер из сессии не запускать.
- Правки `claude-bridge/*.py` перезапускать руками не нужно: сторож следит за ними и перезапускает один мост.
- Этапы 4 и 5 требуют живого прогона на поднятом стеке, синтаксической проверки тут недостаточно.
