Ты — участник команды из нескольких агентов, каждый со своей ролью, которая
подключает OpenCode CLI к OpenKarandash так же по-настоящему, как уже подключён
Claude CLI. Твоя роль — серверная часть (`server.js`), только она.

Перед началом:
1. Прочитай `/mnt/c/0_PROJECTS/OpenKarandash/CLAUDE.md` целиком — там правила
   проекта (язык только русский в комментариях, без зависимостей, запрет
   запускать `server.js` из сессии, конвенции по проверке через `smoke.js`).
2. Прочитай `/mnt/c/0_PROJECTS/OpenKarandash/.claude/agents/memory/opencode-integration.md` —
   там уже проверенные вживую факты о поведении `opencode` CLI (формат стрима,
   флаги, список бесплатных моделей) и зафиксированный контракт API. Не
   перепроверяй то, что там уже написано фактом — верь и используй как есть,
   если только не найдёшь явное противоречие в коде.
3. Прочитай `server.js` целиком в местах, которые касаются Claude: строки
   ~327-944 (TARGETS/runClaude/detectInstalls/askClaude), ~980-1260 (схема БД
   и db.prepare хелперы), ~1425-1490 (роуты `/api/claude/*`). Это твой образец
   для подражания — не абстракцию изобретать, а зеркалить стиль и структуру.

Что нужно сделать (зеркалить архитектуру Claude, НЕ создавать общую абстракцию
над обоими CLI — в проекте сознательно нет такого слоя, читай CLAUDE.md про
отказ от преждевременных абстракций):

1. Свой блок обнаружения CLI: `OPENCODE_TARGETS` (или подобное имя) по образцу
   `TARGETS` — если бинарник не на PATH, проверь известный путь
   `~/.opencode/bin/opencode` (Linux/WSL) и по аналогии подходящий путь на
   Windows (сначала проверь `where opencode`/наличие файла реально, не
   выдумывай путь). Обязательно поддержи `process.env.OPENCODE_BIN` как явный
   оверрайд, как это уже сделано для `CLAUDE_BIN`.
2. `runOpenCode(target, cliArgs, {...})` — аналог `runClaude`, тот же паттерн
   (промпт через stdin, построчный парсинг NDJSON, таймаут, kill).
3. `detectOpenCodeInstalls()` — аналог `detectInstalls`, плюс отдельная функция
   получения реального списка моделей через `opencode models` (построчный
   текстовый вывод `provider/model`, без `--format json` — см. память агента).
   Список моделей НЕ хардкодить.
4. Свой модуль-level `activeOpenCodeTarget` (НЕ переиспользуй `activeTarget`
   Claude — иначе подключения провайдеров будут затирать друг друга).
5. `askOpenCode({ prompt, model, sessionId, mode }, send)` — аналог `askClaude`,
   переводящий события OpenCode (`step_start`/`text`/`tool_use`/`step_finish`/
   `error`, см. точные поля в памяти агента) в тот же общий `AskEvent` формат,
   который уже понимает фронтенд (`session|tool|text|context|error|done|queued`;
   `thinking`/`rate_limit` можно не эмитить — у OpenCode нет этих концепций).
   Пиши в БД теми же хелперами, что и Claude (`startExchange`, `recordStep`,
   `recordAssistantText`, `finishExchange`, `setSessionContext` и т.д.) — они
   уже общие, передавай `target` = id своего OpenCode-таргета. Обязательно
   переиспользуй общую очередь по файлам (`activeRuns`/`waitForFileTurn`/
   `candidateFiles`) — НЕ заводи вторую отдельную очередь, иначе Claude и
   OpenCode смогут одновременно писать в один файл.
   Токены/стоимость бери из `step_finish.part.tokens`/`.cost`.
6. Роуты `/api/opencode/detect`, `/api/opencode/connect`, `/api/opencode/ask`,
   `/api/opencode/stop` — по образцу соответствующих `/api/claude/*` роутов,
   тот же формат ответа (`{ installs: [...] }`, `{ ok, id, label, version }`
   / `{ ok:false, error }`, стриминг NDJSON с `Content-Type: application/x-ndjson`,
   `{ ok, stopped }`). Найди, где в server.js эти роуты диспетчеризуются
   (switch/if по `urlPath`), и добавь свои рядом по тому же принципу.
7. Проверь, нужна ли для OpenCode поддержка `lock-check` (если он умеет вызывать
   инструменты правки файлов через свой хук) — если не уверен, за пределы MVP
   не выходи: главное, чтобы одновременная работа с Claude по файлам была безопасна
   через уже существующую общую очередь (пункт 5).

Проверка своей работы:
- `node -c server.js` — синтаксис не должен быть сломан.
- `node SYSTEM/smoke.js` — не должен падать по существующим (не твоим) маршрутам;
  если добавляешь новый smoke-чек на свои роуты — читай, как это устроено для
  `/api/claude/*` в `SYSTEM/smoke.js`, и добавь аналогичные `check(...)` только
  для базовых вещей (`detect` без сети — не должен падать, даже если бинарника
  нет; `connect`/`ask` можно не покрывать смоуком, если они требуют реального
  бинарника, которого может не быть в CI/на другой машине — тогда просто оставь
  комментарий-пояснение почему).
- НЕ запускай `server.js` напрямую (`node server.js`) ни в фоне, ни на переднем
  плане — это запрещено правилами проекта (см. CLAUDE.md, «Проверка изменений»).
  Используй только `node -c` и `smoke.js`.
- Все новые комментарии в коде — только на русском.

В конце работы допиши короткую запись (дата, что сделал, какие функции/роуты
добавил, на что напоролся, что должен знать фронтенд-агент про реальные имена
роутов/полей) в конец файла
`/mnt/c/0_PROJECTS/OpenKarandash/.claude/agents/memory/opencode-integration.md`
в раздел «Журнал этапов» — не перезаписывай остальное содержимое файла, только
дописывай.

строк), результат `node -c server.js` и `node SYSTEM/smoke.js`, точные имена
и формы роутов `/api/opencode/*` для фронтенд-агента.
