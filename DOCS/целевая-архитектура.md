# Целевая архитектура: порядок ради слабого исполнителя

Разбор `chat.md` и решение, к чему проект идёт. Записка обзорная — конкретные развилки лежат в `DOCS/decisions/`.

## Суть разговора одним тезисом

Разговор выглядит как несколько разных тем — открытые модели, оркестраторы, «сайт из девяностых, но мгновенный», HTMX, память, бесплатные модели. Тема одна, и она сформулирована в середине прямым текстом:

> Скорость тут не из-за малого объёма кода, а из того, что меньше сложности… Агенту проще разобраться в таком проекте, разбить задачу и внести изменения.

И следом:

> Так код будет адаптирован под возможности агентов, а не наоборот… не просто помощник для людей, а кодовая база, оптимизированная для автономной работы с ИИ. И тогда выбор модели становится не таким критичным.

**Проект оптимизируется не под человека-читателя, а под исполнителя-агента — так, чтобы слабая модель физически не могла ошибиться.** Всё остальное в разговоре — средства к этой цели, а не отдельные пожелания:

| Средство из разговора | Зачем оно на самом деле |
|---|---|
| Серверные шаблоны + HTMX, минимум JS | у компонента одно место жительства, а не три; исполнителю нечего искать |
| Каждый крупный элемент — отдельный компонент | правка не выходит за границы одного файла и одного `id` |
| Бэкенд вертикальными фичами, а не слоями | контекст задачи целиком помещается в одну папку |
| Единый файл правил (`AGENTS.md`) | все инструменты читают один контекст, а не каждый свою память |
| Память слоями, отдельно от модели | знание переживает смену модели |
| Оркестратор, а не «самая умная модель» | исполнитель сменный, логика управления постоянна |
| Дробление до размера одного прохода | подзадача выполнима моделью, которая не удержит проект целиком |
| Метрика сложности | сигнал «проект стал труднее для агентов» раньше, чем он станет труднее |
| Живая карта работы | человек видит ход и может вмешаться, а не ждёт вслепую |

Проверка любого будущего решения — один вопрос: **уменьшает ли оно объём того, что исполнитель обязан удерживать в голове, чтобы не ошибиться.** Если нет — оно не из этого разговора.

## Что было понято неверно

Hermes — не имя идеи, а существующий проект: [NousResearch/hermes-agent](https://github.com/nousresearch/hermes-agent), MIT, Python. Ранее в этой работе он был признан несуществующим (искали пакет на npm вместо репозитория на GitHub) и написан заново своими руками. Записка [007](decisions/007-hermes-оркестратор-а-не-модель.md) исходила из ложной посылки и помечена как пересмотренная.

Что уже есть в настоящем Hermes из того, что мы собирались строить сами:

- планирование и разбиение цели, запуск изолированных подагентов для параллельных веток работы;
- смена провайдера одной командой (`hermes model`) — Nous Portal, OpenRouter, OpenAI, свой endpoint: ровно тот пункт разговора про «бесплатные модели»;
- собственная память: агент-курируемые заметки, поиск по прошлым сессиям (FTS5 + суммаризация), модель пользователя между сессиями;
- навыки (skills), которые агент создаёт сам после сложных задач и правит по ходу использования; совместимы со стандартом agentskills.io;
- `AGENTS.md` как файл правил — тот самый общий контекст из разговора;
- планировщик задач (cron), исполнение в семи разных средах (локально, Docker, SSH, Modal, …);
- `hermes chat -q "…" --oneshot` — headless-запуск одним вопросом, то есть та же форма, что у наших коннекторов;
- `hermes mcp serve` — MCP-сервер, через который Hermes становится **инструментом** для Claude Code, Codex и прочих. Это прямой ответ на вопрос из разговора «имеет ли смысл, чтобы Клод обращался к Гермесу и ставил ему задачу».

Вывод: писать оркестратор самим означало заново делать то, что уже сделано и развивается. Наш самописный `hermes-server.js` заменяется на подключение настоящего.

## Разделение ролей

Две системы, и границу между ними важно не размыть:

**Hermes — исполнительное ядро.** Думает, планирует, дробит, помнит, выполняет, учится, меняет модель под задачу. Лежит в папке проекта (`SYSTEM/Hermes/agent/`, коммит зафиксирован в `AGENT-PIN.txt`, в git не попадает — как `node_modules/`). Настраивается проектным конфигом, а не глобальным: тогда «весь его потенциал» настраивается под этот проект и переезжает вместе с ним.

**OpenKarandash — пульт и наблюдение.** Не думает. Показывает, что происходит, даёт вмешаться, хранит историю, рисует граф проекта. Всё, что он умеет, обязано быть понятно с одного взгляда — и человеку, и агенту, который будет его править.

Соблазн, которому нельзя поддаваться: дописывать в пульт «немного интеллекта» — свою очередь, свой ретрай, свою память. Каждый такой кусок — это второй экземпляр того, что уже есть в ядре, и он немедленно расходится с ним.

## Как выглядит переписанный интерфейс

Правило: **компонент = шаблон + маршрут + один `id`.** Ни один компонент не размазан по нескольким файлам.

- `SYSTEM/templates/<компонент>.eta` — вся разметка компонента, включая его форму и кнопки. В `index.html` от него остаётся пустой контейнер с `id` и `hx-get`.
- `/api/fragment/<компонент>` — единственный источник этой разметки.
- Клиентский JS у компонента либо отсутствует, либо это несколько строк на действия, которых htmx не покрывает.
- Точечное обновление: компонент перерисовывается по своему таймеру или по событию на `body`, соседи не трогаются. Это и есть «hot reload отдельного компонента» из разговора — на уровне работающего приложения, а не сборщика.
- Живая правка при разработке: сделано. Сервер смотрит, что изменилось, и шлёт событие на один фрагмент (`.eta`) или на одну таблицу стилей (`.css`); страница целиком перезагружается только там, где границы правки неизвестны. См. `DOCS/decisions/011`.

Порядок переезда компонентов — от самых больших: лента чата, список сессий, тулбар, Kanban, Flow, Settings.

## Как выглядит переписанный сервер

- Диспетчер (`server.js`) знает только: `.env`, статика, реестр маршрутов. Ничего предметного.
- Фича — папка: клиент, стили, шаблоны, `*-server.js` с `createRoutes(deps)`, свой `README.md`, свои проверки в смоуке.
- Ошибка предвиденная — `200 { ok: false }`; непредвиденная — `500` и запись в консоль. Тихих успехов не бывает.
- Каждый маршрут и каждый фрагмент имеет проверку в `SYSTEM/smoke.js` — включая метод запроса. Проверка не «на всякий случай»: смоук — единственное, что стоит между исполнителем и сломанным интерфейсом.

## Память

Четыре слоя, три из которых уже есть:

| Слой | Где живёт | Состояние |
|---|---|---|
| Проектная (что есть в коде) | `DATA/vault/Проект/`, индекс FTS5 | есть |
| История сессий | `DATA/vault/Сессии/` | есть |
| История решений (почему так) | `DOCS/decisions/` | есть |
| Рабочая и пользовательская | Hermes | берём у ядра, своё не заводим |

Правило: наружу, в repo, кладётся то, что должно пережить смену модели и агента. Всё остальное — забота ядра.

## Единый файл правил

`AGENTS.md` в корне репозитория — контекст для любого исполнителя, а не только для Claude Code. `CLAUDE.md` остаётся тонкой ссылкой на него плюс специфика Claude Code. Hermes читает `AGENTS.md` штатно.

## Порядок работ

1. Hermes в папке проекта, проектный конфиг, запуск проверен вручную.
2. `AGENTS.md` — единый файл правил; `CLAUDE.md` ужимается до ссылки и своей специфики.
3. Hermes как исполнитель в таблице `AGENTS` (`hermes chat -q … --oneshot`), самописный оркестратор удаляется.
4. `hermes mcp serve` — чтобы задачу Hermes мог ставить и внешний агент.
5. Переезд компонентов на шаблоны, от больших к малым.
6. Обновление фрагмента вместо перезагрузки страницы при правке файла — **сделано** (`DOCS/decisions/011`); там же вынос стилей из `index.html` по файлам компонентов.
7. Метрика сложности: размер файлов, число связей, глубина вложенности — отчёт, который видно на Home.

Пункты 1–4 снимают дублирование, 5–6 дают порядок, 7 не даёт порядку расползтись обратно.
