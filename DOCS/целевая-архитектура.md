# Целевая архитектура: порядок ради слабого исполнителя

Разбор `chat.md` и решение, к чему проект идёт. Записка обзорная — конкретные развилки лежат в `DOCS/decisions/`.

## Суть разговора одним тезисом

Разговор выглядит как несколько разных тем — открытые модели, оркестраторы, «сайт из девяностых, но мгновенный», HTMX, память, бесплатные модели. Тема одна, и она сформулирована в середине прямым текстом:

> Скорость тут не из-за малого объёма кода, а из того, что меньше сложности… Агенту проще разобраться в таком проекте, разбить задачу и внести изменения.

И следом:

> Так код будет адаптирован под возможности агентов, а не наоборот… не просто помощник для людей, а кодовая база, оптимизированная для автономной работы с ИИ. И тогда выбор модели становится не таким критичным.

**Проект оптимизируется не под человека-читателя, а под исполнителя-агента — так, чтобы слабая модель физически не могла ошибиться.** Всё остальное в разговоре — средства к этой цели, а не отдельные пожелания:

| Средство из разговора | Зачем оно на самом деле |
|---|---|
| Серверные шаблоны + HTMX, минимум JS | у компонента одно место жительства, а не три; исполнителю нечего искать |
| Каждый крупный элемент — отдельный компонент | правка не выходит за границы одного файла и одного `id` |
| Бэкенд вертикальными фичами, а не слоями | контекст задачи целиком помещается в одну папку |
| Единый файл правил (`AGENTS.md`) | все инструменты читают один контекст, а не каждый свою память |
| Память слоями, отдельно от модели | знание переживает смену модели |
| Оркестратор, а не «самая умная модель» | исполнитель сменный, логика управления постоянна |
| Дробление до размера одного прохода | подзадача выполнима моделью, которая не удержит проект целиком |
| Метрика сложности | сигнал «проект стал труднее для агентов» раньше, чем он станет труднее |
| Живая карта работы | человек видит ход и может вмешаться, а не ждёт вслепую |

Проверка любого будущего решения — один вопрос: **уменьшает ли оно объём того, что исполнитель обязан удерживать в голове, чтобы не ошибиться.** Если нет — оно не из этого разговора.

## Оркестратора в проекте нет

> **Раздел описывает состояние до решения `029`.** Hermes вернулся — как внешний оркестратор в Docker, а не как код внутри пульта (`029`, `036`, `040`). Главное правило раздела при этом осталось в силе и специально подтверждено владельцем 2026-09-18: **пульт по-прежнему не думает**. Граф подзадач, попытки, повторы и выбор исполнителя живут в Hermes, а мы их только отражаем в ленте. Читать ниже «оркестратора нет» следует как «своего оркестратора не заводим».

Своего оркестратора мы написали, потом заменили на настоящий (NousResearch/hermes-agent) — и в итоге убрали и его: см. `DOCS/decisions/015`. Пульт остался пультом, а планирование и дробление задачи делает тот CLI-агент, который подключён в настройках.

Отсюда и правило: заводить в пульте «немного интеллекта» — свою очередь, свой ретрай, свою память — нельзя. Каждый такой кусок дублирует то, что уже умеет подключённый агент, и немедленно расходится с ним.

## Разделение ролей

Две стороны, и границу между ними важно не размыть:

**CLI-агент — исполнительное ядро.** Думает, планирует, дробит, помнит свою сессию, выполняет. Подключается в настройках, меняется на другой без правок в пульте — все различия собраны в таблице `AGENTS` (`DOCS/decisions/006`).

**OpenKarandash — пульт и наблюдение.** Не думает. Показывает, что происходит, даёт вмешаться, хранит историю, рисует граф проекта. Всё, что он умеет, обязано быть понятно с одного взгляда — и человеку, и агенту, который будет его править.

## Как выглядит переписанный интерфейс

Правило: **компонент = шаблон + маршрут + один `id`.** Ни один компонент не размазан по нескольким файлам.

- `PROJECTS/<Фича>/<компонент>.eta` — вся разметка компонента, включая его форму и кнопки. В `index.html` от него остаётся пустой контейнер с `id` и `hx-get`.
- `/api/fragment/<компонент>` — единственный источник этой разметки.
- Клиентский JS у компонента либо отсутствует, либо это несколько строк на действия, которых htmx не покрывает.
- Точечное обновление: компонент перерисовывается по своему таймеру или по событию на `body`, соседи не трогаются. Это и есть «hot reload отдельного компонента» из разговора — на уровне работающего приложения, а не сборщика.
- Живая правка при разработке: сделано. Сервер смотрит, что изменилось, и шлёт событие на один фрагмент (`.eta`) или на одну таблицу стилей (`.css`); страница целиком перезагружается только там, где границы правки неизвестны. См. `DOCS/decisions/011`.

Порядок переезда компонентов — от самых больших: лента чата, список сессий, тулбар, Kanban, Flow, Settings.

## Как выглядит переписанный сервер

- Диспетчер (`server.js`) знает только: `.env`, статика, реестр маршрутов. Ничего предметного.
- Фича — папка: клиент, стили, шаблоны, `*-server.js` с `createRoutes(deps)`, свой `README.md`.
- Ошибка предвиденная — `200 { ok: false }`; непредвиденная — `500` и запись в консоль. Тихих успехов не бывает.
- Автоматических проверок у маршрутов нет: смоук удалён (`DOCS/decisions/025`). Между исполнителем и сломанным интерфейсом стоит разбор файла (`node --check`) и живая проверка в браузере на сервере пользователя.

## Память

Четыре слоя, три из которых уже есть:

| Слой | Где живёт | Состояние |
|---|---|---|
| Проектная (что есть в коде) | `DATA/vault/Project/`, индекс FTS5 | есть |
| История сессий | `DATA/vault/Sessions/` | есть |
| История решений (почему так) | `DOCS/decisions/` | есть |
| Рабочая и пользовательская | подключённый CLI-агент | берём у ядра, своё не заводим |

Правило: наружу, в repo, кладётся то, что должно пережить смену модели и агента. Всё остальное — забота ядра.

## Единый файл правил

`AGENTS.md` в корне репозитория — контекст для любого исполнителя, а не только для Claude Code. `CLAUDE.md` остаётся тонкой ссылкой на него плюс специфика Claude Code.

## Порядок работ

1. `AGENTS.md` — единый файл правил; `CLAUDE.md` ужимается до ссылки и своей специфики — **сделано**.
2. Оркестратор из проекта убран, интеллект живёт только в подключённом CLI — **сделано** (`DOCS/decisions/015`), затем **пересмотрено**: интеллект живёт в Hermes снаружи пульта (`029`, `040`).
3. Переезд компонентов на шаблоны, от больших к малым.
4. Обновление фрагмента вместо перезагрузки страницы при правке файла — **сделано** (`DOCS/decisions/011`); там же вынос стилей из `index.html` по файлам компонентов.
5. Метрика сложности: размер файлов, число связей, глубина вложенности — отчёт, который видно на Home.

Пункты 1–2 снимают дублирование, 3–4 дают порядок, 5 не даёт порядку расползтись обратно.
