# Журнал запусков инструментов Hermes — это его state.db

## Решение

Единственный источник ответа на «какой инструмент Hermes когда запускался» — база самого Hermes `hermes-home/state.db` (таблица `messages`: строка роли `tool` с временем, id сессии и результатом, аргументы — в `tool_calls` предыдущей строки `assistant`). Своей таблицы-копии у нас нет. Читается она одной командой: `node SYSTEM/core/hermes-tool-runs.js` (фильтры `--session`, `--tool`, `--since`, `--limit`, `--json`); та же функция `readToolRuns` экспортируется под будущий маршрут.

Таблицы `hermes_runs`/`hermes_tasks` в `DATA/.sessions.db` удаляются при старте сервера.

## Почему

Выглядело так, будто журнал «задуман, но не подключён»: в нашей базе были `hermes_runs`/`hermes_tasks`, но пустые. На деле это остаток встроенного оркестратора из записки 007 (план → задачи → ревью), который удалён целиком решением 015; таблицы пережили код, потому что `CREATE TABLE` из базы сам не уходит. Под журнал инструментов их схема и не годится — в ней цели и попытки, а не вызовы.

Остальные места, где что-то пишется, — не журнал инструментов: `DATA/server-exits.log` — причины остановки нашего сервера, `session_cli` — соответствие нашей сессии и id внутри CLI для `--resume`, `hermes-home/logs/` — служебные логи стека (gateway, curator). Лента сессии в `messages` нашей базы хранит только то, что дотянуто в неё `hermes-history.js`, и отстаёт от Hermes.

Hermes же пишет каждый вызов сам и полностью. Своя копия дала бы второй источник, который расходится с первым при любом ходе мимо нашего сервера.

## Чем платим

Читать приходится копию трёх файлов базы (`.db`, `-wal`, `-shm`): прямое чтение WAL-базы через 9p/drvfs под пишущим контейнером падает с «disk I/O error». На больших базах это секунда-другая на запрос. Схема `state.db` чужая и может поменяться с обновлением `hermes/` — тогда правится один файл `hermes-tool-runs.js`.
