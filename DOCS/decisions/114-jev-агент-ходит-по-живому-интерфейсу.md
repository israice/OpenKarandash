# 114. Jev-агент ходит по живому интерфейсу

## Проблема

`npm run ui` (`SYSTEM/ui-walk.mjs`) обходит интерфейс списком, записанным в
скрипте: вкладки из `App.VIEWS`, кнопки «+» из тулбара, модалка настроек. Список
написан руками, поэтому он одновременно и проверка, и её потолок: всё, чего в
список не внесли, не проверяется никогда. Добавить новую вкладку — значит
вспомнить про скрипт.

Второе ограничение того же места: скрипт умеет только «открыть и посмотреть».
Путь до goal вида «открыть настройки, найти поле и ввести значение» он не
проходит — проверяется лишь `offsetParent !== null` и непустой `innerText`.

## Решение

`SYSTEM/ui-agent.mjs` (`npm run ui-agent`) — тот же безголовый Edge через CDP,
но решение принимает Jev, а не список в коде.

Один ход агента:

1. Ожидание устойчивой страницы: два одинаковых снимка подряд, иначе пульт ещё
   дорисовывает верхнюю панель и нужной кнопки на снимке просто нет.
2. Снимок видимых контролов (`a, button, input, select, textarea, [role=button],
   [data-page]`) одним `Runtime.evaluate`. Каждому проставляется `data-jev-i`,
   подпись берётся из `innerText / value / title / placeholder / aria-label`.
3. **Один** запрос TypeSafe System One с двумя Choice-вопросами: операция
   (`CLICK, TYPE_TEXT, SELECT, SCROLL_UP, SCROLL_DOWN, DONE, BLOCKED`) и
   таргет (контрол по индексу). Оба в одном запросе — как в jev-ultrafast, где
   операция и цель решаются за один round trip.
4. Проверка и выполнение: таргет берётся из узла, помеченного в снимке, а не из
   строки модели; перед кликом элемент прокручивается в видимую часть и
   сверяется, что его не перекрыл другой (`elementFromPoint` по центру).

Транспорт и пороги — те же, что у остальных суждений: `SYSTEM/core/typesafe.js`
и `judgment-config.js`. Отдельной модели и отдельного ключа не заводим: Jev уже
работает в проекте, вопросы в этом скрипте ничего не знают о его словах, пороги
у него свои — так и у `inbox-judgment.js`.

## Что показала проверка на живом пульте

Три вещи, которые выяснились только прогоном и учтены в коде:

- **`BLOCKED` на раннем снимке — это не ответ, а нетерпение.** Пока панель не
  дорисована, модели честно нечего кликать: `blocked 0.95` против `click 1.0`
  на том же снимке после ожидания. Отсюда ожидание устойчивости и три попытки
  вместо мгновенной сдачи (это операция `WAIT` у jev-ultrafast).
- **Пульт прячет `body` через `visibility: hidden`, пока не завершился бут.**
  `innerText` тогда пуст, а `elementFromPoint` отдаёт `HTML`, и проверка
  перекрытия рубит живые кнопки («covered by HTML» на «Feed», «Settings»).
  Поэтому текст страницы берётся с откатом на `textContent`, а hit-test
  пропускается, когда body скрыт: проверять нечего, а клик при этом работает.
- **Проверка перекрытия должна идти после прокрутки в видимую часть.** Иначе
  точка вне экрана даёт фиктивное перекрытие.

Отдельно: `--expect` стоит брать такой строкой, которой на странице до цели не
было. На скрытом пульте текст берётся из `textContent`, и «Feed» там есть
всегда — такая проверка подтверждает меньше, чем кажется.

## Приёмы, взятые у jev-ultrafast

- **Индексированное пространство действий вместо рассуждения по странице.**
  Модель выбирает из того, что страница реально показала. Скриншотов в цикле
  нет вообще — только текст и таблица контролов.
- **`DONE` не является доказательством.** Успех подтверждается независимо:
  `--expect "строка"` читается из живой страницы (title + url + body). Без
  `--expect` подтверждением служит факт, что хотя бы одно действие выполнилось.
- **Отказ опасным кликам.** Подписи `send / submit / pay / buy / checkout /
  delete / publish` (и русские `отправ / удал / плат / куп`) не выполняются
  никогда: прогон останавливается с `refused click`. Проверка живёт в коде,
  а не в вопросе модели.
- **Текст не генерируется моделью.** Значения полей задаёт человек:
  `--text "Подпись=значение"`, подпись ищется без учёта регистра. Иначе в
  проекте появился бы второй платный шаг в цикле.

## Чего скрипт не делает

- Не знает строк приложения: он проходит интерфейс, а не проверяет содержимое
  списков и пересчёты. Для этого `ui-walk.mjs`.
- Не выполняет `SELECT` точным значением, а берёт первый несогласованный
  вариант — точное значение сузило бы вопросы до одного пункта выбора, и на
  этом месте появляется отдельная модель.
- Не ждёт сетевых ответов дольше 1200 мс: инерция пульта делает точное
  ожидание отдельной задачей, а не деталью одной строки.

## Проверка

Запуск: `npm run ui-agent -- --goal "..." --expect "..."`. Код выхода: 0 —
цель достигнута и консоль чиста, 1 — были ошибки консоли, 2 — нет ключа или
цели, 4 — цель не подтверждена. `JEV_DEBUG=1` печатает снимок и вероятности
каждого хода.

Прогон на живой копии пульта:

```
npm run ui-agent -- --goal "Открой окно настроек: нажми кнопку «Settings» в верхней панели" --expect "Settings"
# [0] CLICK # "Settings" — clicked
# [1] DONE # "Settings"
# Итог: done, --expect «Settings» найден   код 0
```

Прогон с недостижимой целью (`--goal "нажми кнопку «Feed»"`, когда панель не
дорисовалась): три `BLOCKED` с паузой, затем `blocked`, код 4 — так и должен
выглядеть отказ, а не зависание.

Что **не** проверено: ввод текста в поле (`TYPE_TEXT`) и `SELECT` на живом пульте
не прогонялись — подходящего поля в верхней панели нет, а сцена с полем требует
придуманной страницы. Код этих двух операций написан по тому же снимку и
охраннику, что и `CLICK`, но фактического прогона не было.

## Чего не сделано

`ui-walk.mjs` не тронут: у него своя роль (проверка вкладок и пустых панелей по
списку), и его браузерная обвязка с `Page.reload` в этом окружении зависает —
причина старая и общая, агент на неё не натыкается (своя вкладка создаётся
сразу по адресу).
