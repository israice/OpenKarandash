# 077. Проект живёт на Windows: WSL, Docker и Hermes убраны

Решение владельца от 2026-10-01. Отменяет и заменяет `003`, `010`, `029`, `030`,
`031`, `033`, `036`, `037`, `038`, `039` (в части пересборки ленты), `040` (в части
Hermes), `041`, `047`, `050`, `069`, а также отменённые ранее `021` и `030`.

## Что было

Проект вырос вокруг трёх инфраструктурных решений, каждое из которых тянуло за собой
остальные:

1. **CLI-агент жил в WSL.** Сервер поднимал `wsl.exe bash -lc "opencode ..."`, а вся
   обвязка была под это: `viaShell` и склейка аргументов в одну строку, PID-маркер
   `REMOTE_PID_MARK`, чтобы убить процесс внутри виртуалки, отдельная ветка
   `kill -TERM` через `wsl.exe`, второй набор целей `OPENCODE_TARGETS`, компенсация
   сырого режима консоли ради Ctrl+C, `localPath()` для путей git.
2. **Оркестратор жил в Docker.** `SYSTEM/core/hermes-stack.js` клонировал `hermes/`
   с GitHub, собирал образ, поднимал `docker compose up -d gateway`, рядом — мост
   `claude-bridge/` на питоне и второй мост `exec-bridge/`, `hermes-plugins/`,
   `hermes-start.sh`/`hermes-stop.sh`, `docker-compose.hermes.yml`. Сторож следил за
   файлами мостов и перезапускал их отдельно.
3. **Проверки жили через это.** Сервер отвечает только локальным запросам, поэтому
   агент из WSL до него не дотягивался: `ui-walk.mjs` и `live-verify/run.mjs`
   перезапускали себя node на Windows через `wslpath` + `powershell.exe`.

Каждая из трёх требовала двух остальных, и вместе они стоили дороже, чем давали:
около тысячи строк серверного кода на коннектор Hermes, полтысячи на мосты, ~180
строк обвязки WSL плюс две копии одного и того же механизма перезапуска себя.

## Что стало

**Всё живёт нативно на Windows, в одном процессе, без внешних слоёв.**

- Агент — `opencode.exe`, цель `opencode-windows` (или `opencode-custom`, если задан
  `OPENCODE_BIN`). Ни `viaShell`, ни склейки аргументов, ни PID-маркера: `spawn`
  получает массив аргументов, а остановка идёт через `taskkill /T /F` по дереву.
- `hermes-stack.js`, `hermes-history.js`, `hermes-tasks.js`, `hermes-tool-runs.js`,
  `claude-bridge/`, `exec-bridge/`, `hermes-plugins/`, `docker-compose.hermes.yml`,
  `hermes-start.sh`, `hermes-stop.sh`, `hermes-home.config.example.yaml`,
  `PROJECTS/Browser/` и клон `jev-ultrafast/` удалены целиком. В таблице `AGENTS`
  остался один агент, и это не упрощение «на потом» — владелец новых агентов не
  заводит (`075`).
- `SYSTEM/core/host-deps.js` остался, но ставит только git и python: Docker больше не
  нужен, а агентский CLI подключается кнопкой в Settings — молча ставить его нельзя,
  человек выбирает сам.
- `npm run ui` и сценарии `live-verify` работают прямо на Windows-хосте, откуда угодно
  не перезапускаются. Код выхода 3 («здесь прогнать нельзя») остался — но означает
  теперь ровно одно: платформа не Windows.
- Из `.env` убраны `HERMES_*`, `API_SERVER_*`, `CLAUDE_BRIDGE_*`, `HERMES_STACK`.

## Что стало с хранением и лентой

У Hermes был свой механизм достраивания ленты: ходы, начатые мимо пульта,
пересборка хода по истории агента, шаги помощников `delegate_task`. Он ушёл вместе
с ним, и вместе с ним ушли таблицы `replaced_messages` и поля
`task_id`/`attempt_id` — писать их стало некому. Само правило «три отображения —
один источник» (новая записка `039`) осталось в силе целиком: изменился механизм
под ним, не правило. Event Schema и её одно место заполнения (`stampEvent`)
тоже остались.

Запись о том, что оркестрации в пульте нет, сохранена в новой `040` — пункт про
Hermes в ней стал историческим, а правило осталось.

## Почему именно так

**Меньше — значит меньше ошибается.** Мерило проекта одно: уменьшает ли решение
объём, который исполнитель обязан удерживать в голове (`DOCS/целевая-архитектура.md`).
Три инфраструктурных слоя требовали держать в голове: как звать CLI, куда уходит
его PID, почему сервер не отвечает агенту, почему `docker pause` тут при чём. После
правки этого объёма не остаётся вовсе, а возможности те же.

**Одна платформа вместо трёх слоёв.** Windows-хостец, WSL и контейнер Docker были
тремя разными средами, и почти каждая интеграция тащила в себе «а если запустить
оттуда». Нативный Windows убирает этот класс ошибок целиком, а не сокращает.

**Масштабируется простыми средствами.** Новый агент — это строка в таблице `AGENTS`
и его цель в списке (как это и задумано в `017`), а не новый мост, контейнер и
образ. Новая страница интерфейса — папка в `PROJECTS/` с `page.js` и `page.css`
(`014`, `016`), и её правка пересобирает только её (`011`).

## Что было проверено и как

- `npm run check` — чисто: неизвестные имена (eslint), циклические связи (madge).
- `npm run ui` — все вкладки, страницы «+» и окно настроек открылись без ошибок
  консоли и пустых панелей.
- Живой прогон на сервере владельца: список сессий открылся, `three-views` сошёлся
  по трём отображениям, короткий ход дошёл до ответа и лёг в базу.

## Отдельно: `npm run check` не работала вовсе

Попутно нашлось и исправлено: `SYSTEM/checks.js` звал инструменты с `shell: true`,
а на Windows `execFileSync` идёт через `cmd`, который режет строку по пробелам —
`C:\Program Files\nodejs\node.exe` превращался в `C:\Program`. Обе проверки молча
падали с `'C:\Program' is not recognized`. Теперь `shell` не используется, и проверки
действительно гоняют eslint и madge. Правило появилось само собой из смены платформы:
то, что проходило под Linux, на Windows тихо не работало.
