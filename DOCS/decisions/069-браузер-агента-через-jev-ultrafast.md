# Браузер агента — jev-ultrafast, клон в корне проекта

## Решение

Для управления браузером берём `browser-use/jev-ultrafast`. Код клонируется в `jev-ultrafast/` в корне проекта по образцу `hermes/`: в git его нет (`.gitignore`), карта проекта его обходит (`SYSTEM/core/scan.js`). В git живёт только наша обвязка — `PROJECTS/Browser/`.

Обновление 2026-09-23: мост до Chrome поднимает агент из сессии (команда в `PROJECTS/Browser/README.md`). Раньше правило было «запускается руками на Windows» — оно отменено владельцем. Сторож мост по-прежнему не поднимает.

Обновление 2026-09-23 (копия профиля): агент может работать с входами, уже стоящими в настоящем Chrome хозяина. Синк `PROJECTS/Browser/sync-user-profile.js` копирует каталог данных Chrome в `DATA/userchrome-profile` (задаётся `CHROME_PROFILE_DIR`), выбранный профиль — как `Default`; куки расшифровываются тем же пользователем Windows, потому что ключ (Local State) копируется вместе. Родной профиль не используем напрямую: Chrome с 136-й версии не открывает отладку на штатном каталоге данных, а живой Chrome держит его залоченным — поэтому копия, и поэтому синк надо повторять, когда нужны свежие входы (Chrome при этом лучше закрыть). Это профиль браузера jev, а не «профиль работника» записки 028: того работника каталог агента pi трогать не задумано.

## Почему

Инструмент на Python (`uv`), а зависимости проекта — npm, и записка 004 разрешает только те, что убирают существенный объём своего кода. Свой драйвер браузера с выбором элементов писать дороже. Класть его в `package.json` нельзя, а чужой код в наш git — незачем: клон обновляется сам. Ключ TypeSafe у проекта лежит в `.env` (`TYPESAFE_API_KEY`), его же читает `SYSTEM/core/typesafe.js`.

## Чем платим

Ещё один клон с внешним обновлением и второй рантайм (Python и `uv`). Нужен ключ OpenRouter (`TEXT_MODEL_API_KEY`) — теперь он в `.env` проекта, для `TYPE_TEXT` используется free-модель (`TEXT_MODEL`, `TEXT_MODEL_BASE_URL`). Chrome стоит на Windows, а исполнение — из WSL/контейнера, поэтому нужен мост `PROJECTS/Browser/chrome-bridge.js`: прокси на стороне Windows, который сам поднимает Chrome на отдельном профиле и пускает нас только по секретному префиксу пути (токен в `.env`). Порт отладки Chrome — полный контроль над браузером и входами в аккаунты, поэтому голым его наружу не выставляем. Мост поднимает агент из сессии (см. Решение), сторож его не поднимает; отдельный профиль `DATA/chrome-profile` значит, что входить в аккаунты в нём придётся один раз.

## Что проверено

Пакет ставится, импортируется, 31 офлайн-тест проходит. Мост проверен на подставном Chrome (другие порты, токен через окружение): ответ `/json/version` через токен возвращает адрес websocket, переписанный на мост; Chrome получает Host `127.0.0.1`; чужой токен и путь без токена дают 404, в том числе для websocket; websocket доходит до Chrome без Origin, байты идут в обе стороны. С настоящим Chrome на Windows и брандмауэром (доступ из WSL по токену, чужой токен — 404) проверено 2026-09-23. Живой проход jev с ключами проекта тоже прошёл: TypeSafe выбирает действия, `TYPE_TEXT` пишет free-модель OpenRouter (`nvidia/nemotron-3.5-lightning:free`); нужен `TEXT_MODEL_BASE_URL=https://openrouter.ai/api/v1` (без него jev по умолчанию идёт в `api.deepseek.com` и падает с 401). Эффект действий — ввод текста и клик — проверен отдельно по DOM, как требует сам jev («DONE не доказывает успех»).
