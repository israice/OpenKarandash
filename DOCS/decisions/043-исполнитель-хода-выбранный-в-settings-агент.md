# Исполнитель хода — выбранный в Settings агент, а не Hermes с мозгом-claude

Следствие `029` и эпика `OpenKarandash-f59`: Hermes — оркестратор ("`040`"), но его мозгом по умолчанию служит claude через `claude-bridge` (`hermes-home.config.example.yaml`: `model.default: claude-bridge-sonnet`). Случай 2026-09-18: сессия велась OpenCode CLI, а ход «сделал, проверь» ушёл в коннектор Hermes (в базе: `provider: hermes-docker`, в `input_sent` — handoff-преамбула «this continues a conversation held by a different CLI»). Подписка claude за мостом оказалась исчерпана — ход умер с `Billing or credits exhausted ... account org-18b1ab... is suspended due to insufficient balance`, хотя выбранный в Settings агент (opencode) был жив и держал историю сессии.

## Решение

**Ход продолжает тот агент, который выбран в Settings и вёл сессию, — не Hermes с всегда-клодом за спиной.** В `askHermes` (`server.js:2314`) в начале добавляется развилка: если `target` сессии принадлежит прямому CLI (`opencode`/`codex`/`pi`), ход передаётся его коннектору — с его же историей (`resumeAndHandoff`) и его моделями. Hermes-коннектор остаётся своим путём только для сессий Claude (`029`: мозг Hermes и есть тот же claude) и собственных `hermes-*`. Неподключённый владелец даёт явную ошибку «is not connected — open Settings and connect it», а не молчаливую деградацию в claude.

- Это вариация того же правила из плана (`chat_to_prompt.md`, этап 5): провайдер выбирается на подзадачу свой, и исчерпанный лимит не должен ломать задачу — подзадача уходит другому провайдеру и продолжает с того же места.
- Для opencode продолжение получается идеальным: у его target в `session_cli` уже лежит история сессии, и `resumeAndHandoff` находит её — продолжение не путается и не начинает разбор с нуля.
- Менять мозг Hermes на opencode невозможно физически (opencode CLI гоняет собственного агента со своим набором инструментов, а Hermes требует OpenAI-совместимого chat_completions с произвольными tool-схемами — так умеет только `claude-bridge`), поэтому правится не мозг, а маршрутизация: не-claude сессия в Hermes просто не заходит.

## Чем платим

**Прямые коннекторы бедны помощью Hermes.** У opencode/codex/pi нет помощников-делегатов (`delegate_task` в дочерних сессиях), поэтому ход открытой сессии через них лишается оркестрации этапов, которую Hermes мог бы разложить на проверяющих. Это сознательная плата: она включается только там, где Hermes всё равно не мог бы вести сессию выбранным агентом.

**Внутренние циклы Hermes остаются на claude-bridge.** Правило действует в контуре приложения (ход из интерфейса/Telegram), но собственные оркестраторские контуры Hermes (cron, супервизор-контрольные точки) по-прежнему думают `claude-bridge-sonnet`. Это не обходится этой запиской; по плану их разгружает `OmniRoute` и политика вызова Claude (этап 5, `f59.5`).

**Codex отдаётся как «не реализован».** Если владелец сессии — codex, развилка приводит к `askCodex`, который честно отвечает «Codex chat is not implemented yet»; это не регресс, `askCodex` таким был и раньше.

## Что проверено

- `node --check server.js` и `npm run check` — чисто.
- Развилка не задевает существующие пути: `askClaude` (строка подмены) вызывает `askHermes` только для claude-сессий; `agentNameByTarget` для пустого target по-прежнему даёт `claude`, и поведение для сессий без владельца не меняется.
- Все коннекторы имеют `connected()`, поэтому ветка «владелец не подключён» не падает, а отвечает читаемой ошибкой.
