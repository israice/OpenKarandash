# Запуск и остановка сервера — из одного источника

## Решение

1. **Правда о запущенном сервере лежит в одном файле — `DATA/server.lock`.**
   Замок читает и пишет модуль `SYSTEM/core/server-lock.js`: он и есть
   владелец файла. Внутри теперь лежит не один pid, а оба: сторож и сервер
   (`{"watchdog": …, "child": …}`), — чтобы остановка нашла всё дерево, а не
   только сервер.

2. **Остановка — одна команда: `npm stop`** (`SYSTEM/stop.js`). Она читает
   замок, гасит сторож, потом сервер, снимает замок и говорит, свободен ли
   порт. Раньше остановка была описана в правилах как ритуал с
   `Get-CimInstance` по имени `node.exe` — теперь он не нужен.

3. **Ctrl+C в терминале тоже оставляет после себя ничего.** Сторож ждёт
   смерти ребёнка и только потом уходит; раньше он гасил сервер и выходил
   сразу, и снять замок (это делал обработчик выхода ребёнка) не успевал.

4. **Сервер не переживает сторожа.** Сторож кладёт свой pid в замок, сервер
   спрашивает, жив ли он, и умирает вместе с ним, снимая замок. Раньше
   умерший сторож оставлял сервер-зомби: он держал порт, базу и telegram-токен,
   и второй экземпляр поднять было нельзя.

5. **Запуск — `npm start`** (то же, что `node server.js`). Отказ «замок
   занят» называет и говорит, что делать: `npm stop`.

## Почему

Жалоба владельца 2026-10-21: сервер остановлен через Ctrl+C, а следующий
запуск отказывается:

```
Another OpenKarandash server is already holding …\DATA\server.lock (last heartbeat 4s ago).
```

Проверено на живом запуске: сервер остановлен, порт 3001 свободен, процесса
нет — а файл замка лежит, и новый запуск отказывает. Причина одна и целиком в
стороже (`SYSTEM/core/watchdog.js`):

```js
if (child) child.kill('SIGTERM');
process.exit(0);            // ← уходим раньше, чем отработает 'exit' ребёнка
```

Снятие замка было в обработчике выхода ребёнка. Родитель уходил первым, и
замок оставался с пульсом не старше трёх секунд — ровно столько, сколько
сторож живёт после `process.exit`. Дальше пульс замолкал, но `STALE_MS` — четыре
пульса, двенадцать секунд: в это окно запуск отказывал.

То же самое оставляло зомби: если сторож умирал, не погасив ребёнка (окно
терминала закрыли, сторож убили), сервер оставался один — с портом, базой и
telegram-токеном. Правила проекта описывали это как ручной ритуал
(`DOCS/agents/проверка.md`), а не как команду.

## Стандарт

Права на остановку процесса и проверку его жизни — POSIX (`kill(2)`, сигнал
0 как проверка без убийства); Windows реализует `SIGTERM` как
`TerminateProcess`, поэтому «мягкой» остановки там нет, и замок снимает тот,
кто пережил гасящего: сторож.

## Чем платим

- В замке теперь JSON, а не pid. Старый формат (просто pid) тоже читается —
  файл живёт в `DATA/` и мог остаться от прежней версии.
- Сторож и сервер должны умереть вместе: сервер спрашивает сторожа о жизни
  раз в две секунды. Если pid сторожа успеет переиспользовать другой процесс
  (на Windows pid переиспользуется), сервер может остановиться зря. Риск
  маленький, цена — лишний перезапуск, а не порча данных.
- Проверка «сервер не пережил сторожа» в самопроверке проходит и на Windows
  (там смерть родителя убивает и ребёнка), и там, где ребёнок остаётся жив
  (сервер сам замечает пропажу сторожа).

## Что не менялось

- Замок остаётся общим для Windows и WSL: решение «работает кто-то другой»
  принимает пульс файла, а не pid. Pid в разных средах ничего не значит
  (`DOCS/decisions/001`).
- Порт по-прежнему ровно один, из `.env`; соседние не подбираются.
- Сервер по-прежнему запускает человек, а агент из сессии — нет
  (`DOCS/decisions/002`).
- Идущий ход по-прежнему дописывается в базу при перезапуске, а не теряется:
  порядок «сервер сам решает, когда ему можно умереть» не тронут
  (`DOCS/decisions/020`).

## Проверено

- Самопроверка `SYSTEM/server-lock-check.js` (в общей проверке `npm run check`):
  девять сценариев на временном файле — захват, отказ при занятом замке,
  снятие, перехват устаревшего, остановка живого процесса, остановка при
  отсутствии замка, смерть сторожа (сервер не переживает), остаток замка после
  резкой смерти (остановка его убирает).
- `npm run stop` на живом проекте: замок от упавшего сервера (формат старый,
  просто pid) убран, порт 3001 свободен — сообщение «the server was not
  running».
- `npm run check` EXIT=0.

Не проверено: живой Ctrl+C в терминале владельца (окно консоли и посылка
0x03 в сыром режиме не воспроизводятся из сессии) и запуск сервера новой
версии — сервер из сессии запускать нельзя (`DOCS/decisions/002`).
