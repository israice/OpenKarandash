# Докеризация сервера: образ, допуск запросов из docker-сети

**Проблема.** Сервер проектировался как пульт для одной машины: `server.js`
слушал `127.0.0.1`, `isLocalRequest` (SYSTEM/core/http-server.js) отвечал 403
всему, у кого адрес соединения не loopback. При запуске в контейнере это
означало три отказа подряд: запрос с хоста приходит через docker-proxy с
адреса шлюза (`172.17.0.1`), а не loopback. Второй претендент — Host: браузер
обращается к контейнеру по `host.docker.internal`, и заголовок Host с этим
именем тоже не проходил проверку.

Сопутствующие находки при сборке:

- bind mount `C:\...:/app` под Docker Desktop на Windows (WSL2) увязает
  процессы в D-состоянии на I/O (9p-дросселирование) — рабочие каталоги
  контейнера держим томами, не bind mount;
- named volume `/app` перекрывает `/app` образа: если том создан до правки
  кода, в нём остаётся старая копия файлов, и правку в контейнер не видно;
- в контейнере нет `.git` — сервер печатает `fatal: not a git repository`,
  но поднимается; карта строится без истории;
- `noteName` вызывался из `graph-vault-core.js`
  (PROJECTS/Graph/graph-vault-sync.js:51,112), а живёт в
  `graph-vault-notes.js` — сборка карты vault падала с
  `require(...).noteName is not a function` на любой машине без git;
- `node-screenshots` требует libdbus-1-3 и родню X11/atk — без них `npm ci`
  ставится, но require падает.

**Решение.** `Dockerfile` (node:22-bookworm, opencode-ai глобально, системные
библиотеки, `npm ci --omit=dev`), `.dockerignore` (node_modules, .git, DATA,
json-renderer — они съедали 700 МБ контекста), `docker-compose.yml`
(тома `project` и `data`, порт 3001).

Доступ: `HOST` в `server.js` — адрес прослушивания (пусто → 127.0.0.1,
прежнее поведение), `ALLOW_CONTAINER=1` в `http-server.js` — допуск адресов
docker-сети, `host.docker.internal` — допустимый Host. Это осознанное
ослабление границы: оно включается явно, окружением, и в образе — только для
запуска в контейнере, где порт всё равно закрыт пробросом портов.

Почему не проще: убирать проверку loopback совсем нельзя — сервер запускает
локальный CLI, а граница запросов описана в 103. Значение по умолчанию
не меняется: контейнер — отдельный режим запуска, а не новая норма.

**Последствия.** Вне контейнера поведение не меняется (проверено: `npm run
check`, пульт владельца). В контейнере сервер доступен с хоста через проброс
порта; скриншоты Karandash недоступны (нет экрана хоста), Hermes-стек нет.

**Пересмотр.** Если понадобится публикация пульта в сеть за пределами
docker-proxy, этот флаг расширять нельзя — нужен отдельно спроектированный
доступ (обратный прокси с TLS), иначе CLI остаётся доступен всем через порт.
