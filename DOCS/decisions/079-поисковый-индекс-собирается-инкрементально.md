# 079. Поисковый индекс собирается инкрементально и один раз жмётся

## Проблема

`rebuildSearchIndex` делал `DELETE FROM docs` и вставлял в FTS5 заново всё: код
проекта, заметки vault и **всю переписку всех сессий**. Замер на живых данных:

| | было |
|---|---|
| живое содержимое индекса | 5.8 МБ |
| файл `DATA/.index.db` | **837 МБ** + 247 МБ WAL |
| прирост за одну пересборку | +1.6 МБ, навсегда |

FTS5 не возвращает удалённые страницы файлу, а WAL постоянного соединения
никто не обрезал. Замерялось копированием живой базы в отдельную папку и
пересборкой индекса по ней шесть раз подряд.

Побочный вред тот же: чтение всей переписки всех сессий на каждый чих держало
event loop занятым, а `prepareVault()` зовётся и при старте, и через три секунды
после каждой пачки правок (`MAP_DEBOUNCE_MS` в `server.js`).

## Решение

**Сборка инкрементальная.** Рядом с FTS живёт обычная таблица `index_state`:
`kind|ref → { rowid, stamp }`. `stamp` — размер и время правки файла, а для
сессии — дата, счётчик реплик и заголовок.

1. Собираем карту «что должно быть в индексе» в памяти (единицы мегабайт).
2. Сравниваем с `index_state`: совпал отпечаток — строка не трогается вообще,
   файл даже не читается, переписка сессии не запрашивается.
3. Разошёлся — старую строку удаляем по сохранённому `rowid`, новую вставляем,
   отпечаток переписываем.
4. Файл или сессия исчезли — удаляем по `rowid` и забываем в `index_state`.

Одна строка кода на случай первого запуска на индексе, собранном прежним
способом: `index_state` пуста, а строки в `docs` уже есть и о них записи нет —
тогда `docs` чистится целиком один раз. Иначе старые строки остались бы
вторыми копиями каждого попадания навсегда.

**Усадка один раз за жизнь процесса.** `compactSearchIndex()` зовёт `VACUUM` при
старте сервера и только если файл больше 64 МБ и свободна больше половины
страниц. Замер на копии живой базы: 837 МБ → 234 МБ за 1.8 с; после того как
индекс пересобран, повторный `VACUUM` даёт те же ~6 МБ. В таймер после правок
усадка не ходит — блокировать event loop там нельзя.

**WAL обрезается после каждой пересборки**, если он больше 8 МБ.

Индекс остался производным кэшем: файл можно удалить, и он соберётся заново.

## Что это дало

| | было | стало |
|---|---|---|
| файл индекса | 837 МБ, растёт на 1.6 МБ за пересборку | ~6 МБ, не растёт |
| пересборка, когда ничего не менялось | 300 мс, читалась вся переписка | ~100 мс, только обход файлов |
| повторная усадка на копии | файл 7.4 → 11.9 МБ за пять пересборок | 5.68 МБ, стабильно |

## Побочно

`npm run check` на этой машине молча ничего не проверял: `checks.js` отдаёт путь
к node в `cmd` без кавычек, а node лежит в `C:\Program Files\nodejs\node.exe`,
и вывод был `'C:\Program' is not recognized`. Обе проверки теперь проходят
по-настоящему — и они чистые.

## Проверено

- Шесть пересборок подряд на копии живых данных: размер индекса не меняется,
  `docs` и `index_state` совпадают по count, строк с потерянным rowid нет.
- `searchProject` отдаёт то же, что и раньше, по трём запросам, включая
  `kind = 'session'`.
- Правка файла (сдвиг времени) переписывает его строку, а не добавляет вторую.
- `npm run check` — чисто; `VACUUM` на копии живой базы — 1.8 с.
- Живой интерфейс не проверялся: новый код в сервере пользователя ещё не
  перезапущен, после перезапуска база сожмётся сама.
