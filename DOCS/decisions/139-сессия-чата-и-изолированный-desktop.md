# Сессия чата и изолированный Linux desktop

## Контекст

Чат-сессия должна работать в отдельном Linux desktop-контейнере с отдельным
home-volume. OpenKarandash не должен получать доступ к Docker daemon напрямую:
жизненным циклом контейнеров владеет `docker_for_desktops`.

## Решение

OpenKarandash хранит связь `chat session -> desktop session -> Git branch` в
своей таблице Sessions и обращается к desktop manager только по HTTP. Manager
выдаёт session-scoped NDJSON `exec` API: каждый запрос сначала проверяет
владельца сессии и managed-container label, а остановка exec дополнительно
проверяет принадлежность процесса тому же контейнеру.

До первого хода OpenCode сессия получает standby-контейнер или новый контейнер;
после подготовки workspace запускается следующий standby. OpenCode и Git
исполняются внутри контейнера, а поток OpenCode JSON-событий проходит через
существующий Sessions stream. GitHub token, если задан, передаётся только как
Git-конфигурация clone/push и не передаётся OpenCode, UI или событиям.

## Последствия

- У каждой чат-сессии свой контейнер, desktop URL, workspace, volume и ветка.
- Удаление чата удаляет контейнер и volume, но не удаляет уже отправленную
  ветку или commit.
- При завершении хода desktop workspace устанавливает зависимости, запускает
  `npm test` и `npm run check`; только после успеха изменения коммитятся и
  отправляются в ветку этой сессии. При включённом `DESKTOP_GIT_PUSH=1`
  создаётся PR в `main` и запрашивается GitHub auto-merge. Ошибка проверки,
  push, GitHub API или запроса auto-merge остаётся ошибкой синхронизации, а не
  успешным статусом. Если desktop image не содержит Node.js 22, перед проверкой
  устанавливается официальный архив Node.js 22 в домашнюю папку контейнера с
  проверкой SHA-256 по `SHASUMS256.txt`.
- GitHub Actions запускает `npm test` и `npm run check` на PR и merge queue.
  Правило `main` требует PR и успешный `project-check`; прямой push в `main`
  запрещён. После слияния отдельный version PR добавляет запись в `VERSION.md`,
  поэтому параллельные сессии не выбирают один номер версии.
- Docker-приложение опрашивает `origin/main`; после появления записи версии оно
  уведомляет интерфейс, блокирует новые ходы, дожидается освобождения активных
  ходов и выполняет только fast-forward. Изменения не подтягиваются в рабочие
  копии сессий. Грязная/не-main/расходящаяся deployment-копия и изменение
  зависимостей блокируют автоматическое обновление; файлы не перезаписываются,
  а причина показывается пользователю. Для изменения зависимостей нужен новый
  Docker image.
- Репозиторий и секреты остаются конфигурацией окружения; реальные значения не
  входят в Git.
- GitHub token передаётся только Git и API создания PR; он не передаётся
  OpenCode, интерфейсу или событиям.

## Пересмотр

Решение следует пересмотреть, если desktop manager перестанет быть единственным
владельцем Docker-контейнеров или потребуется общий workspace для нескольких
чат-сессий.
