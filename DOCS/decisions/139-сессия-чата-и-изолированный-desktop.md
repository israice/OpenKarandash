# Сессия чата и изолированный Linux desktop

## Контекст

Чат-сессия должна работать в отдельном Linux desktop-контейнере с отдельным
home-volume. OpenKarandash не должен получать доступ к Docker daemon напрямую:
жизненным циклом контейнеров владеет `docker_for_desktops`.

## Решение

OpenKarandash хранит связь `chat session -> desktop session -> Git branch` в
своей таблице Sessions и обращается к desktop manager только по HTTP. Manager
выдаёт session-scoped NDJSON `exec` API: каждый запрос сначала проверяет
владельца сессии и managed-container label, а остановка exec дополнительно
проверяет принадлежность процесса тому же контейнеру.

До первого хода OpenCode сессия получает standby-контейнер или новый контейнер;
после подготовки workspace запускается следующий standby. OpenCode и Git
исполняются внутри контейнера, а поток OpenCode JSON-событий проходит через
существующий Sessions stream. GitHub token, если задан, передаётся только как
Git-конфигурация clone/push и не передаётся OpenCode, UI или событиям.

## Последствия

- У каждой чат-сессии свой контейнер, desktop URL, workspace, volume и ветка.
- Удаление чата удаляет контейнер и volume, но не удаляет уже отправленную
  ветку или commit.
- Push включается явно через `DESKTOP_GIT_PUSH=1`; без него commit остаётся в
  workspace и получает статус `committed`.
- Репозиторий и секреты остаются конфигурацией окружения; реальные значения не
  входят в Git.
- Неразрешённая автоматическая проверка не должна приводить к merge в main;
  текущий слой фиксирует commit/push и состояние sync, а policy merge остаётся
  отдельным владельцем GitHub-интеграции.

## Пересмотр

Решение следует пересмотреть, если desktop manager перестанет быть единственным
владельцем Docker-контейнеров или потребуется общий workspace для нескольких
чат-сессий.
