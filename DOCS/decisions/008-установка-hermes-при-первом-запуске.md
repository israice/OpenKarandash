# Hermes ставится сам при первом запуске

**Решение.** Пользователь клонирует репозиторий и запускает сервер — дальше ничего делать руками не нужно: сервер сам скачивает Hermes на зафиксированный коммит, ставит ему окружение Python и пишет проектный конфиг. Установка идёт в фоне, ход виден на вкладке Hermes. Остаётся один шаг человека — выбрать провайдера в настройках.

**Почему не `setup-hermes.sh` из самого Hermes.** Он кладёт venv в одно место (`<репозиторий>/venv`) и правит PATH пользователя. Нам нужны **два независимых окружения** — Windows и WSL: бинарники Python несовместимы, а папка проекта одна и открывается из обеих систем. Поэтому окружения лежат в `SYSTEM/Hermes/runtime/win/` и `SYSTEM/Hermes/runtime/wsl/`, и запуск из любой системы находит своё. PATH пользователя не трогаем вовсе: сервер зовёт бинарник по полному пути.

**Что где лежит.**

| Что | Где | В git |
|---|---|---|
| Сам Hermes | `SYSTEM/Hermes/agent/` | нет, ~250 МБ |
| Коммит, на который он ставится | `SYSTEM/Hermes/AGENT-PIN.txt` | да |
| Окружение Python | `SYSTEM/Hermes/runtime/<win\|wsl>/venv/` | нет |
| Лог установки | `SYSTEM/Hermes/runtime/<win\|wsl>/setup.log` | нет |
| Путь, по которому собрано окружение | `SYSTEM/Hermes/runtime/<win\|wsl>/venv-path.txt` | нет |

**Окружение не переносится вместе с папкой.** Внутри venv абсолютные пути: shebang'и в `bin/`, ссылки редактируемой установки, launcher'ы Windows. После переезда папки файлы на месте и `hermes` даже находится, но запуск падает на `bad interpreter` — по этой ошибке причину не угадать. Поэтому рядом с окружением лежит путь, по которому его собрали: не совпал (или метки нет вовсе) — установка считает окружение негодным, сносит его и собирает заново. Проверяется в `venvMoved()`; сам агент и конфиг при этом не трогаются, заново идёт только `uv venv` и установка зависимостей.
| Состояние и конфиг Hermes | `DATA/hermes/` (`HERMES_HOME`) | нет |
| Ключи API | `.env` проекта | нет |

`uv` — единственное, что ставится вне проекта (`~/.local/bin`): это менеджер окружений, держать его копию в каждом проекте незачем. Если он уже есть, установщик берёт готовый.

**`journal_mode: delete` в конфиге Hermes — не перестраховка.** Hermes держит состояние в SQLite, а папка проекта видна из WSL через `/mnt/c`, где drvfs не даёт разделяемую память для WAL: на том же месте уже спотыкался индекс самого проекта («disk I/O error»). Без этой строки установка проходит, а первый запуск падает.

**Установку Hermes не обходят те, кто ходит по дереву проекта** — ни сторож файлов в `server.js`, ни сборщик карты в `PROJECTS/Graph/graph-server.js`. Общий список — `SYSTEM/core/scan.js`. Без этого сервер на Windows падал на старте: сторож заходил в WSL-окружение и спотыкался о symlink `runtime/wsl/venv/bin/python`, который с Windows не читается (`EACCES`). Заодно обходчики перестали разбирать 250 МБ чужого кода. Отдельно от списка обход стал терпимым к нечитаемым файлам: битая ссылка или занятый файл теперь пропускаются, а не роняют процесс.

Проверить это смоуком «как обычно» нельзя: сторож поднимается только без `NO_RELOAD=1`, а смоук запускает сервер именно с ним. Поэтому в смоуке лежит прямая проверка списка — единственная, которой сервер не нужен.

**Признак готового окружения — интерпретатор, а не папка.** Установку могли оборвать посреди `uv venv`: папка тогда есть, а работать в ней нечем, и следующий запуск честно её пересоздаёт.

**Идемпотентность.** Каждый шаг проверяет, сделан ли он. Повторный запуск на готовой установке не делает ничего. Установку могут запросить одновременно старт сервера и кнопка в интерфейсе — второй вызов подключается к идущей через `installOnce()`, а не начинает вторую.

**Смоук ставить ничего не должен.** `SYSTEM/smoke.js` поднимает сервер с `HERMES_AUTOINSTALL=0`: проверка обязана проходить одинаково быстро и без интернета. Той же переменной установка отключается и у пользователя.

**Чем платим.** Первый запуск на чистой машине тянет из сети около полугигабайта и занимает несколько минут. Взамен исчезает инструкция по установке — и вместе с ней все способы выполнить её неправильно.

**Ключ провайдера — в `.env` самого Hermes** (`DATA/hermes/.env`), а не в проектном. Это место, откуда он их читает (`hermes_cli/env_loader.py`), и оно тоже внутри `DATA/`, то есть вне git. Дублировать секрет в проектный `.env` не стали: два файла — это два места, где его забудут почистить. Ещё одна причина: WSL-цель зовётся строкой для `bash -lc`, и ключ в этой строке был бы виден в списке процессов.

**Проверено.** Установка прогнана целиком в WSL: `hermes --version` запускается из проектного окружения с проектным `HERMES_HOME`, `hermes config set` меняет провайдера и не ломает остальной конфиг. Коннектор проверен отдельно: строка запуска для WSL-цели (та, что сервер на Windows отдаёт `wsl.exe bash -lc`) выполнена как есть — `cd`, `HERMES_HOME` и путь к бинарнику отрабатывают, экранирование переживает одинарную кавычку и `$(...)` внутри задания, отчёт `--usage-file` пишется. Нативная установка на Windows (`runtime/win`) написана, но не прогонялась — здесь нет Windows-хоста.
