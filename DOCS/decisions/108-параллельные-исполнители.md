# Параллельные исполнители: своя ветка, свой файловый фронт

## Решение

При двух и более одновременно работающих исполнителях в одном проекте действуют правила:

1. Каждый работает на своей ветке с уникальным именем. Имя строится как `agent-<короткое-имя-исполнителя>-<тема>`. Запрет на работу из `main` и из ветки другого исполнителя.
2. Каждый выбирает очереди задач, над которыми не работает никто другой. Делить работу следует по границам файлов и ответственности до начала правок, а не по ходу.
3. Проверка завершённости задачи внутри своей ветки (тип-чек, `npm run check`, живой `ui`-walk) — обязательное условие слияния в `main`.
4. Слияние в `main` — только через ветку ответственного исполнителя; версия в `VERSION.md` и заголовок коммита должны быть уникальны (`node TOOLS/next-numbers.js` — для номера записки).
5. Два исполнителя не пишут на одни и те же файлы на одном шаге; если разделить фронт нельзя — один из них переходит на другой фронт.

Правило добавлено в `DOCS/agents/конвенции.md` как строкая норма.

## Почему

Случай 2026-10-05/06: две сессии одновременно выполняли перенос разметки вкладок в шаблоны (`v0.0.161`–`v0.0.167`); каждая оставила свои записи в `VERSION.md`/`CHECKPOINT.md`, записки с одинаковым номером `106`, удаления файлов в worktree и эксперименты с `package.json`. Итог потребовал ручного разбора состояния. Смысл механизма — чтобы это не повторялось.

## Чем платим

- Единица работы становится крупнее: исполнитель должен сперва заявить ветку и границу работ.
- Одна очередь на одного: parallelize по пересекающимся связкам нельзя — теперь один закрывает фронт полностью, потом следующий.
- Для маленьких однофайловых правок выгоднее работать одиночно: строить ветку на одну строку тяжело.

Связано: `DOCS/decisions/017` (маршруты у фич), записки 001 (один порт/копия), 002 (сервер не из сессии).
