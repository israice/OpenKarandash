# Память навыков работника: приёмы копятся в каталоге профиля

## Решение

У каждого профиля есть `memories/skills.md` — приёмы, которые уже сработали. Агент дописывает запись **в конце задачи**, тем же шагом, что и `npm run check` (`DOCS/decisions/034`), и читает файл **в начале** похожего задания.

Запись — четыре поля, и все обязательны по смыслу:

| Поле | Зачем |
|---|---|
| **Когда применим** | без этого приём не найти в нужный момент |
| **Что делать** | сам приём, конкретными командами |
| **Чем подтверждён** | доказательство, что он и правда сработал |
| **Записано** | дата и сессия — видно, насколько опыт свежий |

Серверная половина — `PROJECTS/Flow/profiles-server.js`, подключается из `flow-server.js` (`017`: `server.js` не знает про устройство фич). Маршруты: `/api/flow/profiles` (список работников и объём их опыта), `/api/flow/profile/memory` (прочитать), `/api/flow/profile/memory/add` (дописать). Имя профиля приходит с клиента и становится путём, поэтому пропускается только простое имя существующей папки — без разделителей и `..`.

Файл нарочно обычный markdown, а не таблица в базе: его читает и человек, и модель, и Hermes, которому каталог профиля скармливают целиком. Он версионируется вместе с кодом — под профилями `.gitignore` ловит только runtime-файлы (`auth.json`, `sessions/`, `npm/`, `git/`), а опыт работника — часть проекта.

## Почему в каталоге профиля, а не в общей памяти

Памятей в проекте уже две, и у каждой своя область: `DATA/vault` — знание о самом проекте (файлы, связи, прошлые сессии, `AGENTS.md`), beads — задачи и заметки по ним. Ни та, ни другая не отвечают на вопрос «как **этот работник** обычно решает такую задачу»: опыт роли принадлежит роли, а профиль — это уже каталог агента (`028`, `033`). Класть его в общую память значило бы смешать опыт QA и бэкендера, а заводить третью базу — плодить систему там, где хватает файла в уже существующей папке.

## Чем платим

Память не доезжает до запуска сама. Настоящие ходы идут на цели, настроенной по умолчанию, а не через профиль — `askHermes` в `server.js` профиль не принимает (`033` документирует тот же разрыв для pi). Значит сегодня приём попадает в работу, только если агент прочитает файл сам. Автоматическое подмешивание памяти профиля в запрос (по образцу `handoffPreamble`) — следующий шаг, и он требует, чтобы клиент передавал имя профиля в `/api/agent/ask`.

Ценность записи держится на честности: приём стоит писать, только если он проверен. «Наверное, помогает» засоряет память быстрее, чем приносит пользы, — поэтому поле «чем подтверждён» и обязательно.
