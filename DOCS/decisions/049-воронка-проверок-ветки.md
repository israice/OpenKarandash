# Воронка проверок ветки: дешёвое раньше дорогого, и до рецензента доходит не всё

## Решение

Ветка исполнителя проходит проверки от самой дешёвой к самой дорогой, и упавшая на дешёвом шаге до следующего не доходит:

1. **машинная** — `npm run check` на рабочей копии ветки;
2. **интерфейс** — если ветка трогает клиент: прогон её предпросмотра `/branch/<ветка>/` (`DOCS/decisions/042`, `048`);
3. **дешёвый рецензент** — профиль `reviewer` через `hermes-home/bin/handoff` (`DOCS/decisions/031`);
4. **дорогой проверяющий** — только для ветки, принятой дешёвым, и только на рискованной правке.

Шаги 1–2 — одна команда `npm run gate -- <ветка> [--json]` (`SYSTEM/branch-gate.mjs`). Она никого не зовёт и ничего не решает за оркестратора: говорит, дошла ли ветка до рецензента, отдаёт список правок и причину отказа. Шаги 3–4 зовёт Hermes — оркестрация живёт в нём (`DOCS/decisions/040`), пульт своей очереди проверок не заводит. Порядок Hermes знает из скилла `hermes-home/skills/devops/branch-review-funnel/SKILL.md`. Папка `hermes-home/` в git не хранится, поэтому текст скилла при переустановке восстанавливается по этой записке.

Коды выхода `gate`: 0 — к рецензенту, 1 — на доработку, 2 — проверять нечего (нет рабочей копии или правок), 3 — машинная пройдена, но интерфейс отсюда не проверить.

**Уборка** — `npm run branches` (`SYSTEM/branch-sweep.mjs`): список веток исполнителей с состоянием; `--prune-merged` снимает влитые, `--prune-stale N` — непринятые без коммитов N и более дней, `--only <ветка>` (можно повторять) ограничивает снятие названными. Без флагов ничего не трогает.

## Почему так

- **Проверяющий скрипт берётся из главной копии**, а не из ветки: иначе ветка могла бы пройти проверку, ослабив `SYSTEM/checks.js` у себя. Инструменты (`eslint`, `madge`) тоже из главной — в рабочей копии `node_modules` нет; для этого `checks.js` получил `--root <папка>`. Конфиг `eslint` при этом ветки: набор публикуемых имён (`APP_GLOBALS`) ветка вправе менять.
- **Ветка без `eslint.config.mjs` отбивается сразу** («старше проверок»): иначе `eslint` поднимается к конфигу главной копии, где `.worktrees/**` в игноре, и «проверка» проходит, не посмотрев ни одного файла.
- **Код 3 — не провал и не успех.** Hermes живёт в контейнере: машинная проверка оттуда работает, а сервер пользователя отвечает только локальным запросам, и браузера там нет. Молча пропустить шаг — значит отдать рецензенту ветку с непроверенным интерфейсом; поэтому команда требует повторить себя на хосте (claude через мост).
- **Уборка не снимает**: `main`, копию с незакоммиченными правками (и `git worktree remove` зовётся без `--force` — вторая страховка), ветку без рабочей копии (её завёл человек) и только что заведённую пустую ветку — у неё вершина совпадает с `main`, формально она «влита», но под ней работает исполнитель.

## Чем платим

Прогон интерфейса видит клиентскую половину ветки; правку сервера предпросмотр не показывает (`042`) — в этом случае `gate` пишет рецензенту, что смотреть надо код. Что считать «рискованной» правкой для шага 4, решает Hermes по скиллу, а не правило в коде.

## Что проверено

На временной ветке, заведённой от `main`: безвредная правка клиента — оба шага пройдены, код 0; обращение к неизвестному имени — отбито машинной проверкой, код 1; падение в браузере, которое `eslint` пропускает, — отбито прогоном интерфейса, код 1; старая ветка без конфига — код 1; несуществующая — код 2; из контейнера Hermes `checks.js` работает, прогон интерфейса отдаёт код 3. Уборка проверена на трёх временных ветках через `--only` (фильтр добавлен затем, чтобы снятие можно было ограничить названными ветками): влитая и непринятая 48-дневная сняты, ветка с незакоммиченными правками и все чужие — оставлены. Вызов воронки самим Hermes проверен: на просьбу принять ветку `bd-OpenKarandash-7yx` он нашёл скилл, запустил `npm run gate -- bd-OpenKarandash-7yx --json`, получил отказ на машинном шаге и рецензента не позвал (сессия `hermes-docker-mu7y84dv`).
