# 110. Скриншот уменьшается целиком, а не вырезается углом

**Стандарт:** ISO/IEC 25010 (функциональность — соответствие заявленной функциональности
программного средства). Отдельно к размеру ответа — `OWASP ASVS V5` (проверка ввода и
ограничение размера принимаемых данных).

## Проблема

Замена PowerShell на `node-screenshots` (версия 0.0.165, записка не заводилась) вернула
не то поведение, которое было до неё. Прежний код на `System.Drawing` делал
`Bitmap($full, $w, $h)` — это **масштабирование**. Новый код сохранил имя
`SCREENSHOT_WIDTH` и ту же формулу высоты, но сменил смысл операции: у `node-screenshots`
resize нет вообще, и вместо него остался `crop`, а `crop(0, 0, 480, h)` **вырезает
прямоугольник из левого верхнего угла**.

Итог: миниатюра сессии — это угол экрана, а не экран, сжатый до 480 px. Доля кадра зависит
от монитора: на 1920×1080 остаётся 1/16 площади, на 3840×2160 — 1/64.

Проверено в `index.d.ts` пакета: у `Image` есть только `crop*`, `toPng*`, `toJpeg*`,
`toBmp*`, `toRaw*`. Метода масштабирования нет.

## Что решало неправильно

Вариант «оставить полный кадр и уменьшить его в CSS» — не компромисс, а поломка, и
проверяется числом, а не мнением. Превью принимает `/api/sessions/thumb`
(`SYSTEM/core/sessions-routes.js`), который отклоняет строку длиннее `MAX_THUMB_BYTES`
(300 КБ). Замер полного кадра в data-URL на трёх мониторах машины владельца:

| монитор | разрешение | полный кадр (data-URL) | влезает в 300 КБ | угол (было) |
|---|---|---|---|---|
| C27F390 | 1920×1080 | 331 683 Б | **нет** | 25 487 Б |
| SAMSUNG (primary) | 3840×2160 | 689 143 Б | **нет** | 10 575 Б |
| DELL P2314H | 1920×1080 | 134 395 Б | да | 9 183 Б |

То есть на двух мониторах из трёх превью не сохранилось бы **вообще** — не «дороже», а
никак. Вариант отпадает целиком.

## Решение

`sharp` добавлен в зависимости, версия запинена точно (`0.35.5`). Снимок идёт
`node-screenshots` (захват) → PNG кадра → `sharp` (уменьшение по ширине до
`SCREENSHOT_WIDTH`, `withoutEnlargement`) → JPEG качества 80 → base64 `data:` URL.

Порядок именно такой: кадр сначала кодируется без потерь (PNG), потом **одна**
перекодировка в JPEG. Кодировщик сам выбирает DCT-масштаб, и картинка не мылится
двойным сжатием.

## Почему не остальные варианты

| вариант | почему не он |
|---|---|
| откатить PowerShell + `System.Drawing` | возвращает эвристику антивируса (`ScriptContainedMaliciousContent`), ради устранения которой миграция и делалась |
| писать PNG-энкодер вручную (~150 строк) | новая рукописная работа с бинарным форматом в проекте, и бюджет 300 КБ у PNG на 480×270 не гарантирован — то есть неопределённость вместо зависимости |
| оставить `crop` как есть | миниатюра показывает не то, что снято; тихая неправильность поведения |

Зависимость обоснована по `DOCS/decisions/004` и правилу в `DOCS/agents/конвенции.md`:
убирает существенный объём своего кода, версия запинена точным номером, лок-файл
коммитится. `sharp` для Windows приезжает готовым бинарником — сборочные инструменты
не нужны.

Два нативных модуля подряд — не избыточность, а разные половины работы: `node-screenshots`
не умеет масштабировать, `sharp` не умеет снимать экран.

## Что проверено

- `captureScreenshot()` вызван напрямую на всех трёх мониторах: результат **480×270
  JPEG** на каждом, 28 703 / 22 711 / 12 375 Б — втрое меньше прежнего угла на 4K и
  втрое больше на 1920×1080, где угол был 25 487 Б, то есть это **другой кадр**, а не
  тот же поменьше.
- Содержимое проверено попиксельно, а не по размеру: углы и центр результата
  (`42,53,59` / `11,15,26` / `165,167,164` на первом мониторе) — осмысленные цвета
  содержимого экрана по всей площади, а не пустое поле. MD5 результата не совпадает с
  MD5 `crop` того же кадра ни на одном мониторе.
- Живой сервер (сторож перезапустил его сам): `POST /api/screenshot` отдаёт 28 703 Б —
  байт в байт как прямой вызов функции, то есть маршрут и страница новый код.
- Заведомо неверный индекс монитора (`99`) → `null`, контракт не изменился.
- `npm run check` — EXIT=0, `npm run ui` — замечаний нет.
- Размер результата заведомо меньше `MAX_THUMB_BYTES` на всех трёх мониторах, то есть
  отказ по размеру из-за этой правки больше не воспроизводится.

## Границы

- `SCREENSHOT_QUALITY = 80` подобран на глаз по размеру результата (12–29 КБ при
  пределе 300 КБ) — запас большой, но это не измерение впечатлений, а факт с числами.
- `npm audit` показывает одну high-advisory в `source-map-js` — она пришла **не** от
  `sharp`, а из `madge` → `dependency-tree` → `postcss` в `devDependencies`, то есть
  в код приложения не попадает. Проверено `npm ls source-map-js`. Не чинил: правка
  чужой транзитивной зависимости — отдельная задача.
