# 029. Hermes в Docker подключается к Claude через claude-bridge, а не через ANTHROPIC_API_KEY

Цель — дать серверу доступ ко всему потенциалу Hermes (память, скиллы, крон,
суб-агенты) под тем же UI, которым уже пользуется этот проект, не заводя
отдельного биллинга поверх уже оплаченной подписки Claude Code.

## Решение

- `hermes/` — `hermes-agent` (NousResearch) в нашем git **не хранится** ни
  файлами, ни submodule (`/hermes/` в `.gitignore`): это чужой код, его берёт с
  публичного GitHub сам сторож при старте — нет папки → `git clone --depth 1`,
  есть → `fetch` + перестановка на свежий коммит, если дерево чистое (свои
  правки внутри `hermes/` не затираются, о них пишется в консоль). Репозиторий
  и ветка/тег — `HERMES_REPO`/`HERMES_REF` в `.env` (по умолчанию апстрим,
  `main`). В git остаются только наши настройки к нему:
  `docker-compose.hermes.yml`, `hermes-home.config.example.yaml`,
  `.env.example`, `claude-bridge/`. Раньше был submodule на закреплённом
  коммите — от него отказались, чтобы репозиторий не тянул чужой код и
  обновлялся без ручных действий.
- `hermes-plugins/model-providers/claude-bridge/` — наш провайдер Hermes
  (профиль `claude-bridge`, chat_completions на адрес из `CLAUDE_BRIDGE_URL`).
  Раньше лежал внутри `hermes/` локальным коммитом поверх апстрима и пропал
  при первом же обновлении на апстрим — Hermes тогда не знал провайдера,
  молча брал «custom» и отвечал «API call failed after 3 retries: Connection
  error». Теперь он в репозитории и монтируется compose-оверлеем в штатное
  место пользовательских провайдеров `$HERMES_HOME/plugins/model-providers/`
  (`providers/__init__.py` в Hermes), образ пересобирать не нужно.
- В `config.yaml` только `${CLAUDE_BRIDGE_URL}`: shell-синтаксис
  `${ИМЯ:-значение}` Hermes не разворачивает и оставляет строку как есть.
- `claude-bridge/` — OpenAI-совместимый HTTP-шим (`/v1/models`,
  `/v1/chat/completions`) поверх уже установленного `claude` CLI. Живёт **на
  хосте**, не в контейнере — он сам управляет CLI, который стоит на хосте.
  Готовый рабочий код (не написан с нуля): исчерпывающий `--disallowed-tools`,
  эмуляция tool-calling через системный промпт, картинки, стриминг. Подробности
  и измерения — `claude-bridge/README.md`.
- Hermes поднимается в Docker (`docker-compose.hermes.yml` поверх
  `hermes/docker-compose.yml`). Поднимает его сторож `server.js` через
  `SYSTEM/core/hermes-stack.js`, поэтому команда запуска одна и та же в
  PowerShell и WSL — `node server.js`. До первого запуска дочернего сервера
  (синхронно) он проверяет и чинит зависимости: npm по `package.json`,
  `hermes/` по апстриму GitHub, образ Hermes — при смене коммита
  `hermes/` (метка `hermes-home/.image-built-from`), дописывает в
  `.env`/`claude-bridge/.env` недостающие ключи с генерированными секретами.
  Затем параллельно с сервером поднимает бридж (`python`/`python3`) и
  `docker compose up -d gateway`. Мост гоняет **тот же `claude`, что выбран в
  Settings** (WSL или Windows), а не «свой для платформы»: стартовая цель —
  `CLAUDE_BRIDGE_TARGET` из `claude-bridge/.env`, а подключение Claude в
  интерфейсе шлёт сторожу id цели по IPC, тот перезапускает мост под неё и
  записывает выбор в `claude-bridge/.env`. С Windows-хоста WSL-копия зовётся
  так же, как в `server.js`: `wsl.exe -e bash -lc 'exec claude "$@"'`.
  Системный промпт Hermes (десятки тысяч символов вместе со схемами
  инструментов) уходит в CLI не аргументом, а файлом `--system-prompt-file`:
  на Windows командная строка ограничена ~32k, и `claude.exe` падал с
  «WinError 206». Файл кладётся в `DATA/bridge-tmp/` — общий диск виден и
  WSL-, и Windows-копии, путь переводится под цель (`C:\…` ↔ `/mnt/c/…`). Только
  `gateway` — дашборд Hermes (`:9119`) не нужен, интерфейсом служит наш сервер.
  `Ctrl+C` гасит всё разом: сторож перед выходом синхронно делает
  `compose down` и убивает бридж. Нет Docker или python — сервер всё равно
  стартует, без Hermes. `HERMES_STACK=0` в `.env` выключает стек целиком.
  `hermes-start.sh`/`hermes-stop.sh` остаются как ручной путь для WSL. Контейнер видит
  бридж через `host.docker.internal:8787` (не `network_mode: host` и не
  `127.0.0.1` — под Docker Desktop «host» означает сеть VM самого Docker, а не
  машину WSL/Windows).
- Внутри контейнера Hermes сам поднимает свой OpenAI-совместимый agent API
  (порт 8642, ключ в `API_SERVER_KEY`) — это ПОЛНЫЙ агент со своими
  инструментами и памятью, а не голая модель. Поэтому коннектор `server.js`
  (`OpenKarandash-ykb.4`) будет ходить именно сюда обычным HTTP, а не
  реализовывать ACP JSON-RPC по stdio — тот путь сложнее и не даёт ничего
  сверх того, что уже отдаёт agent API.
- В интерфейсе Hermes не виден вовсе — он под капотом. Пользователь выбирает
  и подключает в Settings обычный Claude (WSL или Windows); `askClaude` в
  `server.js` перед запуском CLI спрашивает `hermesReady()` — отвечает ли
  agent API, поднятый сторожем, — и если да, ход ведёт агент Hermes
  (`askHermes`), а мозгом ему служит тот же подключённый claude через мост.
  Агента нет (`HERMES_STACK=0`, Docker выключен) — прямой claude, как раньше.
  Модель и effort из шапки сессии под Hermes не действуют: модель задаёт его
  конфиг (`hermes-home/config.yaml`).
- `claude` CLI остаётся вне Docker (Windows/WSL, как и раньше) — только он
  трогает подписку.
- Сам `server.js` тоже остаётся на хосте, а не в контейнере (задача
  `OpenKarandash-ykb.6` отложена): он напрямую спавнит CLI `claude`, `codex`,
  `opencode`, `pi` и бинарь доски Kanban, а из контейнера ни один из них не
  виден. Переезд лишил бы всех хостовых коннекторов, оставив только путь
  через Hermes. «Одна команда» достигается скриптом, а не контейнером.

## Ctrl+C на Windows слушается с клавиатуры, а не только сигналом

`wsl.exe` (его запускает сервер для WSL-claude и мост для каждого хода)
переводит консоль в сырой режим, а убитый посреди работы (Stop, конец хода,
перезапуск) не возвращает его: консоль перестаёт превращать Ctrl+C в событие,
и сторож живёт вечно. Программный `GenerateConsoleCtrlEvent` при этом
проходит, поэтому проверка им ничего не показывала. Сторож на Windows держит
stdin в сыром режиме и ловит байт 0x03 сам, переустанавливая режим раз в
секунду (следующий `wsl.exe` снова собьёт его); обработчики SIGINT/SIGTERM
остаются для сигналов снаружи.

## Зависимости хоста ставятся сами

`SYSTEM/core/host-deps.js`, зовётся сторожем до `hermes-stack.prepare`. Цель —
чтобы скачавший репозиторий запустил `node server.js` и сразу работал:

- git, python 3.10+, Docker — проверяются; чего нет, ставится штатным
  установщиком платформы: winget на Windows (`Git.Git`, `Python.Python.3.12`,
  `Docker.DockerDesktop`), `sudo apt-get` в WSL/Linux (`git`, `python3`,
  `docker.io` + `docker-compose-v2`, пользователь добавляется в группу docker).
  В WSL при наличии Docker Desktop на Windows движок не ставится — используется
  клиент WSL-интеграции, а сам Desktop запускается через `cmd.exe /c start`.
  Не запущенный демон запускается (Docker Desktop / `service docker start`) и
  ждётся до 150 с. Установщики идут с `stdio: inherit`: пароль sudo и окно UAC
  видны в терминале пользователя. PATH процесса после установки перечитывается
  из реестра (Windows) или дополняется `~/.local/bin` (Linux) — иначе сторож и
  дочерний сервер не увидели бы только что поставленное.
- claude CLI: проверяется цель из `CLAUDE_BRIDGE_TARGET` (выбор в Settings),
  затем родная для хоста, затем вторая (с Windows в WSL — `wsl.exe -e bash
  -lc`, из WSL на Windows — `powershell.exe`). Нет ни одной — ставится
  официальным установщиком (`claude.ai/install.sh` / `install.ps1`) на
  предпочтительную. Вход проверяется `claude auth status` (JSON `loggedIn`);
  не залогинен — `claude auth login` запускается в этом же терминале.
- Найденная цель уходит дочернему серверу в `CLAUDE_AUTOCONNECT`, тот
  подключает её сам при старте (`autoConnectClaude`) и отдаёт страницe через
  `/api/agent/status`; страница без сохранённого выбора берёт её и рисует
  подключение. Выбор в Settings по-прежнему главнее.
- Не ставится: Node.js (им запускается сама команда) и остальные CLI из
  Settings (codex, opencode, pi) — они необязательны. `HOST_DEPS=0` в `.env`
  выключает проверку целиком.

## Многошаговые задачи: история вызовов в формате протокола

Разбор последней сессии (`hermes-docker-mtqob5ks`): два шага с инструментами
прошли, а на третьем модель вместо JSON-запроса написала текстом «Tool call:
terminal({...})» по несколько штук, мост это не распознал, Hermes закончил ход
как текстовый ответ, и пользователь получил список вызовов вместо результата.
Причина — мост сам записывал прошлые вызовы в историю именно в таком виде,
и модель его выучила. Теперь прошлые `tool_calls` в истории воспроизводятся тем
же JSON-объектом, что требует протокол (`render_tool_calls`), а старый вид на
всякий случай тоже разбирается (`_parse_drift`), но только если весь ответ
состоит из вызовов. Правка в `claude-bridge/`, действует после перезапуска
моста (перезапуск `node server.js`).

## Ходы Hermes видны по шагам

Раньше `askHermes` ходил в `/v1/chat/completions` и получал только итоговый
текст: сессия из 12 вызовов модели и 11 инструментов выглядела на странице
Sessions как один ответ, и понять, где ход споткнулся, было не по чему.
Теперь разговор идёт через API сессий Hermes
(`POST /api/sessions`, `POST /api/sessions/{id}/chat/stream`): события
`tool.started/completed/failed` пишутся строками шагов (`recordStep`, как у
Claude и pi) и уходят на страницу живьём, а по `run.completed` из расшифровки
хода (`messages`) дописываются результаты инструментов и тексты между
вызовами. Id сессии Hermes — `ok-<наш id>` в `session_cli` под целью
`hermes`; сессии, начатой другим CLI, отдаётся пересказ (`handoffPreamble`).
Заодно в мосте страховка на обрезанный JSON-запрос инструмента (модель
потеряла последнюю скобку на 1,1k символов — ход закончился текстом).

## Что не переносится в репозиторий

- `hermes-home/` — данные конкретного запуска Hermes (сессии, история) не
  копируются: заводится пустой каталог, своя копия для этого проекта.
- Секреты (`CLAUDE_BRIDGE_TOKEN`, `API_SERVER_KEY`, логин/пароль дашборда) —
  только в `.env` (не коммитится), в репозитории — `.env.example` с пустыми
  полями, как и с остальными секретами проекта (`AGENTS.md`, «Конвенции»).
- `claude-bridge/claude-config/` — кеш аккаунта Claude Code для
  экспериментального ACP-бэкенда шима (`CLAUDE_BRIDGE_BACKEND=acp`), содержит
  email и org id владельца подписки. Бэкенд по умолчанию и рекомендованный —
  `cli`, ему этот каталог не нужен.

## Проверено вживую

Сквозной путь подтверждён реальным запросом: `curl` → agent API Hermes
(`:8642`) → `claude-bridge` (`:8788`) → `claude` CLI → настоящий ответ модели.
По ходу проверки всплыли два момента, которые иначе не увидеть по коду:

- Штатный порт бриджа (`8787`) и статичные имена контейнеров (`hermes`,
  `hermes-dashboard` — заданы в `hermes/docker-compose.yml`) конфликтуют,
  если на той же машине уже стоит другой клон Hermes/claude-bridge (например,
  прежний прототип `hermes-using-claude`, из которого сюда перенесён код).
  Поэтому здесь свой порт бриджа по умолчанию — `8788`
  (`claude-bridge/.env.example`, `docker-compose.hermes.yml`), и свои имена
  контейнеров — `openkarandash-hermes` / `openkarandash-hermes-dashboard`.
- Без `hermes-home/config.yaml` со `provider: claude-bridge` свежий Hermes
  поднимается с `provider: auto` и не находит credentials — сообщения падают
  с ошибкой ещё до бриджа. Сторож (и `hermes-start.sh`) сам кладёт `config.yaml` из
  `hermes-home.config.example.yaml` при первом запуске (файл в `hermes-home/`
  не трогает, если он уже есть — не затирает ручные правки).

## Переменные окружения стека

`claude-bridge/.env` — по образцу `claude-bridge/.env.example`. Корневой
`.env` (тот же файл, что уже создаёт себе `server.js` с `PORT`) должен
дополнительно нести: `CLAUDE_BRIDGE_TOKEN` (тот же, что в
`claude-bridge/.env`), `API_SERVER_KEY`, `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`
/ `_PASSWORD` / `_SECRET`, опционально `HERMES_UID`/`HERMES_GID` (по умолчанию
свои `id -u`/`id -g`, на Windows — 1000; сторож подставляет их сам). Полный список —
корневой `.env.example`; руками ничего вписывать не нужно, недостающие ключи
и секреты дописывает сторож при запуске, уже заданные строки он не трогает.

## Почему не ACP-клиент в самом server.js

Изначальный план (пока не проверили, что уже есть у Hermes) — держать в
`server.js` постоянный процесс `hermes acp` и разговаривать с ним по JSON-RPC
(тот же протокол, что использует Zed). От этого отказались, когда нашли, что
Hermes в Docker уже отдаёт готовый OpenAI-совместимый API со всем тем же
функционалом — обычный HTTP-коннектор в стиле уже существующих
(`runClaude`/`runOpenCode`/`runCodex`) сильно проще и ничего не теряет.

## Историю Hermes дотягиваем, а не считаем нашу базу единственной

Наша база — не полная копия разговора: сервер пишет только то, что прошло через
него, и пишет по ходу дела. Свою переписку Hermes ведёт сам, и ход в его сессию
может прийти не от нас: из его дашборда, по его же API, заданием по расписанию.
Такой ход не появлялся в ленте вовсе — в сессии `hermes-docker-mtqx7psv` из
тридцати с лишним записей Hermes у нас было тринадцать, и пользователь видел
обрывок работы вместо целого разговора.

Поэтому перед показом сессии сервер спрашивает у Hermes её переписку целиком
(`GET /api/sessions/<id>/messages`) и дописывает недостающее. Что именно
дописать, решает `SYSTEM/core/hermes-history.js` — он не знает ни про HTTP, ни
про схему базы, поэтому проверяется без запуска сервера.

- Курсор — id сообщения Hermes: он монотонный и остаётся на каждой добранной
  строке в `extra_meta`. У сессий, которые вели до появления дотягивания, таких
  отметок нет — там порогом служит время последней нашей записи, иначе первый
  же проход задвоил бы всю переписку.
- Строка ассистента без текста — это только заявка на инструменты: сам шаг
  покажет строка его результата, второй экземпляр не заводим. Имя и аргументы
  вызова берутся из неё по `tool_call_id` и попадают на строку результата.
- Во время нашего же хода дотягивание молчит: строки шагов в это время пишет
  стрим, и добор дал бы дубли. Молчит оно и когда Hermes не отвечает — открытие
  сессии в чате не должно зависеть от того, поднят ли сейчас контейнер.


## Работа агента должна быть видна, а оборванный ход — продолжаем одним нажатием

Сессия через Hermes выглядела зависшей, даже когда шла: между раундами агент
молчит от тридцати секунд до минуты (каждый запрос поднимает Claude заново и
прогоняет через него всю переписку), а в ленте в это время не меняется ничего.
Отличить это от настоящего обрыва было нечем.

- Строка ожидания получила часы: «думает N с», счёт заново после каждого шага.
  Первые секунды не подписываются, чтобы короткий шаг не мигал цифрой.
- Ход, не дошедший до ответа (последней осталась строка шага или сам вопрос),
  помечается в ленте и продолжается кнопкой вместо ручного «продолжай».
  Признак считается по самой переписке, отдельного поля в базе для этого нет.
- Размышления модели идут через мост: Claude отдаёт их своим типом блока,
  мост собирает и возвращает как `reasoning_content`, сервер пишет строкой
  роли `thinking`. До этого поле размышлений у Hermes пустовало во всех
  записях, и между шагами агента в ленте не было ничего.

## Несуществующий инструмент — это ответ модели, а не тишина

Имя, которого нет среди предложенных, мост раньше молча отбрасывал. Если вызов
был единственным, список вызовов пустел, весь объект уходил человеку текстом, и
ход заканчивался ничем. Хуже того, модель об ошибке не узнавала и звала то же
самое снова: в журнале `process_manage` подряд три хода (07:13:46, 07:13:55,
07:14:01).

- Промах в форме имени — другой разделитель или регистр (`search-files`,
  `Read_File`), одна опечатка — сводится к настоящему инструменту и
  выполняется: вызов исполним, терять его не за что.
- Имя, которому среди предложенных ничего не соответствует, возвращается модели
  словами — `No such tool: … Available tools: …` обычным ответом ассистента,
  который она прочитает следующим ходом. Подгонять «похожее по буквам, но не то»
  нельзя: не тот инструмент хуже честной ошибки.
- Пояснение, написанное перед таким вызовом, сохраняется над этой строкой —
  замечание дописывается к сказанному, а не заменяет его.

## Правку моста подхватывает сторож, а не пользователь руками

Мост — питон-процесс, и его код Node не перечитывает: правка `claude-bridge/*.py`
вступала в силу только после того, как пользователь гасил весь стек (Ctrl+C и
заново). Хук «перезапусти в конце хода» тут не годится — поднимать сервер из
сессии запрещено (`AGENTS.md`, хук `no-bg-server.js`): сторож и дочерний процесс
переживут сессию и займут папку с базой.

Поэтому за файлами моста следит тот же сторож, тем же опросом mtime, что и за
серверными файлами, — но реакция другая: перезапускается **один мост**, сервер и
Hermes не трогаются. Это безопасно ровно потому, что мост уже дочерний процесс
сторожа, которого поднял пользователь: своей жизни после сессии у него нет.

- Перезапуск живёт в `SYSTEM/core/hermes-stack.js` (`restartBridge`) — тем же
  кодом переключается цель claude из Settings, отдельной копии для сторожа нет.
- Сломанная правка мост не роняет: файл, который не проходит `py_compile`, не
  подхватывается, прежняя версия продолжает работать — как сторож не подхватывает
  непарсящийся `server.js`.
- Пока перезапуск идёт, следующий замер второй не запускает, а ошибка перезапуска
  пишется в консоль и сторожа не роняет.
- Мост, поднятый не сторожем (переиспользован чужой), не трогается — про него
  пишется предупреждение.
