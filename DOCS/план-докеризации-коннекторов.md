# План переноса server.js в Docker: общий host-мост для CLI-коннекторов

Записка ведёт многоэтапную задачу «упаковать весь проект в docker compose up»
(вариант 2 из обсуждения: CLI остаются на хосте, контейнер стучится в мост).
Каждый следующий этап делается новой сессией, чтобы не тащить весь разбор
кода в одном разговоре — читать эту записку вместо переразведки.

## Этап 1 (сделано) — дизайн общего моста

### Что уже спавнится в server.js — все пять точек одной формы

`runClaude`, `runOpenCode`, `runCodex`, `runPi` (server.js) и скриншот Karandash
(`PROJECTS/Karandash/karandash-server.js`, spawn `powershell.exe`) — везде одна
и та же форма: `spawn(cmd, args)`, построчное чтение stdout (`onLine`),
сбор stderr, таймаут, kill дерева процессов (`killProcessTree`, работает и
через `wsl.exe` по PID-маркеру `REMOTE_PID_MARK`, и через `taskkill` на
Windows). Claude уже получил мост (`claude-bridge/`, решение `029`) — но это
OpenAI-совместимый шim специально для Hermes, три остальных CLI и скриншот в
Hermes не ходят вообще, им OpenAI-обёртка не нужна — нужен голый удалённый
exec.

### Вывод: не пять мостов, а один универсальный exec-мост

Один небольшой HTTP-сервис на хосте (рабочее имя `exec-bridge/`, рядом с
`claude-bridge/` в корне репозитория) с четырьмя ручками:

- `POST /exec` — тело `{ cmd, args, input, env, timeoutMs }` (уже собранные
  `server.js`-ом — весь код выбора цели/wsl.exe/shellLaunch остаётся на
  стороне сервера, мост ничего не знает про Claude/OpenCode/pi конкретно).
  Возвращает `{ runId }`, процесс стартует сразу.
- `GET /exec/:runId/stream` — `text/event-stream`, одна строка stdout — одно
  SSE-событие (то же самое, что сейчас `onLine`), в конце событие `done` с
  кодом выхода, stderr и текстом ошибки.
- `POST /exec/:runId/kill` — то же самое, что `killProcessTree` сейчас: если
  запуск был `viaShell`, мост убивает по PID-маркеру внутри WSL, иначе валит
  дерево процессов хоста.
- `GET /health` — есть у `claude-bridge`, авторизация тем же заголовком с
  общим токеном (`EXEC_BRIDGE_TOKEN`, по образцу `CLAUDE_BRIDGE_TOKEN`).

### Что меняется в server.js — только точка входа `spawn`, не логика коннектора

`runClaude`/`runOpenCode`/`runCodex`/`runPi` внутри себя не меняются вообще —
меняется только то, что стоит за вызовом `spawn(...)`: при контейнерном
запуске (флаг `EXEC_MODE=remote` + `EXEC_BRIDGE_URL=http://host.docker.internal:<порт>`)
этот единственный вызов подменяется HTTP-клиентом к мосту с тем же внешним
контрактом (Promise, `onLine`, `onSpawn`, таймаут) — `askClaude`, `askOpenCode`,
`askCodex`, `askPi` и вся таблица `AGENTS` в `server.js` не видят разницы.
Bез контейнера (`EXEC_MODE` не задан) — прежний локальный `spawn`, поведение
на голом хосте не меняется.

Скриншот Karandash технически такой же спавн+сбор stdout, поэтому пойдёт
через тот же клиент бесплатно — отдельного протокола ему заводить не нужно,
достаточно завести вызов через тот же exec-мост, когда до него дойдёт очередь
(изначально в плане это был отдельный пятый этап — по факту он не отдельный:
достаточно, чтобы exec-мост уже был поднят к тому моменту).

### Порядок следующих этапов (не менять без причины)

2. **Сделано.** `exec-bridge/` со всеми четырьмя ручками, `EXEC_MODE`/клиент
   (`execViaBridge`) в `server.js`, подключён `runOpenCode` (решение `037`).
3. Проверить пилот живым ходом: контейнерный `server.js` → мост → `opencode`
   CLI на хосте → настоящий ответ модели (как в `029` проверяли claude-bridge).
4. По подтверждённому клиенту подключить `pi` и `codex` (Codex — только
   connect, чат ещё не реализован, см. `askCodex` в `server.js`, — мост тут
   не блокер, просто нечего гонять чатом до отдельной задачи на сам Codex-чат).
5. Скриншот Karandash — через тот же exec-мост, отдельного протокола не
   заводить.
6. Dockerfile для самого `server.js` (образ, том под `DATA/`, сеть до моста
   через `host.docker.internal`) и compose-сервис, чтобы весь стек поднимался
   одной командой `docker compose up`.

### Что осознанно НЕ делается

- `claude` через exec-мост не переводится — у него уже есть отдельный,
  проверенный вживую `claude-bridge` (решение `029`), трогать рабочую схему
  ради унификации без пользы не нужно.
- Технологию самого моста (Python vs Node, конкретный HTTP-фреймворк) этап 1
  не фиксирует — решается в этапе 2 по месту, за образец берётся то, что уже
  оправдало себя в `claude-bridge/server.py`.
