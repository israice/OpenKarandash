## МИГРАЦИЯ POWERSHELL SCREENSHOT — ЗАМЕНА НА NODE-SCREENSHOTS

### ЦЕЛЬ
Убрать PowerShell-скрипт `System.Drawing` из `karandash-server.js`, который срабатывал эвристику антивируса как скрин-скрейпинг (ScriptContainedMaliciousContent), и заменить на нативный Node-модуль `node-screenshots`.

### CURRENT STATE (до миграции)
- `captureScreenshot()` и `listScreens()` запускали `powershell.exe -EncodedCommand` с C# кодом через `System.Windows.Forms` + `System.Drawing`
- Базовая кодировка JPEG без EncoderParameters не триггерила AV, но архитектура была хрупкой: Windows-only, зависимость от PowerShell, временные файлы
- `npm run check` — чисто, AV-риск оставался

### TARGET STATE (после миграции)
- `node-screenshots` (нативный бинарный аддон) захватывает указанный монитор, масштабирует до 480px ширины, возвращает base64 JPEG
- Тот же контракт API: `listScreens()` → `[{index, width, height, primary, name}]`, `captureScreenshot(n)` → `data:image/jpeg;base64,...`
- Кроссплатформенно (Windows/macOS/Linux), нет PowerShell, нет временных файлов

### SCOPE
- `PROJECTS/Karandash/karandash-server.js` — полная перезапись двух функций и удаление импортов `fs`, `os`, `path`, `child_process`
- `package.json` — добавлена зависимость `node-screenshots@^1.0.1`

### OUT OF SCOPE
- Клиентская часть Karandash (не менялась)
- Настройка экрана в Settings (API `/api/screenshot/screen` не менялся)

### RESPONSIBILITY
- `karandash-server.js` владеет скриншотом полностью — нигде больше `spawn('powershell')` для скриншотов нет

### DEPENDENCIES
- Добавлено: `node-screenshots@^1.0.1` (нативный, компилируется при `npm install`)
- Удалено: неявная зависимость от PowerShell 5.1+ и .NET Framework

### LEGACY
- Удалены: `fs`, `os`, `path`, `child_process` импорты, две PowerShell-функции (90+ строк C#), временные файлы в `os.tmpdir()`

### TESTS
- `npm run check` — **PASS** (нет циклических связей, размер файлов, vh/vw — чисто)
- Ручное тестирование API:
  - `POST /api/screenshot/screens` → 3 экрана с корректными координатами/именами
  - `POST /api/screenshot` → base64 JPEG (~23KB для 1920x1080, ~6KB для 3840x2160)

### SECURITY
- Риск AV-флага **устранён** — нет PowerShell, нет `System.Drawing`, нет ручной JPEG-кодировки
- Граница доступа не изменилась: маршруты `/api/screenshot*` проходят ту же проверку Origin/localhost (decision 103)

### RISKS
- `node-screenshots` — нативный модуль; на некоторых CI/Win могут требоваться Visual Studio Build Tools (локально работает)
- Порядок мониторов в `node-screenshots` — по Z-order, не по индексу `Screen.AllScreens` WinForms; индекс 0 теперь — не обязательно первичный. API отдаёт `primary: true/false`, клиент может выбрать. Settings уже показывают все экраны — пользователь выберет.

- [x] API contract preserved (listScreens, captureScreenshot) — таблица маршрутов не изменилась, `/api/screenshot`, `/api/screenshot/screens`, `/api/screenshot/screen` на месте

### BLOCKER
`PROJECTS/Karandash/karandash-server.js:50` — `img.crop(0, 0, SCREENSHOT_WIDTH, h)` **не уменьшает снимок, а вырезает прямоугольник из левого верхнего угла**. Миниатюра — это угол экрана, а не весь экран, сжатый до 480 px.

Доля от кадра зависит от монитора: на 1920×1080 уходит 1/4 по каждой оси (1/16 площади), на 3840×2160 — 1/8 по оси (1/64 площади). Миниатюра всегда 480×270, то есть на всех мониторах это один и тот же маленький угол.

### ROOT CAUSE
Замена PowerShell (`Bitmap($full, $w, $h)` — это **масштабирование**) на `node-screenshots` сохранила имя `SCREENSHOT_WIDTH` и формулу высоты, но сменила смысл операции. У `node-screenshots` нет метода resize вообще: в `index.d.ts` у `Image` есть только `crop*`, `toPng*`, `toJpeg*`, `toBmp*`, `toRaw*`. Слово «масштабирует» осталось только в комментарии на строке 41.

### IMPACT
- **Поведение сломано:** `POST /api/screenshot` возвращает угол экрана вместо снимка целиком. Это то, что уходит в сессию как миниатюра Karandash.
- Задевает два потребителя: `karandash.js:397` (миниатюра сессии) и `settings-screenshot.js:40` (предпросмотр экрана в Settings).

### ЧТО ПРОВЕРЕНО ФАКТИЧЕСКИ
- `crop` — истинное вырезание: два выреза одного кадра из разных `y` дают разные хэши (проверено дважды, в разные дни: `9999b643…`/`210fae3…` и `325e8701…`/`b3d1f1a0…`), значит содержимое зависит от положения, а не от размера.
- Все три монитора машины дают `crop` ровно 480×270 — независимо от исходного разрешения, то есть результат не «сжатый кадр», а одинаковый по размеру угол.
- Полный кадр против текущего результата (замер по всем трём мониторам, полный JPEG → base64):
  - 1920×1080: 156 343 Б → base64 204 КБ; угол 17 022 Б → 22 КБ (**×9**)
  - 1920×1080 (второй): 100 867 Б → 131 КБ; угол 6 213 Б → 8 КБ (**×16**)
  - 3840×2160: 833 332 Б → **1085 КБ**; угол 10 140 Б → 13 КБ (**×82**)
  Итог по трафику — от ×9 до ×82 в зависимости от монитора и содержимого экрана. Порядок величин (~10–80×), а не точное число.
- В `package-lock.json` **нет ни одной библиотеки масштабирования** (`jimp`/`sharp` отсутствуют). Пустой каталог `node_modules/@jimp` — остаток неудачной установки, в манифесте его нет.
- В `package.json` `@nut-tree-fork/nut-js` уже убран (коммит `0efd60c`) — этот упрёк снят, чинить нечего.

### OPTIONS
1. **Добавить библиотеку масштабирования** (`sharp` или `jimp`) и заменить `crop` на resize. Возвращает прежнее поведение точно. Цена: новая зависимость, `sharp` — нативный модуль со своим Build Tools на Windows.
2. **Оставить полный кадр, масштабировать в CSS.** Ноль новых зависимостей. Цена: ×9…×82 трафика на каждый снимок (до ~1 МБ base64 на 4K-мониторе), и полный кадр уходит в сессию целиком.
3. **Откатить замену PowerShell.** Поведение возвращается, но вместе с ним возвращается эвристика антивируса, ради устранения которой миграция и делалась.

### RECOMMENDATION
Вариант 1 (`sharp`) — единственный, который возвращает смысл `SCREENSHOT_WIDTH` без регрессии по трафику и без возврата AV-риска. Но это **новая зависимость и новое решение**: по `AGENTS.md` (§33, §39) выбор провайдера скриншотов — не то, что исполнитель вправе решить молча, тем более что `AGENTS.md` отдельно запрещает рыхлые нативные зависимости.
