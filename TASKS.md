# Задачи: граф сессии во Flow

## Контекст

`chat.md` описывает канвас как «карту фактического выполнения»: ноды — реальные шаги
агента, каждая раскрывается гармошкой, правка графа меняет поведение в будущих сессиях.

Разбор кода показал, что ближайшая часть этой идеи уже оплачена, но не подключена:

- `/api/sessions/messages` (`server.js:1598`) отдаёт **23 поля** на сообщение —
  `toolName`, `toolInput`, `toolResult`, `toolError`, `toolUseId`, `parentToolUseId`,
  `model`, `effort`, токены, стоимость, `stopReason`, `inputSent`, `resultMeta`,
  `extraMeta`, плюс роли `thinking`, `hook`, `system`, `unknown`, `top_level`.
- `buildSessionFlow` (`PROJECTS/Flow/flow.js:1584`) читает из них **два**: `role` и `text`.
  Всё, кроме `user`/`assistant`/`tool`, попадает в ветку `else` и подписывается «Answer» —
  хук в графе выглядит как ответ модели.
- `PROJECTS/Feed/page.js:452` уже рисует эти поля карточками-гармошками, то есть
  формат вывода один раз придуман и проверен.

Второй факт: `buildSessionFlow` начинается со сноса всех нод канваса и создаёт новые
с id `flowNode_<seq>_<Date.now()>` (`flow.js:1047`). При живой сессии перестройка идёт
раз в секунду (`flow-session-sync.js`, `scheduleRebuild`). Следствия:

- любая ручная вставка ноды (плюс на ребре) и любая правка текста стираются через секунду;
- `deleteNode` (`flow.js:1458`) чистит позиции, но **не** `flowNodeText`/`flowNodeQuestions` —
  хранилище копит осиротевшие ключи навсегда;
- каждый `savePosition`/`saveGraph` — отдельный `POST /api/flow/state/set` (`flowSet`,
  `flow.js:56`). Сессия в 200 сообщений даёт порядка 800 запросов в секунду.

Цель этапов 1–2 — сделать граф честной картой того, что произошло. Этапы 3–4 —
вторая половина идеи (правка графа влияет на будущее), она требует того, чего в проекте
нет вовсе, и вынесена отдельно.

## 1. Богатые ноды сессии и стабильные id

Один этап, потому что второе — предусловие первого: гармошка, схлопывающаяся раз в
секунду вместе с перестройкой, бесполезна.

Всё правится в `PROJECTS/Flow/flow.js` (+ `flow.css`), сервер не трогаем.

- [x] **1.1. Детерминированные id.** `flowNode_<sessionId>_<position>` вместо счётчика с
      `Date.now()`. `addChildNode`/`addChildNodeRight`/`ensureRootNode` (`flow.js:1045`,
      `1070`, `1474`) принимают необязательный id, при его отсутствии работает прежний
      счётчик. Id сессии сервер строит как `${target.id}-${Date.now().toString(36)}`
      (`server.js:671`) — только буквы, цифры и дефис, для DOM-id и селектора безопасно.

- [x] **1.2. Инкрементальная достройка вместо `delete all`.** `buildSessionFlow` сверяет
      сообщения с уже стоящими нодами: которых нет — создаёт, которые есть — обновляет
      содержимое, лишние ноды **этой же сессии** (сообщение исчезло) — удаляет. Ноды с
      чужим префиксом id (вставленные пользователем) не трогает вовсе.

- [x] **1.3. Пакетная запись состояния.** На время построения `flowSet` копит изменения
      и шлёт один запрос в конце. Мера того же порядка, что и 1.2: без неё богатые ноды
      только ухудшат нагрузку.

- [x] **1.4. `deleteNode` чистит за собой** `flowNodeText` и `flowNodeQuestions` — сейчас
      удаляются только позиции (`flow.js:1464`).

- [x] **1.5. Таблица видов ноды.** `role` + `toolName` → `{ эмодзи, css-модификатор,
      заголовок }`. Разбор: `user`, `assistant`, `thinking`, `hook`, `system`/`unknown`/
      `top_level`, а внутри `tool` — префикс `mcp__`, `WebSearch`/`WebFetch`, `Read`/
      `Write`/`Edit`, `Bash`, `Task`, `AskUserQuestion`, `Grep`/`Glob`. `toolError` — своя
      красная рамка. Эмодзи ставится в `.flow-node__avatar`, цвет — классом
      `.flow-node--kind-*` на ноде.

      Select `.flow-node__type` (`index.html:347`) **не трогаем**: это словарь
      пользователя для собственной разметки, а не тип факта из сессии.

- [x] **1.6. Гармошка — три секции** (по §4 `chat.md`): «Что вошло» (`toolInput`,
      для user — `inputSent`, если отличается от `text`), «Что произошло» (`text`,
      для `thinking` — рассуждение), «Что вышло» (`toolResult`, ошибка выделена).
      Нативный `<details>` в теле ноды — без своего JS на раскрытие.

      Из `PROJECTS/Feed/page.js` переиспользуем только `prettyJson` (`page.js:79`) —
      скопировать в `flow.js`. Прямая зависимость Flow от Feed недопустима: Feed —
      страница кнопки «+», пользователь удаляет её из меню (`DOCS/decisions/016`).

      Два места, где это цепляет существующий код:
      - высота ноды меняется → на `toggle` звать `layoutAllNodes()` + `drawEdge()`;
      - клик по `<summary>` не должен начинать перетаскивание ноды — проверить
        обработчик drag и добавить исключение, как оно уже сделано для select/кнопок.

- [x] **1.7. Вложенность субагентов.** Шаг с `parentToolUseId` вешается под ноду, чья
      `toolUseId` совпадает, а не в общую плоскую цепочку. Это §12–13 `chat.md`
      («модели и субагенты — ноды») из уже имеющихся данных.

**Проверка:** руками в браузере на живом сервере: выбрать в тулбаре Flow сессию с вызовами инструментов и
хуками, убедиться, что виды нод различаются, гармошка открывается и рёбра
пересчитываются; затем запустить ход из Chat по той же сессии и убедиться, что открытая
гармошка переживает живую перестройку, а вставленная вручную нода не исчезает.

## 2. Документы как ноды (§9 `chat.md`)

- [x] Отдельная нода на файл: путь из `toolInput.file_path`, дедупликация по пути.
      Это и есть различие `document.md` (постоянный источник) и `document.md @ session`
      (конкретное использование), которого просит §9. Входящее ребро у неё, как и у
      любой другой ноды, ровно одно — от самого свежего использования; раскладка дерева
      умеет держать позицию только по одному родителю, а «ребро от каждого использования»
      копило столько стрелок в одну ноду, сколько раз файл тронули за сессию, и они
      рисовались поверх чужих веток.
- [x] Открытие и правка содержимого — через уже опубликованные наружу
      `MissionGraph.createFileEditor` / `MissionGraph.nodeByPath` и `MdEditors.attach`
      (перечислены в `AGENTS.md`, так же их зовёт `PROJECTS/Book/book-tab.js`).
- [x] Файлы, которых коснулась сессия без единого вызова инструмента: корневой
      `CLAUDE.md` и файл авто-памяти (`memory/MEMORY.md`) подмешиваются CLI в
      системный промпт/контекст до первого хода агента — см. §5 ниже. Честный
      канал для такого факта — хук (`DOCS/decisions/019`): `SessionStart`
      (`.claude/hooks/context-files-node.js`) сообщает список реально
      загруженных файлов строкой роли `hook`, `messageFilePaths` (`flow.js`)
      достаёт их оттуда так же, как `toolFilePath` достаёт путь из `Read`/`Edit`.
      Пользовательский `~/.claude/CLAUDE.md` (+ его `@`-импорты, напр. `RTK.md`)
      добавляется условно: `askClaude` (`server.js`) при сборке `LEAN_ARGS`
      ставит дочернему процессу `OPENKARANDASH_SETTING_SOURCES`, хук видит эту
      переменную и включает файл, только когда её нет (т.е. запуск не сузил
      `--setting-sources` и источник настроек `user` реально активен).
      Проверено вживую: под `LEAN_ARGS` глобальные хуки пользователя
      (`~/.claude/settings.json`) в трассе headless-сессий не появляются вовсе —
      `user`-источник правда исключён; без переменной хук честно включает файл.
- [x] Вызов `Skill` читает `SKILL.md` в контекст целиком — тот же факт, что и
      `Read`, только путь не в поле `file_path`, а собирается из имени навыка
      (`toolFilePath`, `flow.js`). Скоуп `plugin:skill`/`dir:skill` неоднозначен
      без доступа к списку плагинов — на таких путь не строим, чем гадать.

Отдельным этапом, потому что это первый случай, когда нода не соответствует одному
сообщению: 1.1 даёт ей id вида `flowNode_<sessionId>_file_<хэш пути>`.

## 3. Правка на графе (§6, §7, §10)

Механика на канвасе уже есть — плюс на ребре вставляет ноду, тексты редактируются,
блок `.flow-node__questions` готов. Не хватает двух вещей, обе делаются здесь:

- [x] Пометка «нода добавлена пользователем» в состоянии Flow, переживающая перестройку
      графа сессии (после 1.2 такие ноды уже не сносятся, осталось их сохранять и
      восстанавливать вместе с местом в цепочке).
- [x] Серверный маршрут на изменение строки сессии — сейчас `messages` только пишется
      сервером, маршрута на правку нет. Без него §10 («изменить свои слова») правит
      лишь `flowNodeText`, а не саму сессию. Маршрут — в `PROJECTS/Flow/flow-server.js`
      или в общий набор `/api/sessions/*`; решение записать в `DOCS/decisions/`.
- [x] Гейты (§7) на этом этапе — только свойство ноды (тип `ask_human` в select уже есть).
      Исполнением занимается этап 4.

## Чего в плане нет и почему

**§5 «происхождение каждого шага» в полном виде.** Настоящих причинных связей в базе
две: порядок сообщений и вложенность в субагента (`parentToolUseId`). Связь «действие
появилось из-за правила X» по-прежнему нигде не записана: строка `hook` соседняя по
времени, но не связана причинно. Сам факт «`CLAUDE.md` был в контексте» теперь в трассе
есть (см. пункт 2 выше — `SessionStart`-хук), но это узел документа, а не стрелка
причины; рисовать стрелку «шаг X случился из-за правила Y» — по-прежнему врать графом.
Появится вместе с движком из этапа 4, который сам и будет её записывать.

**Полный дамп всех полей в ноде.** Нода 250 px шириной (`flow.css:121`); 23 поля в неё
не влезают читаемо. Полный дамп уже есть в Feed, дублировать его на канвасе незачем.

**Вынос рендерера полей в общий модуль.** При трёх секциях общего кода остаётся один
`prettyJson` — общий модуль ради него не окупается (`AGENTS.md`: каждая абстракция
обосновывается). Понадобится, если этап 2 или 3 захочет те же карточки целиком.

**Локальные LLM.** Тема снята в первой же строке `chat.md`.
