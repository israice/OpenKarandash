## Искать потерянные функции в истории git, а не переписывать заново

- **Когда применим:** Проверка no-undef показала обращение к функции, которой нигде нет
- **Что делать:** git log -S "<имя>" -- <файл> находит коммит, где функция ещё была; git show <коммит>:<файл> даёт прежнюю реализацию. Восстановить её, а не сочинять новую: разметка и CSS-классы уже рассчитаны на прежний вид.
- **Чем подтверждён:** Так восстановлена pickInstall в PROJECTS/Settings/settings.js: класс picker__item и стиль picker__version уже были в settings.css и совпали без правок
- **Записано:** 2026-09-07 (сессия 1a3d5d21)

## Проверять миграцию базы на копии в /tmp, а не на живой базе

- **Когда применим:** Задача добавляет колонки в DATA/.sessions.db, а поднимать сервер из сессии нельзя
- **Что делать:** Скопировать три файла базы (.db, -wal, -shm) в папку сессии под /tmp и прогнать миграцию отдельным коротким скриптом на копии: PRAGMA table_info до и после, счёт строк, новый вид запроса listMessages, пробная запись новых полей. /tmp — ext4, поэтому node:sqlite не спотыкается на 9p, как на самой DATA. Копировать обязательно все три файла: в режиме WAL часть уже записанного лежит в журнале, и копия одного .db окажется старее базы.
- **Чем подтверждён:** Так проверены колонки Event Schema (source/actor/event_type/task_id/attempt_id/provider/raw): на копии видно, что старая база открывается, ALTER TABLE проходит, а у прежних строк новые поля читаются как null
- **Записано:** 2026-09-18

## Копию базы перед необратимой правкой схемы делает сам сервер, по метке-колонке

- **Когда применим:** Нужен ALTER TABLE, который в SQLite не откатывается, а в базе лежит то, что нельзя потерять
- **Что делать:** Перед блоком миграций вызвать копирование с условием «в таблице ещё нет колонки-метки» (первой из добавляемых). Тогда копия делается ровно один раз, а каждый следующий запуск ничего не копирует, потому что колонка уже есть. Ошибку копирования не глушить, а пробрасывать: не получить новые поля лучше, чем молча потерять историю.
- **Чем подтверждён:** backupBeforeSchemaChange в server.js — на живом сервере пользователя копия легла в DATA/backups/ ровно один раз, в момент первого запуска с новой схемой
- **Записано:** 2026-09-18
