## Искать потерянные функции в истории git, а не переписывать заново

- **Когда применим:** Проверка no-undef показала обращение к функции, которой нигде нет
- **Что делать:** git log -S "<имя>" -- <файл> находит коммит, где функция ещё была; git show <коммит>:<файл> даёт прежнюю реализацию. Восстановить её, а не сочинять новую: разметка и CSS-классы уже рассчитаны на прежний вид.
- **Чем подтверждён:** Так восстановлена pickInstall в PROJECTS/Settings/settings.js: класс picker__item и стиль picker__version уже были в settings.css и совпали без правок
- **Записано:** 2026-09-07 (сессия 1a3d5d21)

## Проверять миграцию базы на копии в /tmp, а не на живой базе

- **Когда применим:** Задача добавляет колонки в DATA/.sessions.db, а поднимать сервер из сессии нельзя
- **Что делать:** Скопировать три файла базы (.db, -wal, -shm) в папку сессии под /tmp и прогнать миграцию отдельным коротким скриптом на копии: PRAGMA table_info до и после, счёт строк, новый вид запроса listMessages, пробная запись новых полей. /tmp — ext4, поэтому node:sqlite не спотыкается на 9p, как на самой DATA. Копировать обязательно все три файла: в режиме WAL часть уже записанного лежит в журнале, и копия одного .db окажется старее базы.
- **Чем подтверждён:** Так проверены колонки Event Schema (source/actor/event_type/task_id/attempt_id/provider/raw): на копии видно, что старая база открывается, ALTER TABLE проходит, а у прежних строк новые поля читаются как null
- **Записано:** 2026-09-18

## Копию базы перед необратимой правкой схемы делает сам сервер, по метке-колонке

- **Когда применим:** Нужен ALTER TABLE, который в SQLite не откатывается, а в базе лежит то, что нельзя потерять
- **Что делать:** Перед блоком миграций вызвать копирование с условием «в таблице ещё нет колонки-метки» (первой из добавляемых). Тогда копия делается ровно один раз, а каждый следующий запуск ничего не копирует, потому что колонка уже есть. Ошибку копирования не глушить, а пробрасывать: не получить новые поля лучше, чем молча потерять историю.
- **Чем подтверждён:** backupBeforeSchemaChange в server.js — на живом сервере пользователя копия легла в DATA/backups/ ровно один раз, в момент первого запуска с новой схемой
- **Записано:** 2026-09-18

## Строка ленты из нескольких событий — сырое дописывается, а не затирается

- **Когда применим:** Одна строка messages собирается из двух и более событий источника: шаг инструмента (вызов + результат), хук (hook_started + hook_response), итоговая реплика (текст + result/run.completed)
- **Что делать:** Первое событие — stampRaw, каждое следующее — appendRaw (server.js): raw превращается в {rawEvents:[…]}. stampRaw второй раз звать нельзя — он молча затирает вызов результатом. Строку, рождённую мимо record* (как запасная в finishExchange), помечать stampEvent вручную, иначе она остаётся без source/event_type
- **Чем подтверждён:** Прогон appendRaw на SQLite в памяти (склейка, третье событие, пустая строка, обрезка по 400000); npm run check чист. Живьём не проверено
- **Записано:** 2026-09-19

## Проверять разрешение адреса прямым вызовом модуля, а не поднятым сервером

- **Когда применим:** Задача добавляет новую ветку в маршрутизацию или в отдачу статики, а запускать server.js из сессии нельзя
- **Что делать:** Вынести разбор адреса в отдельный модуль SYSTEM/core/ с чистой функцией «адрес → что отдавать» и прогнать её через node -e на живых данных: обычный путь, путь без завершающего слэша, попытка выйти вверх через .., неизвестное имя, чужой адрес. Сервер тогда получает готовую проверенную развилку, а глазами пользователь смотрит уже работающую фичу, а не логику разбора.
- **Что делать (сильнее):** Если развилка отдаёт ответ, а не только вычисляет путь, вынести в модуль и саму отдачу — тогда во временном скрипте поднимается http.createServer поверх того же модуля на свободном порту, и проверка идёт настоящими запросами. Для страницы этого мало: надо вытащить из отданного HTML все src/href и запросить каждый, иначе не видно, что часть ресурсов отдаётся 404 и экран откроется битым.
- **Чем подтверждён:** Так проверен SYSTEM/core/branch-preview.js на трёх настоящих рабочих копиях git worktree: 9 случаев адресов (редирект, файл, обход вверх, неизвестная ветка) плюс обход всех 35 ресурсов страницы. Именно перебор ресурсов и вскрыл, что node_modules в рабочей копии ветки нет и htmx там отдавался бы 404 — логикой это не замечалось
- **Записано:** 2026-09-18

## Ход продолжает агент из Settings, а не Hermes с мозгом-claude по умолчанию

- **Когда применим:** Сессию ведёт opencode/codex/pi, а ход уходит в коннектор Hermes — тот по умолчанию думает claude-bridge-sonnet, и при исчерпанной подписке claude ход умирает с 429, хотя выбранный в Settings агент жив и держит историю сессии
- **Что делать:** Не менять мозг Hermes (opencode не умеет быть её brain — он гоняет своего агента, а не произвольные tool-схемы). Перенаправлять ход владельцу сессии: в начале askHermes (server.js:2314) смотрим agentNameByTarget(getSessionMeta.get(sessionId)?.target); если это прямой CLI (opencode/codex/pi) и он подключён — adapter.ask({prompt, sessionId, mode, model, effort}), тот с resumeAndHandoff продолжит своей историей. Hermes-путь оставлять только для claude-сессий (029) и hermes-*.
- **Чем подтверждён:** Случай 2026-09-18 («сделал, проверь» → 429 claude-bridge-sonnet для opencode-wsl-сессии); DOCS/decisions/043; node --check и npm run check чисты
- **Записано:** 2026-09-18
